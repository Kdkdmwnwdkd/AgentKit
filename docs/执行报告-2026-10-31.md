### 1.2 三个真正的短板

按「用户是否会当场受损」排序：

**① 崩溃语义：六家里最差的一档。**
`RealAgentLoop` 的 `checkpoint` 参数默认 `null`（`RealAgentLoop.kt:140`），而唯一的生产构造点 `ChatViewModel.kt:2176-2193` **没有传这个参数**。也就是说每批消息变更后的 `checkpoint?.invoke(...)`（`:304 / :340 / :370 / :591`）在生产环境里全是空调用。
历史落盘只发生在 `conversationStore.appendMessage`（`ChatViewModel.kt:3370`），粒度是「消息上屏时」。
后果：进程在「工具已执行、结果未落盘」之间被杀，重进后模型看到的最后一条是 Assistant 的 tool_call，下一轮会**重复执行同一批操作**。写文件、发消息、点按钮都算。

**② 工具执行没有超时。**
`executeBatch`（`RealAgentLoop.kt:451`）与 `ToolExecutor` 全程没有 `withTimeout`。在 `core/agent/` 与 `tools/` 两个包内检索，`withTimeout` 只出现在 `AskUserBroker:67`、`PlanBroker:84`、`SubAgentRunner:71`、`NetworkRecovery:104`——都是周边组件，**主执行路径没有**。
后果：一个卡住的 shell 命令能让整轮挂到用户手点停止。

**③ 错误分类太粗。**
`isRetryable` 的 `else -> true`（`RealAgentLoop.kt:773`）把「契约违约 / 参数错误 / 反序列化失败」一律当成网络抖动，走 3s/10s/25s 退避重发 4 次。
后果：用户白等约 38 秒，最后看到一条与真实原因无关的「网络超时」。

这三条都不是「想错了」，是**该收的口没收到**。

## 四、怎么干

### 4.1 每一项的固定流程

```
1. 先写失败断言（行为 harness，不是 src.contains）
2. 跑 → 确认它是红的，且红的原因正确
3. 改产品码
4. 跑 → 绿
5. 跑 hotfix11 全量（173 项）确认无回归
6. 提交（一条改动一个 commit）+ 推送
7. 等 CI 绿 → 验 Release 的 versionCode
```

第 2 步不能省。断言没红过，就不知道它到底测了什么。

### 4.2 断言规范（S0-3）

| 允许 | 禁止 |
|---|---|
| 构造真实对象、调真函数、断言输出 | `src.contains("...")` 锁字面量 |
| 断言行为与不变量（N 秒内返回、文件可解析、次数相等） | 断言某个变量名 / 某行代码顺序 |
| 断言「数量变化必须显式更新」 | 断言「这个文件里出现过这句话」 |

存量文本断言不一次性清理（成本高、且它们确实挡住过一些回归），但**新写的一律真跑**。

### 4.3 分工与并行

- 互不依赖的项并行跑 harness（P0-c / P0-d / P0-e 可同时改）。
- 构建一律后台跑，不空转等。
- 需要真机/模拟器验证的（布局类），先 `uiautomator dump` 拿真实 dp 再动手，不靠估算。

### 4.4 提交与发布

- 一个 P0 一条 commit，标题写清「修的是什么行为」，不写「重构 X」。
- 推送走 Git Data API（`git push` 到 github:443 会超时）。
- CI 绿后验 `aapt2 dump badging` 的 `versionCode`，不靠 Release 标题判断。

## 五、本轮具体怎么改（P0-a 展开，其余同理）

### 5.1 P0-a：回合日志落盘 + 孤儿修复

**新增 `core/AtomicJsonFile.kt`**

```kotlin
object AtomicJsonFile {
    // tmp → fd.sync() → rename(2)。rename 在同一文件系统内是原子的：
    // 任何时刻被杀，磁盘上要么是旧完整版本，要么是新完整版本，不会是半截。
    fun write(path: File, bytes: ByteArray)
    fun readOrNull(path: File): ByteArray?
}
```

**新增 `core/agent/RunJournal.kt`**

```kotlin
class RunJournal(private val dir: File, private val keepTurns: Int = 20) {
    /** 每个 checkpoint 调用一次；同回合覆盖写，滚动保留最近 20 个回合。 */
    fun writeTurn(convId: String, turnIndex: Int, messages: List<ChatMessage>)

    /** 启动时调用：找出「有 tool_call 无配对 tool_result」的回合，补合成结果。 */
    fun repairOrphans(): List<RepairReport>

    fun markInterrupted(convId: String, turnIndex: Int)
}
```

**接入 `RealAgentLoop`**

`checkpoint` 语义不变（仍是 `(List<ChatMessage>) -> Unit`），由 `ChatViewModel` 传：

```kotlin
checkpoint = { msgs -> runJournal.writeTurn(convId, turnIndex, msgs) }
```

`checkpoint` 是非挂起函数（`Hooks.kt` 的注释解释了原因：调用点可能在 `NonCancellable` 里，不可二次抛取消），所以落盘必须在内部 `launch` 到 IO 线程，且**失败只记日志不抛**——落盘失败不能弄挂正在跑的回合。

**孤儿修复的文案**（这一条决定它有没有用）

```
工具 <name>(<args 摘要>) 的调用已发出，但结果未落盘：进程在它返回前退出了。
该操作**可能已经生效**。请先用只读方式核对（ls / git status / 查当前界面），
确认现状后再决定是否重试；不要直接重复执行。
```

关键词是「可能已经生效 + 先只读核对」。若只写「执行失败，请重试」，模型必然重跑写操作，等于没修。

**验收 `RunJournalVerification`（行为 harness）**

| 断言 | 内容 |
|---|---|
| J1 | 写入后可解析，字段与原消息逐条相等 |
| J2 | **模拟进程被杀**：只写 `.tmp` 不 rename → 重启读到旧完整版本，不是半截 |
| J3 | 有 call 无 result → 修复恰好补一条合成 result，文案含「可能已经生效」 |
| J4 | 已配对的回合**不被**修补（防误伤） |
| J5 | 21 个回合后最旧的被清理，其余可读 |
| J6 | 两线程各写 50 次同一回合 → 文件始终可解析（原子性） |

J2 和 J6 是这个 harness 的核心，其余是配套。

### 5.2 P0-b：`Hooks` 可改写

```kotlin
data class StepRequest(
    val messages: List<ChatMessage>,
    val systemPrompt: String? = null,   // null = 用 loop 现有的
)

interface Hooks {
    /** 返回 null = 不干预（默认）；返回对象 = 本次请求用它的内容。 */
    fun beforeSerialization(messages: List<ChatMessage>): StepRequest? = null
    // 其余三个时机保持 Unit
}
```

价值不在「能改」，在**提示拼装从此可以被单测**——不用起整个 loop。
风险控制：hooks 抛异常时捕获并降级为 null，绝不让观测代码弄挂回合。

### 5.3 P0-c：ShellTool 三处

`ShellTool.kt:246,268,355` 的 `take(400)` / `take(2_000)` 是**工具内部**提前截断，绕过了 `ToolLimits` 的头尾策略——即便上层做了 6/4 分配，到这里的原文已经只剩开头。

改法：完整输出落盘 `filesDir/tool-output/<callId>.log`，返回「首 2000 + 尾 2000 + 全文路径」。模型需要中间部分时用 `read_file` 分页读。

验收：跑真实 `seq 1 20000`，断言返回含 `1`、含 `20000`、含路径、长度 < 上限；断言落盘文件行数 = 20000。

### 5.4 P0-d：重试白名单

```kotlin
private fun isRetryable(e: Throwable): Boolean = when (e) {
    is LocalInferenceException -> false          // 确定性失败，重试只是再失败
    is LlmHttpException -> e.retryable           // 5xx / 429 才 true
    is java.io.IOException -> true               // 连接层抖动
    else -> false                                // 契约违约 / 参数错误 / 反序列化
}
```

验收：假 provider 抛 `IllegalArgumentException` → 断言 0 次重试、耗时 < 500ms；抛 503 → 断言按 3s/10s/25s 重试 3 次。

### 5.5 P0-e：schema 补齐

`AgentContract.JsonSchema.Property` 已有 `items` / `properties` / `required`（`:180-190`），但三处序列化都没写：

- `core/LLMClient.kt` 的 `toApiTool`
- `core/llm/ClaudeClient.kt:493`
- `core/llm/GeminiClient.kt:386`

三处各自手写同一段 JSON，天然会漂移。改法：在 `AgentContract.kt` 加一个 `Property.toJsonObject()` 递归序列化，三处都调它。

验收：断言 `spawn_agents` 的请求 JSON 含 `"items":{"type":"object"`；断言旧工具（扁平字段）序列化结果**一个字节都没变**。
