# 工具链版本映射修复（2026-10-24）

## 一句话结论

原来的「指定版本安装」有 **4 个会直接导致命令失败**的硬错误——拼出的包名在官方仓库里根本不存在。
本次按官方仓库索引逐个核实后重写映射，并用 80 条断言锁死；装不到的版本现在会**明确拒绝**，不再悄悄换成别的大版本。

## 一、核实到的仓库事实

数据来源：`dl-cdn.alpinelinux.org` 的 APKINDEX、`packages.debian.org`、`sources.debian.org`（2026-10-24 查询）。

| 发行版 | nodejs | python3 | openjdk |
| --- | --- | --- | --- |
| Alpine 3.19 | 20.15.1 | 3.11.14 | 11 / 17 / 21 均有分包 |
| Alpine 3.20 | 20.15.1 | 3.12.13 | 11 / 17 / 21 均有分包 |
| Alpine 3.21 | 22.23.2 | 3.12.15 | 11 / 17 / 21 均有分包 |
| Debian 12 (bookworm) | 18.20.4 | 3.11.2 | **只有 17** |

三条关键结论：

1. **Alpine 和 Debian 都没有 `nodejs18` / `nodejs20` 这种分版本包。** 每个发行版只有一条 `nodejs` 版本线，版本由发行版决定。Alpine 只在 edge 仓库有 `nodejs-current`。
2. **Debian 没有 `python3.11-pip`。** pip 统一是 `python3-pip`，不跟小版本走。
3. **Debian bookworm 没有 `openjdk-11-jdk` / `openjdk-21-jdk`。** 只有 `openjdk-17-jdk`（11 在 bullseye，21 在 trixie）。

## 二、修掉的四个缺陷

### 1. `apk add nodejs18` —— 必然失败

旧代码把主版本号拼进包名（`nodejs$major`）。Alpine 3.19/3.20 上要 node 18 会生成：

```
apk add --no-cache nodejs18 npm
ERROR: unable to select packages: nodejs18 (no such package)
```

现在包名恒为真实存在的 `nodejs` + `npm`，能否满足目标大版本交由发行版判断。

### 2. `python3.11-pip` —— 不存在的包

旧代码用 `python$v-pip`，Debian 上生成 `python3.11-pip`。已改为 `python3-pip`，Python 解释器仍按 `python3.11` 精确安装。

### 3. 候选版本表撒谎

旧表把 Alpine 的 node 18/20/22 全标成「可装」，把 Debian 的 node 标成「一个都装不上」——两头都错。
现在按 rootfs 里读到的发行版版本收窄，三态展示：

- ✅ 官方源就是这个版本；
- 🔄 能装，但装到的是发行版默认版本；
- ⚠️ 官方源没有，装不到。

### 4. `npm` / `py3-pip` / `openjdk` 在 community 仓库

Alpine minirootfs 常常只启用 `main`。旧命令在只开 main 的 rootfs 上会「node 装上了、npm 没有」。
安装前现在会幂等补 community 源（读 `/etc/alpine-release` 得到版本线，已有则跳过，非 Alpine 则不动）。

## 七、第二轮：把「只能在服务器做」的补完（2026-10-24 下午）

上面第六节那条已经修了，修的过程中又挖出一个更严重的。

### 7.1 抽屉「设置」固定在底部（**已回滚，这是一次事故**）

原意：让设置项不随列表滚走，小屏也能点到。

做法：外层 `Column` 撑满，里面拆成「`weight(1f)` + `verticalScroll` 的滚动区」和「固定底部位」。

结果：**真机上整段菜单被测量成 0 高，抽屉里只剩一个「设置」**。用户截图里抽屉一片空白、
左边孤零零一个齿轮图标。对话 / 模型 / 控制台 / 终端 / 定时任务全部消失。

原因：`ModalDrawerSheet` 给内容的不是「确定高度」约束，`weight(1f)` 在这种约束下拿到 0。
在 720×1280 模拟器上碰巧还能看到内容，所以当时"验证通过"了——这是典型的过度拟合测试环境。

已回滚到单滚动区结构（设置仍在列表末尾，小屏需要滚一下，但不会消失）。
`E-11` 断言也改成反向锁定：**抽屉必须只有一个滚动区，不允许用 weight 拆两层**。

教训：没有真机复现条件时，不要为了迁就模拟器的小屏去改全局布局。

### 7.2 新装应用进容器页永远提示「需要 proot」（已修）

proot 三件套是**首次执行容器命令时**才从 assets 提取的（`ensureBinary`），但容器页的入口判定用的是 `isAvailable`——只看文件在不在，不会触发提取。

结果：新装应用 → 没提取过 → 页面显示「需要 proot 运行时 → 请运行 build-proot.sh」→ 而用户根本没有能触发提取的入口。**容器功能对新用户完全死锁**，真机也一样。

修法：进页面时在 IO 线程 `ensureBinary` 一次（幂等，已就绪直接返回），并把提示分成「正在准备」和「提取失败（附当前 ABI 与解决办法）」。

**真机确认（2026-10-24 第二段录屏）**：容器页正常显示「Alpine Linux · 已就绪 · 点击进入」，
语言运行时区域列出了完整安装命令（community 补源 + `apk add --no-cache nodejs npm python3 py3-pip openjdk17 openjdk17-jdk`）。
这条修复成立。

### 7.3 版本表补齐

按官方索引补了 Alpine 3.18（node 18 / py 3.11）、3.22（node 22 / py 3.12）、3.23（node 24 / py 3.12），Debian 11（node 12 / py 3.9 / java 11、17）。

apk/apt 的报错现在会被归类成「没网」「仓库没这个包」「权限不足」「空间不足」，直接给结论，不再只丢一个 exit code。

### 7.5 x86_64 测试套件（脚本拉取，不进仓库）

新增 `scripts/fetch-x86-testkit.sh` + `-Px86Rootfs=true` 构建开关：额外打进 x86_64 的 Alpine rootfs 与 Termux 版 proot 三件套，让 x86_64 模拟器能把容器页走通。产物在 `app/src/debugX86/assets/`，已 gitignore；CI 与正式包不受影响。

### 7.6 结论：模拟器上容器**仍然跑不起来**

套件齐全后，容器页能正常列出两个发行版、能解压 rootfs，但启动容器报 `proot 执行失败`。

手动复现（adb root，把 proot 与 rootfs 搬到 `/data/local/tmp`）：

```
proot --version            → 正常输出 5.1.107.100
proot -r <rootfs> /bin/busybox echo HI
  → proot error: execve("/bin/busybox"): No such file or directory
```

rootfs 内 `/bin/busybox`（808KB，0755）、`/lib/ld-musl-x86_64.so.1`（649KB）都在，`/bin/sh -> /bin/busybox` 也正常。加 `-b /dev -b /proc -b /sys`、改 `TMPDIR` 都不解决。

**不是包名/权限问题，是 Termux 构建的 proot 在 x86_64 模拟器内核上无法完成 guest 进程的 execve。** 这条在模拟器上就是走不通，别再花时间——容器内真实执行只能在 arm64 真机验。

### 7.7 真机视频暴露的真因：JNI 里 `snprintf` 返回值当 `write` 长度

真机录屏里容器一起来就断，终端只有两行：

```
FORTIFY: write: prevented 74-byte read from 64-byte
[连接已断开，退出码 134]
```

134 = 128 + 6，SIGABRT。一开始怀疑是 proot 的构建问题（Termux 版开了 FORTIFY），
甚至去试了自建 proot。实际根因在**我们自己的 JNI**：

```cpp
char buf[64];
const int len = snprintf(buf, sizeof(buf), "execve(%s) failed errno=%d\n",
                         cmdStr.c_str(), e);
write(STDERR_FILENO, buf, static_cast<size_t>(len));   // ← len 是"想写多少"，不是"写了多少"
```

`snprintf` 返回的是**如果缓冲区够大一共会写多少字节**。proot 的完整命令行（rootfs 路径 +
一堆 `-b` 绑定）轻松超过 64 字节，`len` 变成 74，`write` 就要从 64 字节的栈缓冲里读 74 字节，
bionic 的 FORTIFY 当场 abort。

危害远不止一行日志：**它发生在 exec 失败的处理路径上**，把真正的 errno 连同一个子进程一起干掉。
于是所有"容器起不来"的现象都长这样，排查方向被带偏到 proot / rootfs / SELinux 上。

修复：缓冲区提到 256，并且统一截断到实际容量再写（`writeErrnoMessage`）。
4 处（`chdir` / `execve` / 第二组 `chdir` / `execvp`）全部改掉。

语法检查已过（NDK clang `-fsyntax-only`）。**实际效果要在真机重新构建后看**——
这次终于能看到 proot 真正返回的 errno 了。

### 7.8 另一个真机问题：设置页/容器页文字上下重叠

**真因（2026-10-24 第二段录屏确认）：设备开了系统的「拼音标注」。**

第二段录像里每个汉字上方都有拼音（跟随系统、动态取色、回答完成提醒…），
汉字被顶起来，和上一行/下一行挤在一起。终端页是英文等宽，所以完全正常——
这也解释了为什么只有中文界面叠字。

这不是 App 能可靠适配的：拼音是系统在排版层给中文附加的注音，行高需求是动态的，
而本项目的排版规范用**固定绝对 lineHeight**（bodyLarge 15/26 等）。拼音一进来就不够用。

处置：
- 代码侧把 `includeFontPadding` 恢复为系统默认（原来全局关掉）。这**不是解药**，
  只是让字体度量回归系统计算，少一点人为压缩。
- 真正的解药是关掉拼音标注：设置 → 显示/无障碍 → 关掉「拼音标注 / 汉字注音」。
- 如果关掉后仍叠字，再回来查——那时才是 App 的排版问题。

（上一版文档把这条归因于 `includeFontPadding`，是错的，已更正。）

## 十、首启漏斗：对话页「准备清单」

### 问题

配模型之前有引导弹窗，配完之后就没人管了。剩下的三件事散落在三个地方：

- 无障碍 → 权限引导页
- 通知 → 系统设置
- 使用情况 → 系统设置
- 容器 → 设置页里的第三层

用户配完模型会以为「完事了」，过几天发现「它不能操作我的手机」，再回来找入口已经忘了路径。
这不是功能缺失，是**引导断档**。

### 做法

对话页顶部一条折叠态卡片：`还差 N 项，就能全自动`。点开列出未完成项，每项一行、
带一句「它能帮你干什么」，点一下直达对应系统页面；四项都就绪后卡片自己消失。

状态来源复用现有链路：`vm.serviceConnected` / `notificationGranted` / `usageGranted`，
容器状态用 `RootfsManager.isExtracted` 在 IO 线程读一次（已解压就不列这项）。

### 刻意不做的

- **不拦路**：不配也能聊天，卡片可折叠、可无视。拦路是首启漏斗最大的杀手。
- **不弹窗**：弹窗打断正在做的事，卡片贴在顶部不抢焦点。
- **不用百分比**：4 项里差 1 项不代表「75% 可用」，每项是独立增强，说「还差 3 项」更诚实。
- **不放在消息列表里**：一开始插在 `LazyColumn` 的第一个 item，结果空会话走的是另一个
  空态分支，卡片根本不显示。现在放在两个分支之外，空会话和有对话都看得到。

### 验证

模拟器（720×1280 / Android 11）：

- 空会话顶部出现「还差 4 项，就能全自动」
- 展开后列出无障碍 / 通知 / 使用情况（容器已解压，自动从 4 项变 3 项）
- 点「无障碍服务」跳到系统无障碍设置页，无崩溃
- 冒烟脚本加了两条断言，整体 **9/9 通过**

## 十一、长任务存活：补 WakeLock

### 问题

有前台服务 + START_STICKY，但**没有 WakeLock**。

前台服务只保证「进程有通知、不被随手回收」，**不保证 CPU 不睡**。锁屏后 CPU 进入 suspend，
流式响应和容器命令会被挂起，用户看到的是「任务卡住不动」，醒来后可能已经超时。

### 改动

`AgentRunService.onCreate` 拿一把 `PARTIAL_WAKE_LOCK`，`onDestroy` 释放：

- 上限 15 分钟（`acquire(timeout)`）：覆盖绝大多数 Agent 任务；任务卡死时超时自动回收，不耗干电池
- `setReferenceCounted(false)`：只释放一次，避免计数错乱
- 获取失败只记日志、不抛：最坏情况是锁屏后变慢，不是任务失败
- Manifest 里 `WAKE_LOCK` 权限本来就有（第 39 行），无需新增

### 验证

这条**只能在真机验**：模拟器没有厂商省电策略、没有真实 Doze，锁屏行为也不一样。

新增 `scripts/qa/device-survival.sh`：

```bash
ADB=adb bash scripts/qa/device-survival.sh 120
```

先在 App 里发起一个长任务，看到常驻通知后跑脚本。它会：
锁屏 → 等 120s → 比对 pid 与前台服务 → 检查电池优化白名单。

判据是「pid 没变、服务还在、在白名单里」；被重启/被杀会明确区分开
（pid 变了 = 被系统重建，pid 没了 = 被杀）。

脚本还会提示两条它测不了、需要人眼看的：通知栏步骤号有没有继续涨、回 App 看任务状态。

### 补：没有电脑怎么测

`device-survival.sh` 要 adb，但很多用户手上只有手机。所以把自检做进了 App：

**设置 → 自动化 → 后台存活自检**

点一下，通知栏出现一条常驻通知，每 5 秒数字 +5（`已 15 / 300 秒`）。锁屏两分钟后回来看：

- 数字还在涨 → 进程活着、CPU 没睡，任务能继续
- 数字卡住 → 进程在但被冻结（CPU 睡了 / 后台被限制）
- 通知消失 → 进程被杀（厂商省电最典型的表现）

三种结果对应三种修法，比一句「好像断了」有用。

实现要点：`SurvivalCheckService`，前台服务 + `dataSync` 类型，`Handler` 每 5 秒更新通知，
5 分钟自动结束并把通知改成「完成，可划掉」。用前台服务而不是协程，是因为要留下
那条常驻通知当指示灯——进程被杀时它是唯一能看见的信号。

模拟器实测（720×1280 / Android 11）：`15 秒 → 30 秒 → 锁屏 20 秒后 50 秒`，锁屏期间没停。

## 十二、应用内检查更新

### 问题

之前每次出新包，都要人工把加速链接发过去。用户想确认「我装的是不是最新」也没有入口。

### 做法

关于页版本号下面加一行「检查更新」：

```
版本 1.363
当前构建号 363            检查更新
```

点了会请求 `releases/tags/latest`，从标题 `AgentKit latest (run N)` 里抠出构建号，
和本机 `versionCode` 比大小。

### 几个刻意的选择

- **不引入更新库**：只服务一个固定 Release，逻辑就是「读一个数字、比大小」，
  AppUpdater 那类库要加几百 KB 和一堆权限，不值。
- **版本号不从额外清单读**：CI 用 `GITHUB_RUN_NUMBER` 同时写 `versionCode` 和 Release 标题，
  两边天然同源，不会出现「清单忘了更新」的错位。
- **下载地址写死**（走 ghfast 加速通道），不从接口的 `browser_download_url` 取——
  那个指向 github.com 直链，国内很慢；而且让远端决定去哪下载没必要。
- **失败不转圈**：`api.github.com` 在国内不一定通，8 秒超时后直接显示
  「检查失败 + 直接下载最新包 + 打开 Release 页」三个出口。用户要的是新包，不是「检查成功」。

### 验证

- 接口实测：`AgentKit latest (run 363)` → 解析出 363，大于本机 14，判定「有更新」
- 编译通过；UI 组件复用了关于页现有的行样式

## 十四、容器起不来的真因（真机 2026-10-24）：两层问题叠在一起

真机报 `Cannot run program ".../files/bin/proot": error=13, Permission denied`。
查下来是**两个独立问题叠加**。

### 问题一：仓库里的 arm64 proot 是 base64 文本，不是 ELF

```
$ file app/src/main/assets/bin/arm64-v8a/proot
ASCII text, with very long lines (65536)
$ head -c 8 app/src/main/assets/bin/arm64-v8a/proot
f0VMRgIBAQ...
```

`f0VMRg` 正是 `\x7fELF` 的 base64。三个文件（proot / libtalloc.so.2 / libandroid-shmem.so）
全都是 base64 文本——某次提交把二进制当文本存了。

后果：APK 里带的根本不是可执行文件，容器功能从根上就是坏的。
`isAvailable` 只检查「文件存在且可执行位」，文本文件 chmod 0700 后照样过检，
所以 UI 一直显示「已就绪」，直到真正 exec 才炸。

修法：`base64 -d` 解码回真 ELF（aarch64，interpreter `/system/bin/linker64`），
三个文件一起换，依赖名核对过（`libtalloc.so.2` / `libandroid-shmem.so` / `libc.so`）。

### 问题二：Android 10+ 不让从 filesDir 执行 ELF（W^X）

就算二进制是好的，`<filesDir>/bin/proot` 也 exec 不了——`targetSdk 34` 下内核直接
`error=13 Permission denied`。

修法（代码里早就写好的方案，这次落实）：

- proot 改名 `libproot.so` 放进 `app/src/main/jniLibs/arm64-v8a/`
- `packaging { jniLibs { useLegacyPackaging = true } }`——否则 native 库不解压，
  只从 APK 里 mmap，没有可 execve 的路径
- 运行时从 `applicationInfo.nativeLibraryDir/libproot.so` 取
- 两个运行库仍在 assets → 提到 filesDir，靠 `LD_LIBRARY_PATH` 加载
- 原来的 assets 路径保留作回退（旧设备/未来兼容）

### 验证

```
$ run-as com.example.agentkit sh -c "LD_LIBRARY_PATH=... $P --version"
 _____ _____              ___
|  __ \  __ \_____  _____|   |_
|   __/     /  _  \/  _  \    _|
|__|  |__|__\_____/\_____/\____| 5.1.107.100
```

从 `nativeLibraryDir` 执行成功。不加 `LD_LIBRARY_PATH` 时报的是
`library "libtalloc.so.2" not found`——说明已经过了内核的 exec 检查，
不再是 Permission denied。

### 教训

`isAvailable` 这类「文件在不在」的判定，对「能不能真的跑」毫无保证。
这次两个问题都躲过了所有静态检查，只有真机 exec 才暴露。

## 十五、第三个阻塞点：LD_LIBRARY_PATH 指到了错误目录

前两个修完后（真 ELF + 从 nativeLibraryDir 执行），模拟器上报的不再是 `error=13`，而是：

```
CANNOT LINK EXECUTABLE ".../lib/x86_64/libproot.so":
library "libtalloc.so.2" not found: needed by main executable
```

**exec 这一关已经过了**（否则不会进到动态链接阶段），卡在依赖库找不到。

原因：`buildInvocation` 里 `libDir = prootBinary.parentFile`。proot 本体现在位于
`nativeLibraryDir`，于是 `LD_LIBRARY_PATH` 跟着指向 `nativeLibraryDir`，
但 `libtalloc.so.2` / `libandroid-shmem.so` 仍在 `filesDir/bin`。

修法：`buildInvocation` 增加显式 `libDir` 参数，两处调用（`ContainerCommandRunner` /
`ContainerSession`）都传 `ProotRunner.libDir(context)`；`Context` 重载也改为走
`ensureBinary`（优先 nativeProot）。

### 为什么不能把两个 .so 一起塞进 jniLibs

看似更简单，但 `libtalloc.so.2` 的**文件名以数字结尾**，不是 `lib*.so` 形态，
AGP 不会把它当 native 库打包。改名成 `libtalloc.so` 又会破坏 SONAME 匹配
（proot 的 `NEEDED` 写的是 `libtalloc.so.2`）。所以只能分开放、靠 `LD_LIBRARY_PATH`。

## 十六、服务器侧 chroot 实测：安装命令是对的

模拟器上 proot 起不来 guest（见下节），但**安装命令本身**可以在服务器上验证——
服务器就是 x86_64 Linux，x86_64 rootfs 可以直接 chroot 进去。

```
$ sudo chroot /tmp/alptest /bin/cat /etc/alpine-release
3.20.3
$ sudo chroot /tmp/alptest /bin/cat /etc/apk/repositories
.../v3.20/main
.../v3.20/community
$ sudo chroot /tmp/alptest /sbin/apk add --no-cache nodejs npm
(11/12) Installing nodejs (20.15.1-r0)
(12/12) Installing npm (10.9.1-r0)
OK: 75 MiB in 26 packages
$ sudo chroot /tmp/alptest /usr/bin/node --version
v20.15.1
$ sudo chroot /tmp/alptest /usr/bin/npm --version
10.9.1
```

三条结论：

1. 包名 `nodejs` + `npm` 正确，Alpine 3.20 装出来就是 **node 20**，与版本表判断一致
2. 官方 minirootfs 的 `repositories` **已经包含 community**，所以「幂等补源」那段
   在标准镜像上不会重复添加，只在缺 community 的裁剪镜像上生效
3. `apk add --no-cache` 是幂等且可重复执行的，不会因为装过就报错

也就是说：**只要真机上 proot 能起来，这条命令必然能装成 node 20。**

## 十七、模拟器的验证边界（明确写清，避免下次重踩）

| 能力 | 模拟器（x86_64 / Android 11 / TCG） |
| --- | --- |
| proot 从 nativeLibraryDir 执行 | ✅ 通过（`--version` 输出 5.1.107.100） |
| 依赖库 LD_LIBRARY_PATH | ✅ 通过（不再报 not found） |
| proot 启动 guest | ❌ 失败：`the program is an ELF but its interpreter was not found` |

最后一条不是配置问题：

- `/bin/busybox` 是 ELF（`\x7fELF`，808 KB，0755）
- `/lib/ld-musl-x86_64.so.1` 存在（649 KB，0755）
- 符号链接完整（`arch -> /bin/busybox` 等 82 项）
- 同一 rootfs 在同一台机器的 Linux 宿主上 chroot 完全正常

差别只在 **proot 依赖 ptrace 拦截 syscall**，而 TCG 模拟的 Android 内核上这套机制
不工作。原生 ARM 执行的真机没有这个问题。

结论：**容器内真实执行只能在 arm64 真机验证**，模拟器到此为止。

## 十八、真机第二轮：proot 起来了，卡在 /bin/sh

真机（覆盖安装 run 369）点「安装 Node.js」，报：

```
安装失败（exit 1）：proot error: execve("/bin/sh"): No such file or directory
```

**这是明确的进展**：不再是 `Cannot run program` / `error=13`，
说明 proot 本体已经能执行、依赖库也能加载，卡在它去执行 guest shell 的那一步。

### 排除了「绝对符号链接」这个假设

`alpine.tar` 里 `/bin/sh -> /bin/busybox` 是**绝对**链接。怀疑它在 Android 上
会解析到宿主的 `/bin/busybox`（不存在）。于是在服务器上装 proot（Debian 5.1.0）
直接做对照实验：

```
# 原始 rootfs（绝对链接）
proot -r $R /bin/sh -c 'echo PROOT_OK'   → PROOT_OK
# 把 310 个绝对链接全转成相对后再试
proot -r $R /bin/sh -c 'echo PROOT_OK'   → PROOT_OK
```

两种都能跑。**假设不成立**，不是链接形态的问题（proot 自己会做 guest 内解析）。

### 真正可疑的地方：rootfs 是否残缺

`isExtracted` 原来只判 `bin/` 和 `etc/` 两个目录存在。这意味着：

- 解压中断（进程被杀 / 存储不足）会留下 `bin/`、`etc/` 都在、里面却是空的残缺树
- 此后永远显示「已就绪」，`ensureExtracted` 直接 return，**再也不会重新解压**
- 表现就是「UI 说已就绪，proot 说 /bin/sh 不存在」

改动：

1. `isExtracted` 改为校验关键文件：`bin/sh` 存在（**用 lstat**，因为它是指向
   `/bin/busybox` 的符号链接，`File.exists()` 会跟随到宿主不存在的 `/bin/busybox`
   而恒为 false）+ `bin/busybox` 非空
2. `ensureExtracted` 发现目录在但校验不过 → **清空后重新解压**，避免残留让新解压
   「看起来成功」但内容仍不全
3. 安装失败时附 **rootfs 体检**：列出 `bin/sh` / `bin/busybox` / `lib` / `etc/alpine-release`
   的真实状态（类型、链接目标、目标是否在 rootfs 内、bin 条目数）

### 下一步

装新包后进容器页，若 rootfs 不完整会自动重解压（这一步在后台，几秒到几十秒）。
再点安装：

- 成功 → 闭环
- 仍失败 → 错误提示里会带「rootfs 体检」，一屏就能区分是文件缺失还是 proot 层问题

## 十九、自己引入的死循环：布局标记写成「先校验后写」

真机日志：

```
WARN [RootfsManager] rootfs(alpine) 校验不通过，清空后重新解压：bin/sh：链接 -> busybox（目标在 rootfs 内存在）
bin/busybox：919232 字节 / lib：目录 / etc/alpine-release：7 字节 / bin/ 条目数=82
... （同一秒重复 30 多次）
```

体检显示内容**全都齐了**，但 `isExtracted` 仍返回 false。

原因在我上一版的写法：

```kotlin
if (!isExtracted(...)) return null          // ← 这里要求 marker 存在
runCatching { File(d, LAYOUT_MARKER).createNewFile() }   // ← marker 在这里才写
```

`isExtracted` = 内容校验 **且** marker 存在；而 marker 要等校验通过之后才写。
于是永远「校验不过 → 重解压 → 还是校验不过」，每次调用都重解一遍 9 MB。

修法：拆成两层

- `contentReady(d)`：只看 `bin/sh` 存在 + `bin/busybox` 非空
- `isExtracted` = `contentReady` **且** marker 存在
- `ensureExtracted`：解压 → `contentReady` 通过 → **写 marker** → 返回

### 模拟器实测（修复后）

```
点击解压 alpine-x86_64 → 20 秒完成
ls -a rootfs → .agentkit-layout-v2          （标记写入）
readlink bin/sh → busybox                    （相对链接，转换生效）
bin/busybox → 808712 字节
logcat | grep 校验不通过 → 0 条              （不再死循环）
再次进入容器页 → 「已就绪 · 点击进入」，未重复解压
```

### 教训

「校验依赖 A、A 在校验之后才写」这种顺序错误，静态检查看不出来，
日志里表现为无限重试。凡是「标记 + 校验」组合，必须先想清楚写入时机。
