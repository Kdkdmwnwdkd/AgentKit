# 工具链版本映射修复（2026-10-24）

## 一句话结论

原来的「指定版本安装」有 **4 个会直接导致命令失败**的硬错误——拼出的包名在官方仓库里根本不存在。
本次按官方仓库索引逐个核实后重写映射，并用 80 条断言锁死；装不到的版本现在会**明确拒绝**，不再悄悄换成别的大版本。

## 一、核实到的仓库事实

数据来源：`dl-cdn.alpinelinux.org` 的 APKINDEX、`packages.debian.org`、`sources.debian.org`（2026-10-24 查询）。

| 发行版 | nodejs | python3 | openjdk |
| --- | --- | --- | --- |
| Alpine 3.19 | 20.15.1 | 3.11.14 | 11 / 17 / 21 均有分包 |
| Alpine 3.20 | 20.15.1 | 3.12.13 | 11 / 17 / 21 均有分包 |
| Alpine 3.21 | 22.23.2 | 3.12.15 | 11 / 17 / 21 均有分包 |
| Debian 12 (bookworm) | 18.20.4 | 3.11.2 | **只有 17** |

三条关键结论：

1. **Alpine 和 Debian 都没有 `nodejs18` / `nodejs20` 这种分版本包。** 每个发行版只有一条 `nodejs` 版本线，版本由发行版决定。Alpine 只在 edge 仓库有 `nodejs-current`。
2. **Debian 没有 `python3.11-pip`。** pip 统一是 `python3-pip`，不跟小版本走。
3. **Debian bookworm 没有 `openjdk-11-jdk` / `openjdk-21-jdk`。** 只有 `openjdk-17-jdk`（11 在 bullseye，21 在 trixie）。

## 二、修掉的四个缺陷

### 1. `apk add nodejs18` —— 必然失败

旧代码把主版本号拼进包名（`nodejs$major`）。Alpine 3.19/3.20 上要 node 18 会生成：

```
apk add --no-cache nodejs18 npm
ERROR: unable to select packages: nodejs18 (no such package)
```

现在包名恒为真实存在的 `nodejs` + `npm`，能否满足目标大版本交由发行版判断。

### 2. `python3.11-pip` —— 不存在的包

旧代码用 `python$v-pip`，Debian 上生成 `python3.11-pip`。已改为 `python3-pip`，Python 解释器仍按 `python3.11` 精确安装。

### 3. 候选版本表撒谎

旧表把 Alpine 的 node 18/20/22 全标成「可装」，把 Debian 的 node 标成「一个都装不上」——两头都错。
现在按 rootfs 里读到的发行版版本收窄，三态展示：

- ✅ 官方源就是这个版本；
- 🔄 能装，但装到的是发行版默认版本；
- ⚠️ 官方源没有，装不到。

### 4. `npm` / `py3-pip` / `openjdk` 在 community 仓库

Alpine minirootfs 常常只启用 `main`。旧命令在只开 main 的 rootfs 上会「node 装上了、npm 没有」。
安装前现在会幂等补 community 源（读 `/etc/alpine-release` 得到版本线，已有则跳过，非 Alpine 则不动）。

## 七、第二轮：把「只能在服务器做」的补完（2026-10-24 下午）

上面第六节那条已经修了，修的过程中又挖出一个更严重的。

### 7.1 抽屉「设置」固定在底部（**已回滚，这是一次事故**）

原意：让设置项不随列表滚走，小屏也能点到。

做法：外层 `Column` 撑满，里面拆成「`weight(1f)` + `verticalScroll` 的滚动区」和「固定底部位」。

结果：**真机上整段菜单被测量成 0 高，抽屉里只剩一个「设置」**。用户截图里抽屉一片空白、
左边孤零零一个齿轮图标。对话 / 模型 / 控制台 / 终端 / 定时任务全部消失。

原因：`ModalDrawerSheet` 给内容的不是「确定高度」约束，`weight(1f)` 在这种约束下拿到 0。
在 720×1280 模拟器上碰巧还能看到内容，所以当时"验证通过"了——这是典型的过度拟合测试环境。

已回滚到单滚动区结构（设置仍在列表末尾，小屏需要滚一下，但不会消失）。
`E-11` 断言也改成反向锁定：**抽屉必须只有一个滚动区，不允许用 weight 拆两层**。

教训：没有真机复现条件时，不要为了迁就模拟器的小屏去改全局布局。

### 7.2 新装应用进容器页永远提示「需要 proot」（已修）

proot 三件套是**首次执行容器命令时**才从 assets 提取的（`ensureBinary`），但容器页的入口判定用的是 `isAvailable`——只看文件在不在，不会触发提取。

结果：新装应用 → 没提取过 → 页面显示「需要 proot 运行时 → 请运行 build-proot.sh」→ 而用户根本没有能触发提取的入口。**容器功能对新用户完全死锁**，真机也一样。

修法：进页面时在 IO 线程 `ensureBinary` 一次（幂等，已就绪直接返回），并把提示分成「正在准备」和「提取失败（附当前 ABI 与解决办法）」。

**真机确认（2026-10-24 第二段录屏）**：容器页正常显示「Alpine Linux · 已就绪 · 点击进入」，
语言运行时区域列出了完整安装命令（community 补源 + `apk add --no-cache nodejs npm python3 py3-pip openjdk17 openjdk17-jdk`）。
这条修复成立。

### 7.3 版本表补齐

按官方索引补了 Alpine 3.18（node 18 / py 3.11）、3.22（node 22 / py 3.12）、3.23（node 24 / py 3.12），Debian 11（node 12 / py 3.9 / java 11、17）。

apk/apt 的报错现在会被归类成「没网」「仓库没这个包」「权限不足」「空间不足」，直接给结论，不再只丢一个 exit code。

### 7.5 x86_64 测试套件（脚本拉取，不进仓库）

新增 `scripts/fetch-x86-testkit.sh` + `-Px86Rootfs=true` 构建开关：额外打进 x86_64 的 Alpine rootfs 与 Termux 版 proot 三件套，让 x86_64 模拟器能把容器页走通。产物在 `app/src/debugX86/assets/`，已 gitignore；CI 与正式包不受影响。

### 7.6 结论：模拟器上容器**仍然跑不起来**

套件齐全后，容器页能正常列出两个发行版、能解压 rootfs，但启动容器报 `proot 执行失败`。

手动复现（adb root，把 proot 与 rootfs 搬到 `/data/local/tmp`）：

```
proot --version            → 正常输出 5.1.107.100
proot -r <rootfs> /bin/busybox echo HI
  → proot error: execve("/bin/busybox"): No such file or directory
```

rootfs 内 `/bin/busybox`（808KB，0755）、`/lib/ld-musl-x86_64.so.1`（649KB）都在，`/bin/sh -> /bin/busybox` 也正常。加 `-b /dev -b /proc -b /sys`、改 `TMPDIR` 都不解决。

**不是包名/权限问题，是 Termux 构建的 proot 在 x86_64 模拟器内核上无法完成 guest 进程的 execve。** 这条在模拟器上就是走不通，别再花时间——容器内真实执行只能在 arm64 真机验。

### 7.7 真机视频暴露的真因：JNI 里 `snprintf` 返回值当 `write` 长度

真机录屏里容器一起来就断，终端只有两行：

```
FORTIFY: write: prevented 74-byte read from 64-byte
[连接已断开，退出码 134]
```

134 = 128 + 6，SIGABRT。一开始怀疑是 proot 的构建问题（Termux 版开了 FORTIFY），
甚至去试了自建 proot。实际根因在**我们自己的 JNI**：

```cpp
char buf[64];
const int len = snprintf(buf, sizeof(buf), "execve(%s) failed errno=%d\n",
                         cmdStr.c_str(), e);
write(STDERR_FILENO, buf, static_cast<size_t>(len));   // ← len 是"想写多少"，不是"写了多少"
```

`snprintf` 返回的是**如果缓冲区够大一共会写多少字节**。proot 的完整命令行（rootfs 路径 +
一堆 `-b` 绑定）轻松超过 64 字节，`len` 变成 74，`write` 就要从 64 字节的栈缓冲里读 74 字节，
bionic 的 FORTIFY 当场 abort。

危害远不止一行日志：**它发生在 exec 失败的处理路径上**，把真正的 errno 连同一个子进程一起干掉。
于是所有"容器起不来"的现象都长这样，排查方向被带偏到 proot / rootfs / SELinux 上。

修复：缓冲区提到 256，并且统一截断到实际容量再写（`writeErrnoMessage`）。
4 处（`chdir` / `execve` / 第二组 `chdir` / `execvp`）全部改掉。

语法检查已过（NDK clang `-fsyntax-only`）。**实际效果要在真机重新构建后看**——
这次终于能看到 proot 真正返回的 errno 了。

### 7.8 另一个真机问题：设置页/容器页文字上下重叠

**真因（2026-10-24 第二段录屏确认）：设备开了系统的「拼音标注」。**

第二段录像里每个汉字上方都有拼音（跟随系统、动态取色、回答完成提醒…），
汉字被顶起来，和上一行/下一行挤在一起。终端页是英文等宽，所以完全正常——
这也解释了为什么只有中文界面叠字。

这不是 App 能可靠适配的：拼音是系统在排版层给中文附加的注音，行高需求是动态的，
而本项目的排版规范用**固定绝对 lineHeight**（bodyLarge 15/26 等）。拼音一进来就不够用。

处置：
- 代码侧把 `includeFontPadding` 恢复为系统默认（原来全局关掉）。这**不是解药**，
  只是让字体度量回归系统计算，少一点人为压缩。
- 真正的解药是关掉拼音标注：设置 → 显示/无障碍 → 关掉「拼音标注 / 汉字注音」。
- 如果关掉后仍叠字，再回来查——那时才是 App 的排版问题。

（上一版文档把这条归因于 `includeFontPadding`，是错的，已更正。）

## 十、首启漏斗：对话页「准备清单」

### 问题

配模型之前有引导弹窗，配完之后就没人管了。剩下的三件事散落在三个地方：

- 无障碍 → 权限引导页
- 通知 → 系统设置
- 使用情况 → 系统设置
- 容器 → 设置页里的第三层

用户配完模型会以为「完事了」，过几天发现「它不能操作我的手机」，再回来找入口已经忘了路径。
这不是功能缺失，是**引导断档**。

### 做法

对话页顶部一条折叠态卡片：`还差 N 项，就能全自动`。点开列出未完成项，每项一行、
带一句「它能帮你干什么」，点一下直达对应系统页面；四项都就绪后卡片自己消失。

状态来源复用现有链路：`vm.serviceConnected` / `notificationGranted` / `usageGranted`，
容器状态用 `RootfsManager.isExtracted` 在 IO 线程读一次（已解压就不列这项）。

### 刻意不做的

- **不拦路**：不配也能聊天，卡片可折叠、可无视。拦路是首启漏斗最大的杀手。
- **不弹窗**：弹窗打断正在做的事，卡片贴在顶部不抢焦点。
- **不用百分比**：4 项里差 1 项不代表「75% 可用」，每项是独立增强，说「还差 3 项」更诚实。
- **不放在消息列表里**：一开始插在 `LazyColumn` 的第一个 item，结果空会话走的是另一个
  空态分支，卡片根本不显示。现在放在两个分支之外，空会话和有对话都看得到。

### 验证

模拟器（720×1280 / Android 11）：

- 空会话顶部出现「还差 4 项，就能全自动」
- 展开后列出无障碍 / 通知 / 使用情况（容器已解压，自动从 4 项变 3 项）
- 点「无障碍服务」跳到系统无障碍设置页，无崩溃
- 冒烟脚本加了两条断言，整体 **9/9 通过**

## 十一、长任务存活：补 WakeLock

### 问题

有前台服务 + START_STICKY，但**没有 WakeLock**。

前台服务只保证「进程有通知、不被随手回收」，**不保证 CPU 不睡**。锁屏后 CPU 进入 suspend，
流式响应和容器命令会被挂起，用户看到的是「任务卡住不动」，醒来后可能已经超时。

### 改动

`AgentRunService.onCreate` 拿一把 `PARTIAL_WAKE_LOCK`，`onDestroy` 释放：

- 上限 15 分钟（`acquire(timeout)`）：覆盖绝大多数 Agent 任务；任务卡死时超时自动回收，不耗干电池
- `setReferenceCounted(false)`：只释放一次，避免计数错乱
- 获取失败只记日志、不抛：最坏情况是锁屏后变慢，不是任务失败
- Manifest 里 `WAKE_LOCK` 权限本来就有（第 39 行），无需新增

### 验证

这条**只能在真机验**：模拟器没有厂商省电策略、没有真实 Doze，锁屏行为也不一样。

新增 `scripts/qa/device-survival.sh`：

```bash
ADB=adb bash scripts/qa/device-survival.sh 120
```

先在 App 里发起一个长任务，看到常驻通知后跑脚本。它会：
锁屏 → 等 120s → 比对 pid 与前台服务 → 检查电池优化白名单。

判据是「pid 没变、服务还在、在白名单里」；被重启/被杀会明确区分开
（pid 变了 = 被系统重建，pid 没了 = 被杀）。

脚本还会提示两条它测不了、需要人眼看的：通知栏步骤号有没有继续涨、回 App 看任务状态。
