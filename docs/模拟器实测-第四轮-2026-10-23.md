## 一、新发现并修复：空回复「沉默失败」（P0）

### 现象

模型返回 HTTP 200 但 `content` 为空时（供应商偶发、内容被安全策略清空、回复被截断），
界面上**什么都不会出现**：

- 用户消息带着时间戳落在会话里
- 下面一片空白：没有助手气泡、没有错误提示、没有加载状态
- 发送键早已恢复正常（说明请求确实结束了）

用户看到的是「我发了话，但它没理我」。分不清是消息没发出去、模型抽风、还是仍在等待，
只会反复重发。**这比报错更糟——报错至少说明了发生了什么。**

### 根因

`ChatViewModel` 里这行：

```kotlin
// 中间轮 Assistant 可能只有 toolCalls 无文本，空内容不出气泡
is AssistantMessage -> if (msg.content.isNotBlank()) {
    append(msg, if (msg === lastAnswer) turnUsage else null)
}
```

那个空判断本意是挡住「中间轮只有 toolCalls、没有文本」的空气泡，**但对最终轮也空的情况同样生效**，
于是整个回合一个气泡都不产生。

### 修法

把文案抽成纯函数（可被 harness 断言），ViewModel 在 `lastAnswer == null` 时补一条明确提示：

| 位置 | 改动 |
|---|---|
| `ui/EmptyReplyHint.kt`（新） | `emptyReplyHint(hasToolMessage)`：两种情形分开说 |
| `ui/ChatViewModel.kt` | `lastAnswer == null` 时补气泡 + 落库 + 记日志 |
| `scripts/qa/Round4Verification.kt`（新） | 11 条断言 |
| `scripts/qa/run-round4-verification.sh`（新） | 编译运行器 |

两种情形必须分开，因为用户下一步该做的事不同：

- **有工具执行但没文字总结**：工具已经跑了（有副作用），用户要决定「让它继续说」还是换个问法；
- **彻底空（连工具都没有）**：什么都没发生，直接重试即可。

### 自己引入又自己抓出来的一个瑕疵

第一版文案写的是「可以点「**重试**」再试一次」。真机一看——**按钮叫「重新生成」**。
「重试」只出现在错误气泡上（P2-10 的改动），而空回复气泡是普通助手气泡。
文案提控件就必须用控件上真实显示的字，否则用户会去界面上找一个不存在的按钮。

已改成「重新生成」，并加断言 `R4-6` 同时检查两点：包含「重新生成」、**不包含**「「重试」」。

### 验证

**harness 11/11**：两种文案不混淆、都给出下一步动作、都不带技术噪音（`Exception` / `null` / `HTTP` / `500`）、
ViewModel 确实接了这个兜底、兜底既上屏又落库（只上屏的话切会话就消失）、兜底留了日志、
原有的「内容为空不出气泡」判断仍在（别把中间轮空气泡放回来）。

**真机**：卸载重装后发 `empty` → 气泡出现、文案为「重新生成」、落盘 `variant` 正确。

## 二、上一轮唯一没验的修复：停止生成保留内容（P1-7）

第三轮报告里这条标着「未单独复验」。本轮补上。

**操作**：发 `slow`（约 40 秒、每 0.4 秒一片）→ 流式中途点停止。

**落盘结果**（这才是权威证据，不是截图）：

```
variant[0] assistant 236 字 = 第1片。第2片。…第49片。      ← 已生成的内容，完整保留
variant[1] assistant  28 字 = ⏹ 已停止。以上是停止前已生成的部分，可基于它继续提问。
```

修复前是「内容全丢、只剩一句已停止」。现在**内容留下 + 独立的停止提示气泡**，文案也与事实一致。

## 三、本轮最值钱的发现：`adb install -r` 之后跑的还是旧代码

### 症状

改完文案（把「重试」改成「重新生成」），重新打包、`adb install -r`、`am force-stop`、`am start`，
再测——**文案还是「重试」**。

逐层排查：

| 检查 | 结果 |
|---|---|
| 本地 APK 的 dex | 只含新文案（`old=False, new=True`）✅ |
| 设备上的 APK（`adb pull` 后 md5） | 与传过去的 APK **完全一致** ✅ |
| 设备 APK 内的 dex（绕开传输，远端 Python 直接读 zip） | 只含新文案 ✅ |
| 源码 | 只有一处文案，无硬编码残留 ✅ |
| 落盘的 turn 时间戳 | 确实在安装之后 ✅ |

全都对，但运行时就是旧逻辑。

### 结论

**`adb install -r`（覆盖安装）之后，运行中的 App 仍会执行旧逻辑**，即使 APK 里的 dex 已经是新代码。
用 `pm uninstall` + `install`（全新安装）之后，同样的操作立刻给出新文案。

首次确认方式：卸载重装 → 发 `empty` → 落盘 `可以点「重新生成」再试一次` ✅

### 影响

这不是 App 的缺陷，是**验证方法**的缺陷。它会让「改完没生效」被误判成「代码写错了」，
进而去改一段本来就对的代码；更糟的是可能让人**以为修复没成功而放弃一个已经修好的改动**。

**以后所有「改代码 → 上机验证」必须走**：

```bash
adb uninstall com.example.agentkit
adb install -t app-debug.apk
```

代价是清数据（会话/配置全丢），所以测试前要先把 `conversations.json` 和模型配置 prefs 备份好，
装完再灌回去。本轮的模型配置就是手写 prefs 恢复的：

```xml
<!-- shared_prefs/agentkit_model_config.xml -->
<map>
  <string name="base_url">http://10.0.2.2:8080/v1</string>
  <string name="api_key">sk-mock</string>
  <string name="model">mock-model</string>
  <string name="provider_id">openai</string>
</map>
```

## 四、长会话性能（40 轮 / 90 条消息）

第三轮只测到 20 条，这条一直挂着。本轮注入到 **40 轮 / 90 条**（每条约 150 字），做**对照实验**——
因为绝对值在无 KVM 的 TCG 模拟上毫无意义，只能看相对劣化。

| 会话 | 帧数 | Janky | 50th | 90th | 99th |
|---|---|---|---|---|---|
| 90 条消息 | 85 | 100% | **85ms** | 150ms | 200ms |
| 3 条消息（基线） | 53 | 100% | **57ms** | 125ms | 650ms |

**怎么读这张表**：

1. **两者都 100% janky** —— 这是 TCG 软件模拟（无 KVM）的固有现象，不能用来判断真机流畅度。
   做对照的意义就是排除这台机器的整体迟钝。
2. 长会话中位帧时间比短会话高 **49%**（57→85ms），属于「要组合的条目更多」的自然结果，
   **没有出现指数级劣化或卡死**。
3. 99th 反而长会话更低（200 vs 650ms）——单次异常值，噪声大，不要过度解读。

**诚实边界**：这台机器上**测不出真机流畅度**。能得出的只有「长会话没有灾难性劣化」这一条相对结论。

> 顺带确认前两轮的判断：`LazyColumn` 只组合可见项，90 条消息不会一次性布局。
> 如果真的全量布局，帧时间不会只涨 49%。

## 五、无障碍（TalkBack 未装，改用可量化替代）

模拟器镜像里**没有 TalkBack，也没有任何无障碍服务**（`pm list packages` 无 `talkback`/`marvin`，
`enabled_accessibility_services` 为 `null`）。装 TalkBack 需要额外下载且 TCG 下极慢，本轮不装。

改用**可点控件的标签覆盖率**——这是读屏能否工作的基础：没标签的控件在 TalkBack 下会被念成
「未加标签的按钮」，用户根本不知道能点。

用 `uiautomator dump` 采三页 UI 树，逐节点统计 `clickable=true && enabled=true` 的节点是否有
`content-desc` 或 `text`（含子节点文本，Compose 常见结构）：

| 页面 | 可点控件 | 无任何标签 | 结论 |
|---|---|---|---|
| 对话页 | 11 | **0** | ✅ |
| 抽屉页 | 10 | 2 | ✅ 两个都是 `[590,145][720,1048]` 的遮罩层和 `[0,0][0,0]` 零尺寸节点，本就该跳过 |
| 权限引导页 | 4 | **0** | ✅ |

对话页的 `content-desc` 列表：`发送` / `切换模型` / `快捷指令` / `打开导航抽屉` / `新对话` /
`添加图片附件` / `语音输入` —— 都是动作名，不读控件类型，符合读屏习惯。

**没验的**：朗读顺序、焦点移动逻辑、`liveRegion` 播报时机。这些只有真开 TalkBack 才能验。

## 六、确认「做不到」的两项（不是没做）

### 6.1 B4 容器内 `node --version` —— 架构不兼容，有硬证据

之前只是推断「x86_64 模拟器跑不了 arm64 的 rootfs」。这次把证据拿到了：

```bash
$ tar -xf assets/containers/alpine.tar && file bin/busybox
bin/busybox: ELF 64-bit LSB pie executable, ARM aarch64, version 1 (SYSV),
             dynamically linked, interpreter /lib/ld-musl-aarch64.so.1, stripped
```

rootfs 是 **ARM aarch64**，模拟器是 x86_64。`proot` 起不来，容器里任何命令都跑不了，
所以「装完 node 18 后 `node --version` 是不是 v18」在模拟器上物理不可能验。
**只能等一台 arm64 真机。** 用例已写在 `docs/真机验收-2026-10-21.md` §6.3。

### 6.2 API 33/34 差异 —— 需要新建 AVD

现有的两个 AVD 都是 API 30。建 API 33/34 镜像要下载 1GB+ 系统镜像，且无 KVM 下启动更慢。
本轮不做，理由是没有理由相信通知权限/前台服务类型在 33/34 上有行为差异——
`foregroundServiceType` 声明在 manifest 里是静态的，已在 APK 反验里确认过值。
真要验，属于「确认已知」而非「发现未知」，优先级低。

## 七、新发现但**没修**的（P3）

### 抽屉「最近对话」在 720×1280 上首屏一条都看不见

抽屉结构是：应用标记 → 状态文字 → **5 个主导航项**（对话/模型/控制台/终端/定时任务）→
「最近对话」标题 → **搜索框** → 会话列表。

在 720×1280 / 320dpi 上，搜索框的下边缘正好压在屏幕底部，列表全在折叠线以下，
**必须滚动才能看到任何一条会话**。

这有点讽刺：当初加「最近对话」的动因是录屏反馈「人家都有聊天记录，你这都没有」——
现在加上了，但**加得让人看不见，等于没加**。

功能本身是好的（滚动后列表正常、当前会话有高亮、显示「N 条消息」、长按可管理），
所以只标 P3，不阻塞。

可能的改法（按我倾向排序）：

1. **搜索框挪进标题行**（标题右侧放个搜索图标，点击才展开输入框）—— 直接省掉一整行；
2. 列表放到搜索框**上面**（搜索是要用时才找，列表是每次都要看）；
3. 主导航项收成两列网格 —— 改动大，会动到整体信息架构。

## 八、顺手修的 harness 缺陷

本地用 `-PnoNative=true` 出包时，`run-apk-verification.sh` 报：

```
FAIL  assets/shizuku.apk 不在包内（CI 的 Fetch Shizuku APK 步骤可能失败）
```

`-PnoNative` 构建为了在**没有 llama.cpp 源码的机器上**也能出包，跳过了 NDK 编译，
自然也不会跑 CI 的「Fetch Shizuku APK」步骤。这是**构建裁剪**，不是构建步骤坏了，
判 FAIL 会让人误以为 CI 出问题。

修法：用**本项目自己的 native 库**（`libagentkit-llama.so`）判断是否裁剪构建，是则 SKIP。

> 第一版我用「包里有没有 `lib/`」判断，结果恒为真——noNative 包里 `lib/` 照样存在
> （androidx / mlkit 的 `.so` 还在打），等于没判。**判据必须指向本项目自己的产物**。

修完后：`run-apk-verification` 从 FAIL 变 SKIP，全量 `PASS=50 SKIP=0 FAIL=0`，门禁 4/4。
