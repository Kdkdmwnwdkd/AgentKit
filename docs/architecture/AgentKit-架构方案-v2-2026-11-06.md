## 0. 一页速览

### 0.1 三句话判断

**第一，骨架是对的，而且比文档写的更值钱。** 四条真实分界线（界面 / 回合编排 / 能力接入 / 系统执行）成立：
`RealAgentLoop` 零 `ui/` import，只认 `ToolRegistry` 的 descriptor；`TerminalSessionPool` 不认识 Agent，只认 `TerminalBackend`。
56 个工具能按组动态加权、四个执行后端能沿一条降级链回退、三家模型协议收敛到 `chatOnce` —— 这三件事在同类项目里通常做不成。

**第二，真正的系统性缺陷只有一个：同一份事实有多个真源。** 六条线独立扫描，最后都撞到同一堵墙：

| 事实 | 真源数量 | 分裂形态 |
|---|---|---|
| 「这个供应商是不是本地」 | 4 处 | `id.startsWith("local-")` / `providerId == "local-llama"` / `style` / 目录 `group=LOCAL` |
| 「这个工具要不要审批」 | 2 处 | 工具类 `needsApprovalFor` vs `ToolCatalog.approval`；5 条声明永远不会生效 |
| 「这条记录属于哪个会话」 | 0 处 | 附件、审批白名单、挂起卡片都没有 `convId` |
| 「刚才发生了什么事件」 | 3 套 | `RunEvent`(6) / `TurnEvent`(8) / `AgentEvent`(5)，同一动作三种说法 |
| 「容器命令怎么执行」 | 3 条 | 交互终端 / 会话池 / 一次性 runner，锁与超时语义各自演化 |
| 「这次失败卡在哪一步」 | 4 种答案 | 池层、一次性通道、容器 runner、日志，互不相交 |
| 「会话库的真相」 | 2 份 | index 与分片只有写序，没有一致性对账 |

**第三，顺序必须改。** v1.0 的「先补余量 → 再拆结构 → 后做能力」方向对，但漏了一个前置条件：
**守卫体系本身已经不可信**（实测：42/112 个 harness 全部 SKIP、70 个 PASS，`gate.sh` 仍判 `GATE PASS`）。
在这种守卫下拆 `ChatViewModel`，会把 626 条押在单文件上的文本断言换成「存在性检查」——**红会消失，判别力也一起消失**。
所以 v2.0 的顺序是：**先修事实（P0）→ 再修守卫（P1）→ 然后才拆（P2）→ 最后做能力（P3）**。

## 1. 约束与事实基线

架构必须先服从约束。下面这些是从构建脚本、Manifest 和依赖清单读出来的**硬约束**，不是偏好：

| 约束 | 事实依据 | 对架构的强制影响 |
|---|---|---|
| 单 APK、单进程、无 root | `AndroidManifest.xml`，无多进程声明 | 后台能力只能靠前台服务 / 无障碍 / Shizuku 借权 |
| `targetSdk = 28` | `app/build.gradle.kts:43` | 为在 `filesDir` 内 `execve`（proot 必需）；代价是放弃 29+ 的存储与通知新约束 |
| 仅 `arm64-v8a` | `app/build.gradle.kts:50-53` | 本地推理无法在常规模拟器回归，只能真机验 |
| 无 GMS、离线可用 | 依赖清单无 play-services；OCR 用打包模型的 mlkit | 基础能力不得依赖云侧 SDK |
| 本地 `n_ctx` 极小且四处真源 | `ContextBudget.kt:53/85`、`LocalLlamaSetting.kt:26/152`、`LocalLlamaClient.kt:134` | 云端/本地不能共用一套预算参数 |
| **依赖不是零** | `app/build.gradle.kts`：17 条 `implementation`，含 okhttp 4.12 / rhino 1.7.14 / mlkit-chinese / shizuku×2 / WorkManager | 见 §1.2 |
| 发行物是 debug 签名包 | `app/build.gradle.kts:60`，`build.yml:285` 直推 `latest` | 正式分发前必须补 release 签名与版本策略 |

### 1.2 「零第三方依赖」的纪律改写

`README.md` 写「零第三方新增依赖」，实际有 8 个能力性库（okhttp / rhino / mlkit / shizuku×2 / work / compose-bom / serialization）。
这不是道德问题，是**表述失真带来的判断风险**：接手的人会以为「加库不可能」，于是把该用库解决的事手写成两千行自有实现。
建议改成可执行版本：

> **新增依赖必须在 `docs/DEPENDENCIES.md` 登记用途、体积、许可证、退出成本；
> 能用 200 行以内自有实现替代且无正确性风险的，不引依赖。**

### 2.2 边界审计：哪两处成立，哪三处不成立

**成立（应沿用，不要绕开重造）**

| 接缝 | 证据 | 为什么值钱 |
|---|---|---|
| `RealAgentLoop` ↔ `ToolRegistry` descriptor | `RealAgentLoop.kt:1-40` 零 `ui/` import；工具只以 descriptor 出现 | 引擎不认识任何具体工具，加工具不动引擎 |
| `TerminalSessionPool` ↔ `TerminalBackend` | `TerminalSessionPool.kt` 只认接口；四个后端实现各自独立 | 执行后端可替换，池不感知 proot/adb/shizuku |

**不成立**

| 断点 | 事实 | 后果 |
|---|---|---|
| L0 不依赖 L3 | `core/ConfigStore.kt` → `skill.ModelConfig`；`core/CapabilityAuditReporter.kt` → `skill.CapabilityRegistry`；`core/job/CompletionNotifier.kt` → `AgentKitApplication` | core 无法独立编译，模块化第一道墙 |
| 同一能力只有一个实现 | `terminal/TerminalEmulator` 与 `core/terminal/*` 双份；容器有 3 条执行路径 | 语义各自演化，修一处漏两处 |
| L1 只依赖单向 | 类型已经单向（17 处契约），但运行时同一个 VM 实例被 17 个屏幕共享，屏幕各读各的流 | 组装根收的是「类型」，不是「依赖」 |

### 2.3 目标分层规则（写进守卫，不写进文档）

| 规则 | 表述 | 检查方式 |
|---|---|---|
| D1 | `L1 → L0/L2/L3/L4` 允许；反向禁止（现有 3 条豁免只减不增） | import 扫描，扩展到全部包 |
| D2 | `L0` 只能依赖 `L0` 与 JDK/Android 框架 | 同上 |
| D3 | 同一能力只有一个包拥有实现（先收 `terminal` 双份） | 目录级白名单 |
| D4 | 单文件 ≤1500 行适用**全仓**，不只是 5 个文件 | `wc -l` 全量 + 每包行数总量预算 |
| D5 | 新增 `layer`/`lines` 豁免必须同 commit 带 `ARCH-EXEMPT: <理由>`，否则红 | `git diff` 取新增行 |
| D6 | 新增断言一律行为化；文本断言总量只减不增 | `assertion-census.py` 的 `__TOTAL__` 单调下降 |
| D7 | 每个「事实」只允许一个源，其余必须是派生视图 | 结构对账（见 §11 不变量表） |
| D8 | 任何跨会话状态必须带 `convId`，任何在飞结果必须带 `turnId` | 类型签名扫描 |

### 2.4 横切三件套（v2 新增）

现在横切逻辑散在六处，每处各写一遍。目标收成三件：

1. **`CapabilityCatalog`**（`core/tool/ToolCatalog` 扩权）——工具/组/能力/审批/顺序的唯一真源，闸门直接读它。
2. **`TurnEvent` 作为唯一事实**——`RunEvent` 并入，`AgentEvent` 降级为对 UI 的投影（带 `turnId + scope + convId`）。
3. **`Diagnostics` 统一口径**——失败回执统一 `{backend, stage, code, errno}`，日志/诊断包/工具回执三处同源。

## 4. 关键运行链路

### 4.1 一轮对话（成立，不要动）

```
send() → runTurn(turnId, scope)
  ├─ 装配：SystemMessage(FROZEN/SESSION/TURN) + priorMessages + UserMessage
  │        └─ 系统提示每回合只拼一次，保 KV 前缀（本地推理刚需）
  ├─ 每步重算暴露面 KernelExposure.plan()（seed file → 强制 pin → 滞回淘汰）
  ├─ buildRequestMessages：pruneImages(保最近 2 张) → fitToBudget(按完整步整组丢)
  ├─ chatOnce → streamChat → TextDelta/ReasoningDelta 只进回调，Completed 整条入历史
  ├─ finish_reason 归一（length/stop/其它）
  ├─ executeBatch：含写整批串行；全只读 chunked(5) 并行且保序
  └─ 取消：ensureActive 每步检查；NonCancellable 内 closePending 补配对
```

三处设计质量高于项目其他部分，**方案里不要改**：三段式系统提示保缓存、按「完整步」裁剪而非按消息裁剪、只读并行但保序。

### 4.2 工具调用七道闸（成立，补两处）

```
模型 tool_call
 → scopedRegistry.descriptor（只认本回合可见）
 → ① 未启用 → tool_not_enabled（并指出该开哪个组）
 → ② 失败熔断 → 短路
 → ③ 参数级审批 → needsApprovalFor（当前只读工具类，不读目录 ← 补 B-4）
 → ④ 副作用登记 → DISP 落盘，写不进则拒写
 → ⑤ 执行（90s 只读 / 600s 写，无批级上限 ← 补 A-2）
 → ⑥ truncateToolResult（预算 1.2×，下限 1000 字符）
 → ⑦ ToolMessage 回灌 + 图片单独回灌
```

两处要补：**③ 的判据改为 `needsApprovalFor(args) || catalog.approvalOf(name) != null`**；
**⑦ 之后补「结果槽」**——每个调用完成即写入 `MutableMap<callId, ToolMessage>`，取消时从这里取真实结果，而不是按 `readOnly` 猜。

### 4.3 取消与恢复（v1.0 结论在这里被证伪一半）

现状事实（✔）：

- 批内结果要等**整批结束**才 `messages.addAll(results)`（`RealAgentLoop.kt:790-797`）；
- 中途取消时 `closePending` 只看 `messages` 里有没有 ToolMessage（`:925-946`），无法知道某调用其实已成功；
- 已成功的 `ToolFinished` 已先落 store，随后被同一 `call.id` 的改判事件 upsert 覆盖（`ChatViewModel.kt:2028-2039`）；
- 取消时 `send()` 抛异常、完整 history 不返回（`ChatViewModel.kt:2901-2916`），只抢救流式正文。

**目标语义（写进契约）**：取消后每个 `callId` 恰好一条终态，且三类可区分——
`ok`（真实结果保留）/ `cancelled_unknown`（已派发、结果未知）/ `not_dispatched`（从未派发）。
判据：3 个串行写替身，第 2 个执行中取消 → #1 真实成功、#2 unknown、#3 not_dispatched，store 中无「成功卡被改写」。

### 4.4 执行后端选择（骨架对，四处实现缺陷）

链条唯一：`proot → shizuku → adb → user`（`preferProot=false` 为 `shizuku → adb → user`，顺序表外的后端追加末尾）。
`R-12` 的身份维度是真的：`TerminalIdentity` 带 `uid` 与 `satisfies()`，「请求是下限、后端声明是实际」贯穿工厂筛选、会话复用、执行校验三处 ✔。

五条通道的实际能力边界（✔ 代码 / ○ 运行时）：

| 通道 | 实际 uid | 能做 | 不能做 |
|---|---|---|---|
| 无障碍 | App uid | 读 UI 树、手势、`ACTION_SET_TEXT`、截图 | 起 shell、跨应用私有目录 |
| Shizuku | 2000 | 持久 `sh`、`pm`/`am`/`input` | 写 `/system`、真 root |
| 无线 ADB | 2000 | 同 shell，`shell,v2` 分流出退出码 | Android 11 无法配对（`SDK>=31`） |
| proot | App uid（`--root-id` 是 guest 内假 0） | 完整用户态、apk/apt | 真提权、跨应用私有目录 |
| 本机 sh | App uid | toybox、自身 `filesDir` | 任何特权操作 |

**今天真正高于 App 的只有 uid 2000 一档，且有两个独立入口**——「无 root」这个前提在实现上自洽，不存在第五条偷偷提权的路。

四处缺陷：同别名并发 `open`（A-4）、30s vs 20min（A-5）、死会话识别（A-6）、租约双闸互斥（P2 收口）。

### 4.5 落盘与恢复

```
persist: 写脏分片（tmp→fsync→.bak→rename）→ 写 index（同流程）
load   : index + .bak → 逐分片 readShard → mapNotNull（缺则静默丢）
重建   : 仅当 index 与 .bak 全坏时，扫目录用文件名当 id
```

缺的是**跨文件不变量**：index 里没登记的分片永不收编；index 有 id 而分片读不出时静默跳过；`writeShard` 返回 0 被忽略。
目标：加载后做一次对账（`index.ids` vs 目录差集），多出的收编、缺失的 WARN 并从 `.bak` 再试；写 index 前校验本次 `dirty∪removed` 全部落盘成功。

| 契约 | 现状 | 要补的约束 |
|---|---|---|
| `AgentTool` | `{name, description, parameters, readOnly, needsApprovalFor}`，组/能力/审批在 `ToolCatalog` | 审批改为「目录优先」，工具类只做参数细分 |

> **一条贯穿全项目的设计原则**：凡是「用字符串承载枚举语义」的地方都出过事——
> `style` 拼错静默回落、`client.id` 协议/供应商混用、回执码散字符串、后端名重复两份、
> `container_toolchain.action` 的错误提示少一个合法取值。
> 不需要引入密封类体系，只要**把字符串常量收进 `object` 并让 harness 断言穷尽性**。

## 9. 演进路线

### 9.1 排序原则（为什么不是「先拆」）

```
P0 修事实   ── 现在有 15 个 A 级事实错误，每一个都在污染数据或授权语义
   ↓
P1 修守卫   ── 守卫不可信时，任何重构都无法证明「没变坏」
   ↓
P2 拆结构   ── 此时拆分才有客观判据，才敢一次一步
   ↓
P3 做能力   ── 新能力必须落在已经收口的结构上
```

反例：v1.0 的 P1 说「抽 `TurnRequestAssembler` 减 150 行」，六个月后进度仍是 0——

所以 P1 的第一交付物不是「拆出来的文件」，是「拆了也不会假红的守卫」。

## 10. 质量体系：本项目最独特的一块，也是最脆的一块

### 10.1 实测现状

| 项 | 数值 |
|---|---|
| runner | 112 个执行体（92 真编译 + 7 Python 对账 + 11 bash 扫描 + 2 门禁自测） |
| 文本断言 | 1,368 条 / 53 文件；其中 626 条（45.8%）在 `Hotfix11Verification.kt` 一个文件 |
| 行为断言 | 存在且质量不错（真写盘计数、100 线程并发），但占比约 4 成 |
| 编译闭包 | 49 个 runner 显式列 ≥3 个 `.kt`；全仓点名 293 个唯一文件（97%） |
| 架构守卫 | 只扫 `core/`，5 条断言；基线 3 layer + 5 lines |
| 变异 | 3 个手动 `mutate.py`，无 workflow 调用 |
| 门禁 | `GATE OK 6/6` 在「42 SKIP + 70 PASS」下仍 PASS |

### 10.2 失效机制：不是行数，是 fan-in

设文件 `f` 的接触面 `F(f) = runner 点名数 + harness 引用数`。
拆分 `f` 的收益 ≈ 减少的行数（150–420）；成本 ≈ `F(f)` 次编译清单修补 + 锚定断言重写。

- `ChatViewModel`：`F ≈ 8（runner）+ 8（harness）+ 18（readSource 点）≈ 34`；按五步拆，约 170 个接触点。
- `ChatScreen`：`F ≈ 22`。
- 临界判断：**当 `F > 20` 时，一次拆分的验证修补量已超过被拆代码本身**；当前已有 2 个文件过线。

真正的失效不是「红」，而是**绿得没有意义**：把 `readSource("ui/ChatViewModel.kt")` 改成全树 grep 后，
那段文字出现在仓库任何地方都算过——600 条断言从「结构约束」退化为「存在性检查」。

### 10.3 迁移五步

1. 先修门禁（Q-1/Q-2），让「暗着的 harness」不再合法。
2. 再修编译闭包（Q-3），让拆分不再炸 49 个 runner。
3. 拆最大的断言文件（Q-5），把 626 条压到 ≤300，每条替换必须附一次变异记录。
4. 上变异 workflow（Q-6），证明判据有判别力。
5. 最后才拆产品代码（P2 第 3 步起），每步一个 commit、同步下调基线。
