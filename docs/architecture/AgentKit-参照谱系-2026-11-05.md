## 0. 一句话

六家参照各贡献了一块，拼起来正好是这个项目的形状：

| 来源 | 给的是 | 在 AgentKit 里的形状 |
|---|---|---|
| **RikkaHub** | 协议抽象的「薄」 | 3 个 Provider 类型而不是 30 个类；消息分支 = 节点 + 游标 |
| **Operit** | 工具权限的「严」 | 危险度分级 fail-closed + 参数级审批 + 失败必带 `hint` |
| **AiCode** | 执行环境的「全」 | 内置 rootfs + 检查点 + 精确编辑 + 双层写保护 |
| **Coomi** | 循环的「稳」 | 并发判据 = 本批是否含写；同指纹最多真跑 2 次 |
| **zafiro** | 分层的「净」 | 运行时不认识 Android；终端 = 身份 × 后端二维矩阵 |
| **IRIDIS** | 本地推理的「快」 | 按机型定线程/ctx 的档位表 + 前缀缓存复用 |
| **DeepSeek Harness** | 组合的「活」 | 作用域化的工具注册、系统提示分段装配、会话事件日志 |

一句话概括这个组合：**RikkaHub 教我们少写类，Operit 教我们多设闸，AiCode 教我们把环境装进去，
Coomi 教我们别让循环失控，zafiro 教我们把边界画直，IRIDIS 教我们榨干芯片，
DeepSeek Harness 教我们让每一块都能被替换。**

## 2. 借鉴 → 落点

只列**能在本仓库指出落点**的条目。指不出落点的，说明只是读过、没落地，不算借鉴。

| 机制 | 出处 | AgentKit 落点 | 我们的差异 / 反超 |
|---|---|---|---|
| 工具按组按需载入 | IRIDIS | `core/capability/CapabilityManifest`（15 组 56 工具）+ `KernelExposure` | 反超：加了**粘性**（开过就一直开）+ `__find_tools` 兜底 + token 预算门（默认面 525 token） |
| 机型档位表（按 SoC 定线程/ctx） | IRIDIS | 本地推理参数 | 未完全落地，见 §5 |
| 工具调用前后钩子严格配对 | RikkaHub | `ToolExecutor` 的 commit → result 不变式 | 反超：取消路径在 `NonCancellable` 内补配对 |
| 消息分支 = 节点 + 游标 | RikkaHub | `core/ConversationBranch.kt`（`TurnRecord.variants + selectedIndex`） | 一致 |
| 上下文滞回截断 + tool 配对保护 | RikkaHub / Coomi | `core/agent/ContextBudget.fitToBudget`（按完整步整组丢） | 差异：我们按「完整步」切，比按消息切更保守但不会切断工具配对 |
| Provider 无状态、配置快照 | RikkaHub | `LLMConfig` 无状态 + `ProviderManager.create` | **这里出了 bug**：`LLMConfig` 缺 `providerId`，见架构方案 R-01 |
| 3 个 Provider 类型而非 N 个类 | RikkaHub | `LLMClient` 接口 + 三实现 + `ProviderCatalog` 目录 | 反超：目录化后新增一家只需 1 文件 2 处 |
| 工具结果单条独立截断 | Operit / AiCode | `truncateToolResult` + `ContextBudget.toolResultLimitChars`（预算 1.2×，下限 1000） | 一致 |
| 权限分级 fail-closed | Operit | `SkillSecurity`（未知 = DANGEROUS，19 个显式高危） | 反超：未知默认危险，比白名单安全 |
| 「工具不存在」可纠正 | Operit | `tool_not_enabled` 回执，指出该开哪组 | 反超：区分「真没有」与「有但没开」 |
| 内置 rootfs + proot | AiCode | `core/container/` + `ProotBackend` | 差异：我们**不做**手机端 Gradle 构建，走云端 CI |
| 检查点快照 | AiCode | 未落地（路线图 Phase 3 §5「精确编辑 + 双层写保护」） | 缺口 |
| 精确编辑：字符串匹配而非行号 | AiCode | `edit_file` 工具 | 一致 |
| 并发判据 = 本批是否含写 | Coomi | `RealAgentLoop.executeBatch`（含写整批串行，全只读 `chunked(5)` 并行保序） | 一致，且补了「结果保序」 |
| 失败指纹 + 熔断（同调用最多 2 次） | Coomi | `FailureGuard` | 一致 |
| 400 字段自降级重试 | Coomi | 未落地 | 缺口，但与 R-09 同源（重试粒度） |
| 运行时抽成独立层，不认识 Android | zafiro | `core/` 不 import `ui`（3 条豁免） | 仅部分成立，见架构方案 §2.2 |
| 终端 = 身份 × 后端二维矩阵 | zafiro | `TerminalIdentity`（权限档，带 uid + `satisfies`）× `TerminalBackendFactory.providersFor`（通道序） | 二维齐了（R-12）。差异：我们让「请求身份」表达**下限**而非等值匹配，因此 uid 2000 的会话能被 user 请求复用 |
| 工具结果契约 `{ok,code,message,hint,data}` | zafiro | `core/ToolResult.kt`：五元组 + `parts` 承载图文多片段 | 功能等价。五元组覆盖「成败码、消息、建议、数据」四类回执语义，是为满足本项目 UI 分流与失败提示而定的命名 |
| 作用域化工具注册 | DeepSeek Harness | `KernelExposure.scopedRegistry` + `RunScope`（main / skill / sub） | 一致 |
| 系统提示分段装配 | DeepSeek Harness | `buildSystemPrompt` 的 FROZEN / SESSION / TURN 三段 | 反超：分段是为了**保 KV 前缀缓存**，这在手机上比在服务器上更值钱 |
| 会话事件append-only日志 | DeepSeek Harness | `core/agent/journal/TurnJournal` | 差异：我们只记「恢复所需」，不是完整事件流 |

## 3. DeepSeek Harness：结构同构，但不是移植

先说结论：**两边包结构几乎是同一张图**，但一个是 TypeScript/Node 的插件树，一个是 Kotlin 的单模块 APK，
物理上不可能有代码流动。这是「词汇层同构」，也正是净室重写最理想的结果——学的是分解方式，不是实现。

| deepseek-harness | AgentKit | 同 | 异 |
|---|---|---|---|
| `core/session`（append-only `SessionEvent`） | `core/agent/journal/TurnJournal` | 都是「事实先落盘，再谈恢复」 | dsh 是完整事件流可重放；我们只记恢复锚点 |
| `core/system-prompt`（section + tool-schema 装配） | `buildSystemPrompt` + `buildRequestMessages` | 分段装配 | 我们多一层「按 token 预算裁剪」，dsh 交给模型窗口 |
| `core/tools`（scoped registry + guarded pipeline） | `KernelExposure` + `ToolExecutor` | 作用域 + 守卫管道 | 我们多了分组粘性与 token 预算门 |
| `core/agent` + `core/agent-loop`（接口与驱动分离） | `AgentLoop` 接口 + `RealAgentLoop` | 接口/实现分离 | `AgentLoop.stop()` 曾是死接口，R-19 已删（生产只走 Job.cancel） |
| `core/scope`（per-agent 注册原语） | `AgentScope` + `RunScope` | 作用域传播 | 我们用协程上下文，不用 ThreadLocal |
| `llm/llm`（adapter seam） | `LLMClient` 接口 | 适配器缝 | 我们的 `id` 字段语义过载（R-01） |

**还有两件值得再借的**：

1. **事件三分**：dsh 把事件分 `session/*`（durable）、`agent/*`（in-flight）、`capability/*`（policy），
   三者用途不同、生命周期不同。AgentKit 现在是「一堆回调 lambda」，这正是 `ChatViewModel` 72 条
   StateFlow 收不住口的同源问题——事件没有分类，就只能都堆在一个地方。
2. **注册是可回卷的 effect**：dsh 的插件卸载会把注册**自动回卷**。对照我们的 `R-07`：
   `ToolRegistry.unregister` 全仓零调用，停用 MCP 服务器后工具还在、调用打到死连接。
   这不是「忘了调一个方法」，是**注册模型缺了回卷语义**。这条应该从 P0 bug 升级成 P1 结构项。

> **2026-11-06 补记：当时这里判断错了一半。**
> 「10 月开源的那个架构」不是 deepseek-harness，是 **`dsh-superagent-prototype`**（2026-10-31 创建，MIT，2 万★）。
> 它跑在 harness 之上，是一个「监听 GitHub/飞书 → 自己开工作项 → 开 worker 会话 → 提 PR」的 bundle。
> 两者是宿主与插件的关系，不是两个候选。DeepInfer 那条判断仍然成立（服务端推理框架，与手机端无关）。
>
> 补记带来的结论变化（详见 `docs/research/superagent-架构层与运行层-2026-11-06.md`）：
> 1. 本节「结构同构」的判断**成立且更强**——它的 Engine 有五部件（Intake/Evals/Tickets/Assignments/Replies），
>    与我们 `RealAgentLoop` 的职责划分是同一张图的两种画法；
> 2. 但它真正领先的不是分解方式，是 **「每个状态只有一个写者」写成了一张可核对的表**（`docs/007-architecture.md:259-271`）；
> 3. 文章里的 Router/Worker 双层在代码里只是两个提示词预设常量（`src/app/sessions.ts:48`），**不能当架构分层照搬**。

## 4. 设计坐标：同一个问题，各家怎么解，我们为什么这么选

| 问题 | 各家解法 | 我们的选择 | 理由 |
|---|---|---|---|
| 容器放哪 | Operit 拆第二个 App；AiCode / IRIDIS 塞进同一个 | **单 App + 内置 rootfs** | 双包的心智成本 > 包体积收益；用户明确要「一个 App」 |
| 怎么提权 | Operit / AiCode 引导装 Shizuku；Coomi 加 libsu | **先 Shizuku，再自研 ADB 配对** | 四家都没在 App 内实现无线配对，「不装第二个」是我们的差异化 |
| 工具给几个 | Operit 全量塞；IRIDIS 按组；zafiro 少而精 | **按组 + 粘性 + 预算门** | 56 工具全量 10,064 token，默认面压到 525 token（省 94%） |
| 上下文怎么裁 | RikkaHub 滞回阶梯；Coomi 按 token 估算 | **按「完整步」整组丢 + 钉首尾锚点** | 切断工具配对比丢内容更致命 |
| 循环边界 | Operit 无界互相递归；zafiro 有界 | **有界 maxSteps** | 无界递归在手机上等于烧电 + 卡死 |
| 本地推理 | IRIDIS 四引擎按机型选；zafiro 单 llama.cpp | **单 llama.cpp + 租约空闲卸载** | 多引擎是 4 倍的维护面，先把手上一件事做扎实 |
| 状态放哪 | RikkaHub DataStore 一切；zafiro 运行时库不碰 Android | **Store 分层 + owner 捕获** | 生成中切会话是手机特有的场景，必须显式建模 |

## 5. 明确不学的（反例清单）

判断力体现在这里——列出来，是为了下次不再重新评估一遍。

| 不学 | 出处 | 为什么 |
|---|---|---|
| 39 家 Provider 铺量、ToolPkg 包生态、蓝牙 16 工具、浏览器 18 工具 | Operit | 工具面的边际收益递减，token 成本线性上升 |
| 换栈（Java 壳 + Rust 引擎 + Vue 前端） | Coomi | 反例：换栈不解决入口拥挤，只是把复杂度搬了个地方 |
| 手机端跑 Gradle 编译 APK | AiCode | 慢且 OOM；我们走 GitHub CI |
| 14 个 Gradle 模块 + Room + Koin + Ktor | RikkaHub | 与「零新增依赖」直接冲突 |
| 四引擎全上（llama.cpp / MNN / LiteRT / GenieX） | IRIDIS | 维护面 ×4，我们连一个引擎的档位表都还没做完 |
| 虚拟屏 / `app_process` + 隐藏 API | Operit | 灰区，且与 targetSdk 28 的策略冲突 |
| 完整事件流可重放 | DeepSeek Harness | 手机上存储与功耗都不允许；只记恢复锚点 |

## 7. 谱系反过来修正了架构方案的三处

写完谱系再看架构方案，有三条判断需要调整：

| 原判断 | 修正 | 依据 |
|---|---|---|
| `R-07`（MCP 停用后工具残留）是 P0 小 bug | **升级为 P1 结构项**：注册模型缺回卷语义 | DeepSeek Harness 的注册是 effect，随插件卸载回卷；我们连 `unregister` 都没人调 |
| 本地推理只有 `LocalLlamaClient` 一个实现，无须抽象 | **P3 预留 `LocalEngine` 接口**（不加实现） | IRIDIS 证明「引擎可换」是真实需求（CPU/GPU/NPU 按机型选），现在不预留，将来换引擎要动 `LocalLlamaClient` 的调用方 |
| `ChatViewModel` 的 72 条流是「状态所有权未收口」 | 同源问题还有第二个解法：**事件三分** | `session/*` 持久事实、`agent/*` 在飞状态、`capability/*` 策略，三类事件的消费方天然不同，混在一起才需要 72 条流 |

## 附录 · 核对方法

```bash
# 许可证 / 星数 / 语言 / 是否改名（301 会跟随）
curl -sL -H "Authorization: token $TOKEN" https://api.github.com/repos/<owner>/<repo>

# 目录结构（判断「四引擎」这类说法是否成立）
curl -s -H "Authorization: token $TOKEN" \
  "https://api.github.com/repos/<owner>/<repo>/git/trees/main?recursive=1"
```

沙箱内 `github.com:443` 直连不通（单 IP 丢 SYN），`api.github.com` 可用；
`git clone` 会卡死，大仓库用 API tarball 或 `gh-proxy` 镜像。
