# 容器安装 exit 99：并发抢锁的根因与修复（2026-10-25）

> 真机反馈：Alpine「已就绪」后，点「安装 Node.js 20」，得到
> `安装失败（exit 99）：ERROR: Unable to lock database: temporary error (try again later) ERROR: Failed`。

## 1. 现场证据（17431.mp4 + 同批日志）

日志里 40 秒内出现了 **5 次** `ContainerNetwork: resolv.conf 已写入`：

```
14:00:03.931  resolv.conf 已写入   ← 终端会话（后面有 invocation 自检）
14:00:11.149  resolv.conf 已写入   ← 无任何后续日志
14:00:16.996  resolv.conf 已写入   ← 无
14:00:29.681  resolv.conf 已写入   ← 无
14:00:35.928  resolv.conf 已写入   ← 无
14:00:39.089  resolv.conf 已写入   ← 终端会话（自检通过）
```

`resolv.conf` 只在两处写：`ContainerSession.create()`（开交互终端）和
`ContainerCommandRunner.run()`（跑一次性命令）。也就是说，**中间四次是一次性命令**，
而旧版执行器**只在失败时打日志**，所以它们全程静默——从日志看不出有人在并发跑 `apk add`。

结合 `ContainerScreen` 的旧代码：

```kotlin
scope.launch(Dispatchers.IO) { runInstallInContainer(context, id, cmd) }
```

按钮没有运行态、不禁用、不做去重。点一下起一个 proot，连点五下就是五个 `apk` 同时跑。

## 2. 根因

apk 用 `/lib/apk/db/lock`（flock）做进程间互斥。第二个 apk 拿不到锁时立即退出，
退出码 **99**，报 `Unable to lock database: temporary error (try again later)`。

所以这不是：
- 网络问题（DNS 已确认可用，同一 rootfs 之前装成功过）；
- rootfs 损坏（卡片显示「已就绪」，`bin/sh` 校验通过）；
- 版本映射错误（3.20 → nodejs 20.x，映射本身是对的）。

**并发本身就是 bug。** 包管理器是单写者模型，容器里只该有一个 apk/apt 在跑。

## 3. 修了什么（四处）

| # | 位置 | 改动 | 解决什么 |
|---|------|------|----------|
| 1 | `ContainerCommandRunner` | 加进程级**公平锁** `execLock`，所有容器命令串行执行 | 两个 apk 不再可能同时跑 |
| 2 | `ContainerCommandRunner` | **同命令去重**：完全相同的命令在飞时直接返回 `EXIT_BUSY(-2)` | 连点十下不会攒出十个下载任务 |
| 3 | `ContainerCommandRunner` | 抢锁**原地重试**（2s / 5s），判据 `ToolchainInstaller.isLockConflict()` | 兜住「上一次安装被杀、锁还没释放」的窗口 |
| 4 | `ContainerScreen` | 加 `installing` 运行态：按钮禁用 + 文案「正在安装 …」；失败结果**内联常驻**（替代 `take(80)` 的 Toast） | 用户点下去立刻有反馈，不必等失败提示才反应 |
| 5 | `TerminalSession` | 主动 `destroy()` 时不再把 137 当退出码上报 | 去掉一条与真崩溃（LMK 杀进程）混淆的误报 |

### 为什么退出码用 -2 而不是复用 -1

`-1` 现在是「前置条件不满足」（proot 缺失、rootfs 未解压）——那是要用户去修环境的。
「同一条命令已在执行」只要等一会儿，语义完全不同。UI 上一个是红色报错，一个是
「等它结束再点」，混用会让用户以为容器坏了。

### 为什么锁判据放在 `ToolchainInstaller` 而不是执行器里

执行器带 `android.content.Context`，进不了 JVM harness；判据写错（比如只认 99、
不认 apt 的 `lock-frontend`）的后果是「重试逻辑静默失效」——这种 bug 只能靠真机
复现，而真机复现一次要好几分钟。放到纯逻辑层后，`scripts/qa/BatchBVerification.kt`
在 JVM 上就能断言，包含反例（网络失败**不能**被判成抢锁，否则会把 15 分钟耗在重试上）。

## 4. 验证

- 本地 `kotlinc` 编译 `ToolchainInstaller` + `ContainerCommandRunner`（Android 桩），
  编译通过；锁判据 6 条断言全通过（apk 99 / apk 文本 / apt 文本 / 网络反例 / 成功反例 / 包不存在反例）。
- `BatchBVerification` 新增 B4-12..B4-14 三条（判据正确性、串行闸门存在、UI 防重入）。
- CI：编译 + 全量 QA + 门禁。

## 5. 还没验证的（真机待确认）

1. **容器内终端提示符**：17431.mp4 末尾终端只有 `- $`，且会话 4 秒就被销毁（日志
   `终端会话已销毁` → `退出码=137`）。137 = 128+9 是**我们 kill 进程组**的结果，不是崩溃；
   但「进容器后多久出提示符」这次没有干净样本，需要重测一次（进容器后停 10 秒不退出）。
2. **串行锁在真机的实际排队体验**：现在第二个安装请求会显示「同一条命令已在执行」，
   而不是排进队列。如果用户觉得应该排队，改成排队只是把 `EXIT_BUSY` 分支去掉。
3. `apk add` 本身耗时（nodejs + npm 约 30–60 MB）在网络差时可能接近超时上限（15 分钟），
   真机上留意耗时日志 `容器命令结束：exit=0 耗时=xxxs`。

## 6. 复现与自查手册

真机上再次遇到安装失败，按顺序看：

1. 日志搜 `容器命令开始` / `容器命令结束`：现在每条都会记，含 exit 与耗时。
   - 只有一条且 `exit=99` → 有外部进程占着 apk 锁（不是本 App 触发的并发）。
   - 出现 `拒绝重复命令` → 用户连点了，按钮禁用已生效说明这是旧包。
2. 日志搜 `包管理器被占用` → 触发了重试；看重试后是否成功。
3. 卡片里的失败文本保留了**最后 4 行**输出——apk 的真实原因几乎总在最后。
