# 门禁链加固：让「验证工具自己失败」能被抓住

> 2026-11-05。范围：`scripts/qa/`。不改任何产品代码。
>
> 一句话：`run-gate-verification.sh` 一直在测 `gate.sh`（**读日志的一方**），
> 而日志是 `run-all.sh` 写的。判定逻辑在源头，却从来没有断言覆盖。

## 一、为什么现在做这个

最近四轮里，「测量工具本身不可信」咬了四次，每一次的表现都是**看起来通过了**：

| # | 事故 | 表现 | 当时怎么发现的 |
|---|---|---|---|
| 1 | `run-localmodel` 用陈旧 class 编译 | 报 `unresolved reference: CapabilityManifest`，像代码坏了 | 重编后 24/24 全过，才知道是产物过期 |
| 2 | `verify-r5.sh` 装包失败 | **exit 0、无输出**，但我以为包装上了 | 发现 `lastUpdateTime` 没变 |
| 3 | 断言普查把注释里的 `.contains("` 计数 | 文本断言从 1370 变 1371，被迫改注释措辞 | census 报错 |
| 4 | 新断言「守在空白区域上」 | 切片按 `init {` 切，而目标字段在切片之外；变异后仍全绿 | 反向变异（把 IPC 加回去，居然不红） |

这四件事的共同点：**它们不需要有人犯错，只需要没人注意**。项目的全部结论建立在
`PASS=92` 和「门禁 5/5」上，如果这两个数字本身可以被静默污染，前面所有轮次的
结论都要打折。

## 二、本轮修的两个漏洞

两个都在 `run-all.sh` 的判定分支里，此前**没有任何测试**（自测只覆盖 `gate.sh`）。

### 漏洞 1：跑了 0 条断言，算 PASS

旧判定只看输出里有没有「通过标记」：

```bash
elif echo "$out" | grep -qE "0 failed|FAIL=0|FAIL: 0|0 失败|_OK [0-9]|全部通过"
```

`=== 结果：0 通过 / 0 失败 ===` 含 `0 失败`，于是被判 PASS。
**空集合满足全称命题**——一条断言都没跑，却和跑满 22 条同等对待。

修法：先判「双零」，再判通过标记。

```bash
elif zero_assertions "$out"; then
  fail=$((fail + 1)); failed="$failed $s"
  echo "FAIL  $s（输出显示 0 条断言：跑了但什么都没验证）"
```

判定规则（三条，都在 `zero_assertions()` 里）：

| 形态 | 正则要点 |
|---|---|
| 中文 | `0 通过 / 0 失败`，**左边界不能是数字** |
| 英文 | 同一行 `PASS...0` 且 `FAIL...0` |
| 英文短语 | `0 passed ... 0 failed`，左边界同上 |

### 漏洞 2：exit 3 一律当 SKIP

`exit 3` 是约定的「环境不具备」码。但旧代码不看理由：

```bash
if [ $rc -eq 3 ]; then
  skip=$((skip + 1)); echo "SKIP ..."
```

真实错误恰好返回 3（某些编译器/工具会）时被静默吞掉。表现是「少了一个 PASS」，
而**新增一个失败 runner 时总数不变**——门禁 5 只卡总数下限，看不出来。

修法：`exit 3` 且输出里没有任何 `SKIP` 说明 → 判 FAIL，并写明原因。

## 三、新增防护：编译产物陈旧

35 个 harness 拿 `app/build/tmp/kotlin-classes/debug` 当 classpath。源码改了没重编时，
它们会报 `unresolved reference`——看上去是代码错，实际是产物过期。事故 1 就是这么来的。

`lib/deps.sh` 新增 `qa_classes_stale <仓库根>`：取最新 `.class` 的时间戳当参照，
找有没有 `.kt` 比它新，有就返回那个文件路径。

- `run-all.sh` 开头查一次，陈旧时打 `WARN` 并提示重编
- 汇总行之后输出机器可读的 `ENV STALE ...`（不塞进汇总行，免得破坏既有解析）
- `gate.sh` 门禁 2 见到 `ENV STALE` 就判 **BLOCKED**，理由写「本轮结论不可信」

为什么不直接 abort：跑完能看到其它结果，但「绿」这个结论被作废。
**结论不可信比结论为红更危险，因为它看起来是好的。**

## 四、自证：新规则先咬了自己两次

这两次都值得记，因为它们是同一类错误的不同形态。

### 第一次：检测器吞掉了「描述现象的文字」

空跑检测上线，跑全量 → **自己的自测被判 FAIL**。查日志，22 条断言全过。

真凶是自测里的一个用例标题：

```
== 场景 6：0 通过 / 0 失败（空跑）→ FAIL ==
```

检测器把**描述这个现象的文字**当成了现象本身。

修法不是改标题（那是迁就检测器），而是给规则加上下文约束：双零必须出现在
含「结果 / 汇总 / TOTAL / SUMMARY」的行里。代价是漏掉不带任何汇总前缀的裸计数——
**宁可漏检，不可误杀**（误杀会让整轮红）。

### 第二次：`source ... || true` 让检查器静默失效

产物陈旧检查写完，自测场景 12 一直红。查下来：测试把 `run-all.sh` 复制到临时仓库，
但**没复制 `lib/deps.sh`**；`source` 失败被 `|| true` 吞掉，`qa_classes_stale` 压根没定义，
检查器一声不响地什么都没做。

改成：

```bash
if ! source scripts/qa/lib/deps.sh 2>/dev/null; then
  echo "WARN  缺少 scripts/qa/lib/deps.sh —— 跳过产物陈旧检查"
fi
```

> 检查器自己失效时，表现是「一切正常」。这比检查报红难发现得多。

## 五、测试覆盖

### 新增 `run-runall-verification.sh`（27 条断言）

造一批剧本明确的假 runner，让**真实的** `run-all.sh` 去跑，断言分类与退出码。
全部在临时目录，不碰真实仓库与真实日志。

| 场景 | 断言点 |
|---|---|
| 1 | 两种通过写法（中文 / 英文）都判 PASS |
| 2 | `exit 1` → FAIL，退出码非 0 |
| 3 | `exit 0` 但无通过标记 → FAIL |
| 4 | `exit 3` 但没说明理由 → FAIL（新） |
| 5 | `exit 3` 且自报 SKIP → SKIP，不阻塞 |
| 6 | `0 通过 / 0 失败` → FAIL（新） |
| 7 | `100 通过 / 0 失败` → PASS（**左边界**，防误杀） |
| 8 | 清单内失败脚本 → XFAIL |
| 9 | 清单内脚本通过 → 报 XPASS |
| 10 | 每个 runner 都落完整日志 |
| 11 | 讨论空跑的文本 → 不误判（**第一次事故的固化**） |
| 12 | 产物比源码旧 → 打 ENV STALE |
| 13 | 产物比源码新 → 不打标记（负向对照） |

### 扩充 `run-gate-verification.sh`（20 → 23 条）

新增场景 11：日志带 `ENV STALE` → BLOCKED，且红必须来自产物陈旧
（断言门禁 5 仍放行，排除「别的门禁顺带触发」）。

## 六、反向变异：六次，全部靶向精确

| 变异 | 结果 |
|---|---|
| 去掉空跑判定 | 3 条红，**全在场景 6** |
| `exit 3` 退回无条件 SKIP | 2 条红，**全在场景 4** |
| 空跑检测去掉左边界 | 5 条红：`20 通过` / `100 通过` 被误杀——证明那条边界真的在挡误报 |
| 去掉上下文约束（退回第一版） | 2 条红，**全在场景 11** |
| 陈旧检查永久失效 | 2 条红，**全在场景 12** |
| 陈旧检查永远报警 | 1 条红，**全在场景 13** |

后两次是一对：只测「能抓到」而不测「不乱报」，检查器可以靠「永远返回陈旧」通过全部断言。

## 七、验证

```
全量 harness        PASS=92 SKIP=0 XFAIL=0 FAIL=0
gate.sh             GATE PASS（5/5）
架构守卫            5 通过 / 0 失败
文本断言            1370 条（未增）
harness 基线        91 → 92（新增一个 runner）
```

新增 runner 后全量实跑一遍，确认**新规则没有误伤任何既有脚本**：
离线回放 91 份历史日志零命中，实跑 92 个 runner 全绿。

## 八、边界

- 空跑检测是**启发式**，不是计数协议。要彻底解决得让每个 harness 输出结构化计数，
  92 个脚本体量太大，本轮没动。当前取舍：**宁可漏检，不可误杀**。
- `qa_classes_stale` 依赖 GNU `find -printf`。macOS 上会退化为「不判断」——
  漏报而不是误报，属于可接受的降级。
- 本轮**没有设备**，未产生任何启动耗时数字，也不宣称启动变快。
