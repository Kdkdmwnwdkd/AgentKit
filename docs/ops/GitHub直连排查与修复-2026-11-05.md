# GitHub 直连：从「连不上」到「能推」，以及途中踩的五个坑

日期：2026-11-05
结论：**直连可用，但前提是把 `github.com` 固定到一个能走的边缘 IP 上。**
推翻 [`沙箱网络与GitHub通道说明.md`](沙箱网络与GitHub通道说明.md) §2 的「`git push` 直连不要用」——
那条结论在当时是对的，但它描述的**不是「协议不行」，是「那个 IP 不行」**。

---

## 一、先看清「连不上」这四个字有多含糊

之前几轮所有的绕路（`gh-proxy` 镜像、Git Data API 手工造 commit、MCP `push_files`），
都建立在一句没被验证过的话上：**「GitHub 连不上」**。

这四个字把四件完全不同的事糊成了一件：

| 层 | 问的问题 | 不通时的表现 |
|---|---|---|
| 1 DNS | 域名解析到哪 | 解析失败 / 落到保留网段 |
| 2 TCP | 443 端口能不能建连 | `Connection timed out` / `Connection refused` |
| 3 TLS | 握手能不能完成、证书对不对 | `SSL handshake failure` / 证书告警 |
| 4 应用 | 认证过不过、请求体传不传得完 | `could not read Username` / `recv error` |

**这四层的修法完全不同**，而过去每次失败都只看到最后一行红字就归因成「墙」。
真正花掉时间的是这个归因，不是网络。

## 二、排查：一次只动一个变量

### 2.1 解析层——正常

```bash
$ getent hosts github.com
20.205.243.166   github.com
```

不是 `198.18.x` 保留网段，没有 DNS 劫持。这一层排除。

### 2.2 TCP 层——**这里是分水岭**

关键动作是**不要只测 `github.com:443` 一个点**，要横向铺开：

```bash
# 同一个 IP，不同端口
$ timeout 5 bash -c 'cat < /dev/null > /dev/tcp/20.205.243.166/443'; echo "443 -> $?"
443 -> 124          # 超时（124 = timeout 命令自己的退出码）
$ timeout 5 bash -c 'cat < /dev/null > /dev/tcp/20.205.243.166/80';  echo "80  -> $?"
80  -> 0            # 通
$ timeout 5 bash -c 'cat < /dev/null > /dev/tcp/20.205.243.166/22';  echo "22  -> $?"
22  -> 0            # 通
```

**同一个 IP，80 和 22 通、443 不通。** 这一条就否掉了三个常见猜测：

- 不是「IP 被整体封锁」——同一 IP 的其它端口是活的
- 不是「SNI 关键字检测」——那要到 TLS 握手才触发，TCP 是能连上的
- 不是「DNS 污染」——解析出来的就是真 IP

### 2.3 换个 IP 试试

```bash
# 同网段的邻居
$ timeout 5 bash -c 'cat < /dev/null > /dev/tcp/20.205.243.168/443'; echo ".168 -> $?"
.168 -> 0
$ timeout 5 bash -c 'cat < /dev/null > /dev/tcp/20.205.243.165/443'; echo ".165 -> $?"
.165 -> 0
```

`.168`、`.165` 的 443 都通，只有 `.166` 不通。

**结论收敛到：单个边缘 IP 的 443 上，SYN 被丢弃。** 既不是网段级，也不是域名级。

### 2.4 再找一个能用的

```bash
$ for ip in 20.200.245.247 140.82.112.3 140.82.113.3 140.82.114.3; do
    code=$(curl -s -o /dev/null -m 8 -w "%{http_code}" --resolve github.com:443:$ip https://github.com)
    echo "$ip -> $code"
  done
20.200.245.247 -> 200     # TLS 握手约 0.2s
140.82.112.3   -> 200
140.82.113.3   -> 200
140.82.114.3   -> 200
```

`--resolve` 这个参数是排查的关键：**它只影响这一次请求的解析，不碰系统状态**，
可以拿一排候选 IP 快速试，试完不留痕。比改 `/etc/hosts` 好，因为改 hosts 需要 root、
容易忘记还原，而且会影响机器上所有程序。

## 三、修复：`http.curloptResolve`

```bash
git config --global http.curloptResolve "github.com:443:20.200.245.247"
```

这一行的作用：**git 自带的 libcurl 在连接 `github.com:443` 时，直接用指定的 IP，
跳过自己的 DNS 解析**。系统 `getent` 看到的还是 `.166`，但 git 走的是 `.247`。

三个好处：

1. **不需要 root**，不需要改 `/etc/hosts`，不影响其它程序
2. **只作用于 git**，浏览器、curl 各自按自己的路由走
3. **可回滚**：`git config --global --unset http.curloptResolve` 一行还原

验证：

```bash
$ git ls-remote origin HEAD
9445b67e0ada7f540d1b42cbb6babe08de190af5	HEAD
```

## 四、通了之后，还有四个坑

别以为能建连就完事。**能读不等于能写，能写不等于写得对。**

### 坑 1：认证——非交互环境根本没有口令可取

```bash
$ git push origin HEAD:main
fatal: could not read Username for 'https://github.com': No such device or address
```

逐条排查过，四条路全空：

| 查法 | 结果 |
|---|---|
| `cat ~/.git-credentials` | 不存在 |
| `ls ~/.config/gh/hosts.yml` | 不存在 |
| `ls ~/.ssh` | 只有 `known_hosts`，无私钥 |
| `env \| grep -i token` | 只有无关的 `CODEBUDDY_*` 变量 |

用 SSH 再确认一次：

```bash
$ ssh -T git@github.com
git@github.com: Permission denied (publickey).
```

> **注意**：这里 `Permission denied (publickey)` 不代表 SSH 不通——**它证明 SSH 是通的**，
> 服务器正常回了拒绝。如果真不通，会是 `Connection timed out`。
> 这两个错误的含义完全不同，过去可能被混着读。

有一个容易踩的点：`~/.gitconfig` 里挂着

```
credential.helper = /usr/local/system/bin/git-credential-helper
```

这个 helper 在**交互式终端**里能弹窗取凭据，但在**管道 / 后台 / CI** 里返回空。
所以「我本地明明能推」和「脚本里推不了」可以同时成立。

### 坑 2：TLS 中断——读通、写不通

拿到凭据后，用一次性 URL 推：

```bash
$ git push "https://<user>:<token>@github.com/<owner>/<repo>.git" HEAD:main
fatal: unable to access 'https://github.com/.../': 
GnuTLS recv error (-110): The TLS connection was non-properly terminated.
```

第一反应是「IP 又坏了」，但同一时刻连测三次 `ls-remote` 全通：

```bash
$ for i in 1 2 3; do git ls-remote origin HEAD; done
9445b67…	HEAD
9445b67…	HEAD
9445b67…	HEAD
```

**读能过、写不过**——问题不在连接本身，在「大 body 的 POST」这条路上。
两个参数解决：

```bash
git -c http.postBuffer=524288000 -c http.version=HTTP/1.1 push <URL> HEAD:main
```

- `http.postBuffer`：git 默认把小于 1MB 的推送缓冲在内存里、一次发完；超过就走 chunked。
  把它调大，让整个 pack 一次发出去，避开 chunked 编码在中间设备上的兼容问题。
- `http.version=HTTP/1.1`：排除 HTTP/2 多路复用在中间设备上被错误处理。

> 这两个参数是**在「读通写不通」这个特定症状下的经验解**，不是通用加速手段。
> 如果症状是「读也慢」，加这两个不会有帮助。

### 坑 3：`git clone` 全量核验跑了 7 分钟没完

推完想核验内容对不对，第一反应是 `git clone` 重新拉一遍。结果：

```
7 分 22 秒，仍在拉取，0 字节输出
```

中止。改用 GitHub API 取 tree 比对：

```bash
curl -s -H "Accept: application/vnd.github+json" \
     -H "Authorization: Bearer <token>" \
     "https://api.github.com/repos/<owner>/<repo>/git/trees/<sha>?recursive=1"
```

一次请求拿到 774 条（含目录）/ 688 个 blob 的 sha，和本地 `git ls-tree -r` 比对。
**成本低两个数量级，结论一样硬**——因为比的是内容哈希，不是「看起来对不对」。

顺带一个坑：**未认证的 API 请求按出口 IP 限流**。第一次匿名调用直接吃到：

```json
{"message": "API rate limit exceeded for 152.136.239.205."}
```

沙箱是共享出口，别人的调用会算到你头上。这种时候不要怀疑 token 失效，是额度问题。

### 坑 4：29 条「差异」，其实是工具的输出编码

第一次比对：

```
远端 blob=688  本地 blob=688
仅远端: 29  仅本地: 29  内容不同: 0
```

内容不同的有 **0 条**，但路径对不上 29 条。看一眼「仅本地」那侧：

```
"docs/\344\270\213\344\270\200\351\230\266\346\256\265..."
```

路径被做成了**八进制转义**。原因是 `git ls-tree` 默认 `core.quotepath=true`，
非 ASCII 路径会被转义，而 API 返回的是 UTF-8 原文。

```bash
git -c core.quotepath=false ls-tree -r HEAD --format='%(objectname) %(path)'
```

加这一个参数，29 条差异归零，688/688 全等。

> **这一条值得单独记**：如果当时看到「29 条差异」就慌了，去改代码或反复重推，
> 会白费一整轮。**比对的失败信号本身，也需要能被解释。**
> 判据是「内容不同 0 条」——那说明数据是对的，对不上的是比对的表示层。

### 坑 5：写完文档才发现，旧文档说「别这么干」

本轮成功后翻了仓库里现有的 [`沙箱网络与GitHub通道说明.md`](沙箱网络与GitHub通道说明.md)，§2 写着：

> | `git clone` / `git push` 直连 | **不要用** | 见 §1 反例，重试是纯浪费 |

这条在 2026-10-30 是对的，而且证据充分。但它记的是**当天的状态**，被写成了**通用规则**。

正确的写法是分开两件事：

- **不随网络变的**：「先分层定位，再决定绕不绕」——永远成立
- **随网络变的**：「直连不通」——今天不通，明天可能通，换个 IP 可能就通

已按那份文档自己的维护约定（§6「旧结论改判，注明证据，不要直接删」）追加改判。

## 五、这套方案的局限，必须说在前面

**写死一个 IP 是有保质期的。** `20.200.245.247` 是 GitHub 的边缘节点，
它今天能走，明天可能被丢包，也可能被 GitHub 自己下线重排。

所以不要把它当成永久修复，要当成「**在当前环境下让路打通的一次性缝合**」。

什么时候会失效，怎么发现：

| 症状 | 说明 | 处置 |
|---|---|---|
| `ls-remote` 变慢或超时 | 这个 IP 也开始丢包了 | 重新跑 §2.4 找新的 |
| TLS 握手报证书错误 | IP 被换了用途，证书对不上 | 立即换 IP |
| 只在某些时段不通 | 链路拥塞，非封锁 | 换 IP 或改用镜像 |

**更稳的做法（本轮没做，留给后面的人）**：

1. 把 §2.4 的候选列表做成探测脚本，启动时跑一遍，选第一个 `200` 的
2. 或者干脆**不用固定 IP**：先试直连，失败再走镜像，把「今天走哪条」交给运行时判断
3. CI / 自动化场景**根本不该依赖这条缝合**——它们应该用官方推荐的认证方式（deploy key / PAT + 标准 https），
   而不是靠一个手挑的 IP

## 六、给下一个人：十分钟诊断脚本

不依赖任何本项目代码，粘进 shell 就能跑：

```bash
#!/usr/bin/env bash
# 用法：bash gh-diag.sh
# 输出：每层一行结论，最后一行为建议

set +e
DOMAIN=github.com

echo "== 1. 解析 =="
IPS=$(getent ahostsv4 "$DOMAIN" | awk '{print $1}' | sort -u)
echo "解析到: $IPS"
[ -z "$IPS" ] && { echo "结论: DNS 失败，先修 DNS"; exit 1; }

echo "== 2. TCP 443（每个解析结果都试）=="
for ip in $IPS; do
  timeout 5 bash -c "cat < /dev/null > /dev/tcp/$ip/443" 2>/dev/null
  echo "  $ip:443 -> $([ $? -eq 0 ] && echo 通 || echo 不通)"
done

echo "== 3. 候选 IP 的 TLS =="
for ip in 20.200.245.247 140.82.112.3 140.82.113.3 140.82.114.3 $IPS; do
  code=$(curl -s -o /dev/null -m 8 -w "%{http_code}" --resolve "$DOMAIN:443:$ip" "https://$DOMAIN")
  echo "  $ip -> $code"
done

echo "== 4. 应用层（需要凭据，可选）=="
git ls-remote "https://$DOMAIN/Kdkdmwnwdkd/Polaris.git" HEAD 2>&1 | head -2

echo "== 建议 =="
echo "  若有 IP 返回 200 但 git 慢/失败 → git config --global http.curloptResolve \"$DOMAIN:443:<那个IP>\""
echo "  若全部不通 → 走镜像：https://gh-proxy.com/https://$DOMAIN/..."
```

判读顺序就是**从上往下**：哪一层断了就停在哪一层，不要跳。

## 七、安全

1. **令牌在聊天/日志里明文出现过，就等于已泄露。** 本轮因为需要推送，凭据在命令行里出现过一次，
   用完全局搜索确认没有落进 `.git/config`、`git remote -v`、任何文件：

   ```bash
   git remote -v | grep -c "ghp_"     # 0
   grep -c "ghp_" .git/config         # 0
   ```

   但这只能证明「没落盘」，证明不了「没进日志」。**建议用完即吊销重发。**

2. 一次性 URL（`https://user:token@host/...`）**不要用 `git remote add` 存**。
   存了就写进 `.git/config`，此后每次 `git remote -v` 都会打印出来。

3. 第三方镜像（`gh-proxy` 等）**永不带可写凭据**。

## 八、一句话总结

> 过去绕过的不是「GitHub」，是一个丢 SYN 的边缘 IP。
> 而之所以绕了那么多轮，是因为每次只看到最后一行红字就归因成「墙」——
> **没把「连不上」拆成解析、TCP、TLS、应用四层去量。**
