## 三、w1（已合入）

### 交付的内容
- `AgentCapability`（只有生命周期，没有业务）+ 注册表 `CapabilityHost`
- `IdleUnloadPolicy`（通用空闲节拍器，30 秒一检查）
- `LocalLlmRuntime`（进程级单例：在途计数 / 节拍 / 配置）+ `wrapLocalLlm()` 每轮轻装饰器

### 合入时改的三处（都写进了 `docs/运行层第一块-接线说明.md` 第七节）

1. **注册表改名** `CapabilityRegistry` → `CapabilityHost`。
   仓库里早有 `com.example.agentkit.skill.CapabilityRegistry`（工具权限的 fail-closed
   真相源），两者一个管「工具多危险」、一个管「功能何时启动」，同名不同义，且同时出现在
   同一个 `ChatViewModel` 里。grep 与 IDE 自动导入必然互相误伤。

2. **启动等待加 15 秒上限**。原 `startIfNeeded` 等 `STARTING` 是无超时 `while` 轮询：
   任何能力 `start()` 抛异常却把状态留在 `STARTING`，后续所有调用**永久挂住**。
   现在超时 / 抛异常 / 返回却没置 READY，三种出口统一抛 `CapabilityStartException`
   （带能力 id 与原始 cause）。顺带修了 `stop()` 后重启会重复起事件收集协程的泄漏。

3. **空闲阈值 5 → 30 分钟**。3B Q4 冷加载真机实测约 14 秒（10-29 日志）。
   5 分钟一卸，等于把「看会儿别的再回来问一句」变成 14 秒黑等：省 2GB 内存，
   赔首字延迟。释放日志也补上了代价说明（「下次对话会自动重载，首字会慢十几秒」）。

### 新增验证
`scripts/qa/run-runtime-capability-verification.sh`：32 项。
静态 22 项（命名不撞车 / 有超时 / 阈值 30 / 接线 / 两道闸门 / stop 取消协程），
行为 10 项真编真跑（幂等、依赖先启、异常定位到 id、假装就绪被判失败、停后可重启、
重复 id 被拒）。

> kotlin-stdlib，挑到旧版，编译用新、运行用旧 → `NoClassDefFoundError: SpillingKt`。

## 四、w2（暂缓）

**内容**：机型画像 → 三档（ECO 4 线程/4K、BALANCED 6/8K、PERFORMANCE 8/16K），
AUTO 档「只减不增」（`min(用户值, 档位值)`），锁档按表直取，画像缺失不猜档。

**不阻塞合并的理由**：对当前这台机器**不会压参数**。用户设 4 线程，
`min(4, 6或8)` 仍是 4；ctx 4096 也低于任何档位上限。逻辑本身是对的。

**暂缓的理由（产品层面）**：
1. 会在设置页多一个「资源档位」选项。正在做线程/绑核调优的阶段，多一个会改参数的
   入口等于给判断加噪声；
2. 档位表的三组数字是**按典型机型推的，没有多机型实测**（报告自己扣的 1 分就是这个）；
3. 与 W-97/W-98 的结论有张力：我们实测「线程多反而 decode 慢」（5 线程比 4 线程慢），
   而 BALANCED 档允许 6 线程。等 tok/s 收敛后，档位表应当按实测重写，而不是照抄。

## 五、w5（不建议整分支合）

**内容**：w2 + 7 块功能（W3 审批档位 / W4 提示词变量 / W5 SSH 远端 shell /
W6 本地知识库检索 / W7 费用下钻 / W8 二维码配置迁移 / W9 长对话归档）。

### 三段式问题

1. **命名误导**：报告标题写「运行层主链 W3–W9」，但这 7 块**不是运行层**——
   运行层只有 w1 那三个文件。把功能增量挂进运行层分支，会让「运行层」这个词失去边界。
2. **真机零验证**：作者自己只给 8.5，扣分点写明「UI 交互未经真机」。
   二维码扫描导入、审批弹窗手感、SSH 实连，这三样都只能人验。
3. **方向与诉求相反**：这 7 块让设置页新增 4 个区块（审批三档、资源档位、SSH 档案、
   费用参考），界面比现在**更挤**。而当前诉求是「功能太多、太拥挤、要用才开」。

### 可拆出来单独评的块
- 低风险、纯逻辑、易验：长对话归档（W9）、提示词变量（W4）
- 中风险、需人验：审批档位（W3，改了权限判定路径）、费用下钻（W7，只是展示）
- 高风险、必须真机验：二维码迁移（W8，自写编码器）、SSH（W5，真连远端 + 新攻击面）

## 六、共性发现（三个分支都有）

1. **`startIfNeeded()` 全仓 0 个调用点，能力实现只有 1 个**。
   也就是说「按需加载」这套机制目前**没有任何功能真的走它**——骨架搭好，电线没接。
2. **能力契约只管运行时资源，完全不管界面**。
   诉求是「界面拥挤」，这套东西解决的是「内存不释放」，两者不是一回事。
   要真解决拥挤，得让设置页/首页从「功能表」渲染，而不是继续往写死的 `Column` 里加区块。
3. **编号体系分叉**：新分支用 W-RT1…W-RT9，主线用 W-9x。将来追溯「哪版引入的」会打架。
   本次合入统一按主线编号记作 **W-99**。

## 七、留给下一个话题的基线（工具面现状）

为避免重复摸底，先把当前事实记在这里：

| 事实 | 数值 / 位置 |
|---|---|
| 注册的工具数 | **51 个** `register(...)`（`ChatViewModel`） |
| 工具实现的文件数 | 24 个（`tools/*.kt`） |
| 本地模型实际暴露 | **7 个**（`ToolExposurePolicy.LOCAL_CORE_TOOLS`） |
| 云端 provider | 不裁剪，全量 |
| 轻聊 / Agent 分档 | `LocalLlamaSetting.agentMode`，**默认关**（关＝轻聊档，不注入工具协议） |
| Agent 档系统提示体量 | `LocalAgentPrompt` 字符串约 3139 字符 ≈ **1400 token**（不含 7 个工具 schema） |
| 轻聊档系统提示体量 | `LocalChatPrompt` ≈ **57 token** |

也就是说：**「工具清单每轮过一遍」这件事在本地通道已经裁过一轮**（51 → 7），
并且默认走轻聊档。如果真机上仍感觉慢，下一步该量的是：
- 每轮 `prompt 长度：N 字节 → M token` 的 M 到底是多少（日志里有）；
- Agent 档那 1400 token 系统提示 + 7 个 schema 在 M 里占多少；
- 51 个工具**构造**本身在冷启动时花多久（部分工具构造会建目录 / 扫路径 / 探测二进制）。

这三项量出来，才能判断「运行层优化」该砍哪里，而不是凭感觉加一层抽象。
