## 结构性问题

### A 级（会导致错误）

**A1 附件是“跟着人走”的第四轴，不是“跟着会话走”。**
`_pendingImages`/`_pendingFiles` 挂在 VM 上（`ChatViewModel.kt:2447`、`:2530`），
`loadConversation()` 清译文、存草稿、换输入，唯独不动附件（`:3178-3187`）。
在 A 会话贴了截图/文档，切到 B 会话发消息，附件随 B 的请求发出去——用户视角是“串味”，
模型视角是“莫名其妙收到一份别的对话的材料”。
根因：附件生成于 Composer（`ChatContracts.kt:100-108`），却由 Conversation 轴的生命周期管；
两轴之间没有归属键。
最小修法：附件加 `forConvId`（或按会话存 Map），`loadConversation` 投影，`send()` 只取 `forConvId == owner`。
**A2 `sessionAllowed` 是进程级，注释却写“本次会话”，且无清空点。**
`ChatViewModel.kt:1629` 声明，`:1648` 读、`:1675` 写，全仓无 `clear()`。
`newConversation()`（`:3205-3212`）与 `switchConversation()`（`:3224-3227`）都不碰它。
后果：在闲聊会话里对某个可记忆组点过“始终允许”，之后换到执行真实任务的会话，
同类操作不再弹窗——R-08 把**风险粒度**收紧了（不可逆命令不可记忆），但**时间粒度**仍然是“进程活着就有效”。
根因：审批授权没有挂在任何一条状态轴上，是第四轴里最隐蔽的一个。
最小修法：把集合搬进 `GenerationRunController` 的 owner 生命周期（`finish()` 清），
或至少 `newConversation()` / `switchConversation()` 清空并改名为 `processAllowed`。
判据：切换会话后首个同类危险调用必须重新弹窗。
**A3 审批 / 追问 / 计划卡片不按归属会话过滤。**
`pendingApproval`、`askUserPending`、`planPending` 三条流都直接渲染
（`ChatScreen.kt:195`、`:646-648`、`:668-671`），卡片不知道自己属于哪个会话。
生成中允许切会话（`ChatViewModel.kt:3218-3227`），于是 A 会话的审批弹窗会盖在 B 会话上，
用户点“允许”批准的是自己看不见的那条命令。
根因：运行态有 owner（`GenerationRunController.owner`），挂起态没有——它们是 process 单例
（`AskUserBroker.kt:41`、`PlanBroker.kt:57`）。
最小修法：三个 pending 各加 `convId`（broker 的 `ask/propose` 入参已有上下文，
`ChatViewModel` 传 `generation.targetConversation()`），UI 侧与 `activeConversationId` 不等时
显示“另一个对话在等你确认”并给“跳过去”入口，而不是直接弹操作按钮。

### B 级（阻碍演进）

**B1 契约按“屏幕”切，不按“驱动源”切——所以它没变窄。**
`ChatContracts.kt:26-43` 的自述说拆的依据是“状态变化的驱动源”，但落地结果是
7 个子接口合并成一个 51 成员的 `ChatScreenContract`，而 `ChatScreen` 恰好用满 51 个
（集合相等）。同一份 VM 被切成十几面镜子，每面都映一份完整依赖面：新增一个字段仍要
改契约 + VM + 屏幕；重组粒度仍是“整页”。
根因：切分单位是**消费者**而非**变化频率**。真正的驱动源只有四个：token（每帧）、
回合边界（每秒级）、用户输入（每次敲键）、配置（每次保存）。
最小修法（渐进、不动页面结构）：在 `ChatScreenContract` 内部把 `ChatStream` 再降一级——
`messages` 与 `streamDraft` 不再同层传给 `ChatScreen`，而由 `ChatScreen` 只把
`streamDraft` 透传给末尾草稿条目（消费方自己 collect），页面根不读它（见 B3）。
契约文件不动，改 3 个调用点。
**B2 `refreshConversations()` 仍是 O(全库)，且被两侧线程同时调用。**
`list()` 每次对全部会话的全部轮次全部变体求和再排序（`ConversationStore.kt:374-400`），
而 `onStoreChanged` 在**每条消息落库后**同步触发（`ConversationProjection.kt:122-125`）。
一个 20 轮的会话有 40+ 次工具事件 → 40 次 × O(全库)。主线程路径在切会话/删轮
（`ChatViewModel.kt:1582-1620`），Agent 回调路径在 `handleAgentEvent`（`:2013`）之后。
根因：把“摘要列表需要更新”实现成“重算摘要列表”，缺少增量。
最小修法：`ConversationStore` 维护 `id → ConversationSummary` 缓存，`appendMessage` 只重算**被写的那一条**，
`refreshConversations()` 发布快照。判据：追加一条消息不得触碰其它会话（`store.list()` 调用计数桩即可判红）。
**B3 `streamDraft` 被提升到 `ChatScreen` 函数根，导致每 token 整页重组。**
`ChatScreen.kt:181` 在页面根部 collect，`:466` 又把它捕获进 `itemsIndexed` 的 item lambda。
`UiItem` 没有 `@Stable`（`core/UiItem.kt:24`），工程用 Compose 1.5.15（`app/build.gradle.kts:81`）
没有强跳过 → `MessageRow(item: UiItem, …)` 不可跳过。所以每个 token：
`GenerationRunController.appendText`（`:107`）→ `_draft.value` → `ChatScreen` 整页重组
→ 全部可见 item lambda 重建 → 每个 `MessageRow` 重跑 → 末尾草稿条目
`UiItem.Assistant(streamDraft.orEmpty())` 每帧新建对象 → `MarkdownText` 以 text 为 key
**全量重解析**（`MarkdownText.kt:62`）→ 整段回答 O(n²)。
最小修法（两处，合计 <60 行）：① 草稿条目自己 collect（把 `streamDraft` 从页面参数表里拿掉，
只在 `item(key="stream-draft")` 内部读），页面根不再订阅；② `UiItem` 加 `@Stable`
（密封接口注解对全部实现生效），让未变的 `MessageRow` 真正跳过。
判据：Token 注入 1,000 次，`MessageRow` 组合次数不随 token 增长（可用 harness 计
composition 次数，或加 `Modifier.layout` 计数）。

**B4 `sessionUsage` 仍是 `Eagerly`。**
`ChatViewModel.kt:1989-1993`：`messages.map{ sum }` + `SharingStarted.Eagerly`。
没有 UI 收集（在设置页、日志页、后台）时仍在算；每次工具事件都全表求和，会话内 O(n²)。
最小修法：`WhileSubscribed(5_000)` + 在 `appendItem` 处增量累加（assistant 的 usage 加一次），
不需要全表扫描。改动 <20 行，`TokenUsage.sum` 保留给重载路径。

**B5 五步拆分 0/5，而“接口层完成”制造了已拆完的错觉。**
第 3 步（窄接口）先落地、第 2 步（拆文件）没落地，于是 `ModelConfigScreen` 看起来“已经独立”，
实际 43 个成员全部由同一个 3,869 行类实现（`ChatViewModel.kt:375`）。
阻力不是 UI（已挡住），而是：① 每个待拆块都被 `send()` 与 `handleAgentEvent()` 直接引用
（`send` 里用 `_pendingImages/_pendingFiles`、`resolveMentionBlock`、`projectRulesBlock`，
`:2708-2770`）；② 私有函数是类成员，搬出去要先改成顶层/对象（`friendlyMessage:3009`、
`isResumeIntent:448`、`summarizeServerError:2991`）；③ 基线余量为 0，任何“先加后删”的
中间态都会撞 guard。
最小修法：按“纯函数 → 无 UI 依赖的对象”单文件纯搬移，一次一步、同步下调 `arch-baseline.txt`；
第一步 `ChatText` 不改任何 UI 签名，是唯一零阻力的一步。

### C 级（只是不好看 / 会漂移）

**C1 配置语义与失败恢复策略写在 `onClick` 与 `when` 里。**
`ModelConfigScreen.kt:1459-1474` 用注释解释“切到本地不清 Key”，`:2172-2189` 把
`RecoveryAction` 映射成按钮文案。前者是配置语义、后者是诊断策略，都该由 core 给出
（`ConfigSanitizer` / `Diagnosis` 已经有位置），现在等于第二份真源。
最小修法：前者收敛成 `ProviderCatalog.switchToLocal(config)` 一个函数；后者保留 UI 分支，
但把文案表挪到 `TestResult` 的伴生对象，避免文案与 `FailureKind` 分头改。
**C2 倒计时以“本次组合起点”计，离开页面再回来会从 30s 重播。**
`ChatScreen.kt:2781-2786` 用 `System.currentTimeMillis()` 作为起点，`ApprovalRequest`
没有创建时间（`ChatViewModel.kt:287-295`）。权威 deadline 在 VM（30s 后 deny），
显示却可能从 30s 重新走——用户看到 25s 剩余时实际 2s 后就被拒。不会挂死，但会“骗人”。
最小修法：`ApprovalRequest` 加 `atMs: Long = System.currentTimeMillis()`，倒计时改为
`APPROVAL_TIMEOUT_SEC - (now - request.atMs)/1000`。5 行。
