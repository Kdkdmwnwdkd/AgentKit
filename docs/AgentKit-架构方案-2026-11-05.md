## 0. 一页速览

**这个项目现在是什么**：一个单进程、离线优先的 Android 本地 Agent。四条真实分界线是
「界面 / 回合编排 / 能力接入 / 系统执行」，这条骨架是成立的，也是它最值钱的部分——
56 个工具能按组动态加权、六种执行后端能沿一条降级链自动回退、三家模型协议能收敛到
一个 `chatOnce` 入口，这三件事在同类项目里通常都做不成。

**但有三个结构性事实必须先承认**：

| # | 事实 | 后果 |
|---|---|---|
| 1 | **五个文件同时顶在行数天花板上，余量为 0**（`ChatViewModel` 3884/3884、`ChatScreen` 3157/3157、`ModelConfigScreen` 2309/2309、`RealAgentLoop` 1553/1553、`AppScaffold` 1516/1516）✔ | 任何功能改动都先要「腾地方」，重构与需求互相锁死 |
| 2 | **架构守卫只覆盖 5 个文件、只检查 3 个包名**，73,006 行里 71,000 行不受任何结构约束 ✔ | 边界靠自觉，「四层分离」在 core 内部已出现 6 处未登记的反向依赖 ○ |
| 3 | **质量体系是「源码文本镜像」而非行为验证**：1370 条文本断言 / 53 文件，主要断言「代码长什么样」 ✔ | 重构时断言集体变红，重构成本被质量体系自己放大 |

**P0 清单（都是小改动、真实缺陷，建议本周做完）**：

- `R-01` 上下文预算的供应商窗口收敛**全程失效**——`LLMClient.id` 返回协议名 `"openai"`，被当成供应商 id 去查目录，恒返回 0 ✔
- `R-02` 生成中切会话，**标题写到新会话**（`ChatViewModel.kt:2989` 用 `_activeConversationId` 而非 owner） ✔ 已修
- `R-03` 危险操作审批的 30 秒超时**写在 Composable 里**，离开对话页即失去超时，`await()` 永久挂起 ✔ 已修
- `R-04` `run-all.sh:132` 用子串匹配判断「0 失败」，**打印「10 失败」会被判 PASS** ✔ 已修
- `R-05` 消息列表 `itemsIndexed` **无 key**，工具卡原位替换导致整表重排 ✔ 已修
- `R-06` 取消/失败后工具卡**停在「执行中」**，重载后变「已完成」+ 空结果 ✔ 已修
- `R-07` 停用 MCP 服务器后**工具仍在**（B 级，随 P1 的注册回卷一并做完） ✔ 已修
- `R-08` `approveAlways` 按组记忆，勾一次「不再询问 shell」后 `rm -rf` 不再确认 ✔ 已修
- `R-09` 重试粒度是整次请求，已上屏的文本会**重放一遍** ✔ 已修
- `R-17` 新 harness 只要 `exit 3` 就能永久 SKIP，**门禁照样绿**（零覆盖） ✔ 已修
- `R-20` 工具 schema 暴露 `su` / `ssh`，而这两个身份**首期没有执行路径** ✔ 已修

**路线结论**：不要先做新能力。先花两周把「余量」和「守卫」补上（P0 + 守卫升级），
再按「抽控制器 → 换窄接口」的顺序拆 `ChatViewModel`，最后才谈 Phase 2 的自授权通道。
顺序反了，Phase 2 的两三千行会直接压到已经没有余量的 `RealAgentLoop` 上。

## 1. 约束条件

架构方案必须先服从约束，否则都是空谈。下面这些是从构建脚本和运行环境里读出来的**硬约束**，不是偏好：

| 约束 | 事实依据 | 对架构的强制影响 |
|---|---|---|
| 单 APK、单进程、无 root | `AndroidManifest.xml`；无多进程声明 | 所有「后台能力」只能在进程内做，靠前台服务/无障碍/Shizuku 借权 |
| `targetSdk = 28` | `app/build.gradle.kts:47` 附近，注释写明原因 | 刻意降级以允许 `filesDir` 内 `execve`（proot 必需）；代价是放弃 29+ 的存储/通知新约束 |
| 仅 `arm64-v8a` | `abiFilters += "arm64-v8a"` | 原生推理与终端 JNI 单架构；x86 模拟器只能跑 `-PnoNative` 削弱包 |
| 无 GMS、离线可用 | 依赖清单无 play-services；OCR 用打包模型的 mlkit | 不能依赖任何云侧 SDK 做基础能力 |
| 本地推理 `n_ctx` 极小 | `ContextBudget.LOCAL_LLAMA_BUDGET_TOKENS` | 上下文预算必须按通道自适应，云端/本地不能共用一套参数 |
| **依赖并非为零** | `app/build.gradle.kts:124-148`：Shizuku api+provider、WorkManager、Compose BOM、coroutines、kotlinx-serialization、**okhttp 4.12**、**rhino 1.7.14**、**mlkit text-recognition-chinese** ✔ | 见下 |

> **关于「零第三方依赖」的订正**
>
> `README.md:6` 写「零第三方新增依赖」，`docs/` 里多处把它当作纪律引用。实际 `build.gradle.kts`
> 里有 8 个外部库，其中 okhttp、rhino、mlkit 都是**能力性依赖**（网络栈、JS 引擎、OCR），
> 不是可有可无的胶水。
>
> 这不是道德问题，是**表述失真带来的判断风险**：接手的人会以为「加个库」是不可能的，
> 于是把本该用库解决的事手写成 2000 行自有实现；反过来，评审时又会拿这句话质疑任何引入。
>
> 建议把纪律改写成可执行的版本：**「新增依赖需在 `docs/DEPENDENCIES.md` 登记用途、体积、
> 许可证、退出成本；能用 200 行以内自有实现替代且无正确性风险的，不引依赖。」**
> 这条既能保留原有的克制，又能解释 okhttp 和 rhino 为什么该在。

**这条骨架的判断**：L2 与 L3/L4 的分离是真实的——`RealAgentLoop` 不认识任何具体工具，
只认 `ToolRegistry` 的 descriptor；`TerminalSessionPool` 不认识 Agent，只认 `TerminalBackend`。
这两处是项目里最干净的两个接缝，后续所有演进都应该**沿用**它们，而不是绕开重造。

### 2.2 已存在的边界违例

守卫脚本 `run-arch-guard-verification.sh` 只扫 `core/` 下对 `ui`、`tools`、`MainActivity`
的 import，因此下面这些**同性质但换了个目标包**的依赖不会被发现 ○：

| 文件 | 反向依赖 | 性质 |
|---|---|---|
| `core/ConfigStore.kt:5` | → `skill.ModelConfig` | 基础设施依赖能力层 |
| `core/CapabilityAuditReporter.kt:5` | → `skill.CapabilityRegistry` | 同上 |
| `core/terminal/ContainerSession.kt:7`、`ProotBackend.kt:8` | → `terminal.TerminalSession` | 同一能力被两个包各实现一份 |
| `core/job/CompletionNotifier.kt:10` | → `AgentKitApplication` | 基础设施依赖 app 壳 |

结论：**「L0 不依赖 L3」目前不成立**。这不是必须立刻修的缺陷，但它是「core 无法独立编译」
的直接原因，也是任何模块化尝试的第一道墙。

### 2.3 目标分层规则（建议写进守卫）

| 规则 | 表述 | 检查方式 |
|---|---|---|
| D1 | `L1 → L2/L3/L4/L0` 允许；反向一律禁止（现有 3 条豁免按只减不增冻结） | import 扫描，扩展到全部包名 |
| D2 | `L0` 只能依赖 `L0` 与 JDK/Android 框架 | 同上 |

## 4. 关键运行链路

### 4.1 一轮对话（已是事实，作为目标基线）

```
send() → runTurn(turnId, AgentScope)
  ├─ 装配：SystemMessage(FROZEN/SESSION/TURN 三段) + priorMessages + UserMessage
  │        └─ 系统提示每回合只拼一次，保 KV 前缀（对本地推理是刚需）
  ├─ 每步重算工具暴露面 KernelExposure.plan()（seed file → 强制 pin → 滞回淘汰）
  ├─ buildRequestMessages：pruneImages(保最近 2 张) → fitToBudget(按完整步整组丢)
  ├─ chatOnce → streamChat → TextDelta/ReasoningDelta 只进回调，Completed 整条入历史
  │        └─ 非 SSE 供应商：未见 `data:` 即转 PlainBody 整段解析（优雅降级）
  ├─ finish_reason 归一（length/stop/其它），截断每回合只报一次
  ├─ executeBatch：含写整批串行；全只读 chunked(5) 并行且保序
  └─ 取消：ensureActive 每步检查；NonCancellable 内 closePendingToolResults 补配对
```

**评价**：这条链路的设计质量高于项目其他部分——三段式系统提示保缓存、按「完整步」裁剪
而不是按消息裁剪、只读工具并行但保序、取消时补配对，这四点都是踩过坑之后的正确解。
**方案里不要动它**，只把装配逻辑搬出去（见 §9 P1-2）。

### 4.2 工具调用（七道闸）

```
模型 tool_call
 → scopedRegistry.descriptor 校验（只认本回合可见）
 → ① 未启用？        → tool_not_enabled（并指出该开哪个组）
 → ② 失败熔断？      → 短路，避免同一工具连续踩坑
 → ③ 参数级审批？    → needsApprovalFor → UI 弹窗（同组一次放行）
 → ④ 副作用登记？    → DISP 落盘，写不进则拒写
 → ⑤ 执行（90s 只读 / 600s 写）
 → ⑥ truncateToolResult（按预算 1.2×，下限 1000 字符）
 → ⑦ ToolMessage 回灌 + 图片单独回灌
```

这套闸门序列是**本项目最有复用价值的设计**，建议原样保留，只做两件事：
把回执码枚举化（现在是散字符串 `tool_not_enabled`/`approval_denied`/`session_desynced`），
以及把「审批粒度」从组降到「身份 + 命令前缀」（见 `R-08`）。

### 4.3 执行后端选择

`providersFor` 唯一降级链：`proot → shizuku → adb → user`，逐个 `start()`，失败回落。
三层资源由 `runtime/lease` 统一节拍回收，`activeCount>0` 与 `isSafeToRelease` 双闸，
**只告警不夺资源**。会话并发由 `TerminalSessionPool` 的「每会话一把 Mutex」保证，
`(backendKey, alias)` 分池 + 4-hex 句柄 + 哨兵串判定完成，超时置 `desynced` 而不是静默错位。

**架构判断**：这是全项目最接近「工业级」的一块。它原先缺一个维度——**身份**：
`TerminalIdentity` 只是展示位，非 User 直接返回空，身份靠 `backendKey` 侧载，
于是七个后端实现（含以 uid 2000 跑的 Shizuku 与无线调试）**一律自称 `User`**。
R-12 已修：`identity` 变成带 `uid` 的**权限档**，请求值是下限、后端声明值是实际，
一个谓词 `satisfies` 贯穿工厂筛选、会话复用、执行校验三处。
现在 `prefer_proot=false` 拿到的会话会如实报告「uid 2000」，`identity=shizuku` 也能进池开持久会话。

### 4.4 生成中切会话

```
GenerationRunController.owner(@Volatile) ← start() 写入 / finish() 清空
isOwnerActive() = owner != null && owner == activeId()
appendText()    → 先攒 draftBuffer，仅 ownerActive 才写 _draft
syncDisplay()   → 切回时从断点恢复打字机
落库目标        → store.appendMessage(owner ?: active)
```

机制本身是对的（owner 捕获 + 条件投影），但**最后一米漏了两处**：
标题生成用 `_activeConversationId`（`ChatViewModel.kt:2989`），`finish()` 先清 owner
再回调宿主，导致收尾后在飞的工具回调仍落到「当前会话」。修复方式是**把 owner 换成运行代次
token**，而不是继续补 if。

## 5. 契约层

| 契约 | 定义位置 | 现状 | 需要补的约束 |
|---|---|---|---|
| `AgentTool` | `core/AgentContract.kt:19-38` | `{name, description, parameters, readOnly, needsApprovalFor}`，组信息不在工具上（R-13：组/审批组/capability 统一进 `ToolCatalog`，其余三处变派生视图） | 新增工具只剩两处：工具类 + 目录一行；漏改由 `run-r13-catalog-verification.sh` 判红 |
| `ToolResult` | 同文件 | `{ok, code, message, hint, data}` | `code` 枚举化；`hint` 应可由 `code` 推导 |
| `LLMClient` | `core/LLMClient.kt:176` | `id` = 协议名（`"openai"`/`"claude"`/`"gemini"`） | **`id` 语义已过载**：既当协议标签又被当供应商 id 查窗口，直接导致 `R-01` |
| `LLMConfig` | `core/LLMClient.kt:31` | `baseUrl/apiKey/model/customHeaders/customBody/reasoningLevel` | 缺 `providerId`，是 `R-01` 的根因 |
| `TerminalBackend` | `core/terminal/backend/` | `open/write/read/close` + `backendKey` + `identity` | R-12 已让 `identity` 成为**实际权限档**（带 `uid`），与 `backendKey`（通道）是两个维度 |
| `Store` | `ConversationStore` 等 | 内存 `synchronized` + 单线程 400ms 去抖 + 原子替换 | 缺 schema 版本、缺跨 store 事务 |

> **一条设计原则**：这五个契约里，凡是「用字符串承载枚举语义」的地方都出过事——
> `style` 拼错静默回落、`client.id` 协议/供应商标识混用、回执码散字符串、后端名重复两份。
> 下一步不需要引入密封类体系，只要**把字符串常量收进 `object` 并让 harness 断言穷尽性**即可。

## 6. 状态与数据

### 6.1 三条状态轴

| 轴 | 载体 | 特点 |
|---|---|---|
| 会话数据 | `ConversationStore`（整库 JSON → R-10 后分片 + 轻量 index） | 权威、可恢复 |
| 运行态 | `GenerationRunController` + `AskUserBroker`/`PlanBroker`（进程级单例） | 易失、跨 ViewModel 生命周期 |
| 显示投影 | `ConversationProjection` + `streamDraft` | 可丢弃、条件投影 |

`ChatViewModel` 里 **72 个公开 `StateFlow`、108 个公开函数、51 个 `MutableStateFlow`**，
没有统一 `UiState` 边界 ○。这不是「状态多」，是**状态所有权从未收口**——
所以新增功能默认继续往 ViewModel 加流，冻结线一次次弹回去。

### 6.2 落盘

| 项 | 现状 | 判断 |
|---|---|---|
| 写入单位 | **整库全量重写**（序列化全部会话）→ tmp → `fd.sync()` → 复制 `.bak` → rename | 原子性合格；写放大不合格 |
| 去抖 | 单线程 `ScheduledExecutor` + 400ms；结构性变更 urgent 直写 | 合理 |
| 最坏损失 | ≤400ms 变更 + **整段在途回复**（草稿不落盘） | 可接受，但 `flush()` 全仓零调用是隐患 |
| 版本 | 业务文件**无 schemaVersion**，只靠 `ignoreUnknownKeys` + 默认值 | 前向兼容靠 Kotlin 默认值撑，向后兼容无解 |
| 双写 | `messages` 与 `turns` 两份并存 | 写放大 2×，且字段永远删不掉 |
| 备份 | 覆盖 5 类，**不含** workspace/skills/jobs/logs/media | 换机迁移会丢工作区与技能 |
| 备份校验 | 条目白名单 + 单条 24MB + 累计 64MB + 条数比对，**无哈希** | 坏包可静默入库 |

## 7. 非功能设计

### 7.1 性能

已量化的基线（来自项目自身埋点）：冷启动 `total` 2.1–2.4s，慢段 `refresh` / `registry` / `skills`。

现存热点 ○：
- `refreshConversations()` 遍历全部会话 × 全部变体求和，**主线程 O(全库消息)**，每次追加消息/工具事件都触发
- `sessionUsage` 用 `stateIn(Eagerly)` + `O(n)` 全表扫描，**每次工具事件跑一遍 → 会话内 O(n²)**
- `streamDraft` 每 token 发射，读点在 `itemsIndexed` lambda 内 → 每个 token 重跑全部可见行
- `AgentLogger.restoreTail` 在 `Application.onCreate` 用 `readLines()` 全量读两个 2MB 文件

**目标**：冷启动 ≤2.0s（P50）、对话滚动不掉帧、工具事件不触发全量扫描。
手段不是优化算法，而是**把数据派生从主线程挪走 + 给列表加稳定 key**。

### 7.2 可靠性（降级矩阵）

| 故障 | 现有降级 | 缺口 |
|---|---|---|
| 供应商不返回 SSE | 转 `PlainBody` 整段解析 | 仅 OpenAI 通道；Claude/Gemini 未覆写 `streamChat` |
| 429 / 5xx | 10/30/60s 退避 + 尊重 `Retry-After` | 重试粒度是整次请求，**已上屏的 delta 会重放** |
| 权限缺失 | 六级后端回落 `proot→shizuku→adb→user` | 文案与代码两份真源 |
| JSON 异常 | `JsonSafe` 已覆盖 42 文件 / 244 处 | 基本清零（「21 文件 188 处硬转换」是过期数字） |
| 落盘失败 | 原子替换 + 保留 `.bak` | rename 失败退化为直接覆盖，可能截断主文件 |

### 7.3 安全

| 维度 | 现状 | 风险等级 |
|---|---|---|
| 危险工具分级 | 19 个 DANGEROUS，**fail-closed**（未知=DANGEROUS） | 好 |
| 审批 | 参数级 `needsApprovalFor`，同组一次放行 | 中：`approveAlways` 按 `shell` 整组记忆，之后 `rm -rf` 不再弹 |
| 路径沙箱 | **仅** `read_file/write_file/edit_file` 做 `startsWith(workspace)` | 高：shell/容器/ADB 无任何路径限制 |
| shell 规则 | 只有「只读白名单」决定是否弹窗，**无执行黑名单** | 中：设计如此，但需在文档里说清这是「审批」不是「拦截」 |
| MCP | 每次调用必确认 | 好 |
| 技能包 | Zip Slip 防护 + id 白名单 | 好，但 `load_skill` 被判 SAFE 且无审批却会下载安装可执行 JS |

### 7.4 可观测

`StartupTrace`（分段可归因）、`TurnJournal`（逐步恢复日志）、`AgentLogger`（500 条环 + 2MB×7 天）、
`ToolLoadProfiler`（逐工具装配耗时）。这套东西已经够用，缺的是**统一的 code 维度**——
回执码不枚举化，就没法做「按失败码统计」这种最基本的运维视图。

压到没有余量的文件上，最后只能抬基线，等于把守卫废掉。

### P1 · 结构（3–4 周，按「先抽控制器、后换窄接口」）

## 10. 守卫与度量升级

现有体系是四层（断言 → 运行器 → 门禁 → 基线），骨架没问题，问题在**判据太软**。

| 升级项 | 现状 | 目标 | 实现代价 |
|---|---|---|---|
| 结果协议 | 文本匹配「0 失败」 | 每 runner 末行 `QA_RESULT pass=N fail=N skip=N`，整数解析，`pass=0` 一律红 | 小，纯 bash |
| 门禁判据 | 只看 PASS 总数，SKIP 算覆盖 | ✔ 已做（R-17）：SKIP 必须走 `KS_HARNESS_SKIP`，且理由里的缺件路径由 `run-all` stat 核验（说缺的东西其实在就判 FAIL）；每个 SKIP 逐条登记进 `skip-allowlist.txt`，条目数冻结；有 SKIP 时 PASS 下限主动让位（前提不成立），改由登记册逐条核对 | 小 |
| 架构守卫 | 5 文件 + 3 包名 | 全仓 ≤1500 行 + 各包行数总量预算 + 豁免必须带 `ARCH-EXEMPT:` 理由 | 中 |
| 变异测试 | 手动做过 | 每周 `schedule` 在 `/tmp` 副本注入 1 处变异（删 `coerceIn`、改常量），对应 runner 必须红 | 中，零新依赖 |
| 断言结构 | 1370 条文本断言 | 新增断言一律「结构化比较」，文本断言总量只减不增（现有机制已如此） | 已在做 |

**判断「这套源码扫描路线什么时候失效」**：>100k 行时，三个点会先崩——
①81 个 runner 各自硬编码源文件清单，文件一拆就编译失败；
②文本断言随重构面积线性增长；③无影响分析，94 个 runner 全量跑。所以 P1 的拆分必须
**与 runner 清单同步改造**，否则拆一个文件红一片。
