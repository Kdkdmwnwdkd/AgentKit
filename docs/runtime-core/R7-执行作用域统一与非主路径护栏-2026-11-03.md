# R7 · 执行作用域统一与非主路径护栏

> 2026-11-03 ｜ 净线实现 ｜ 分支 `main` ｜ 编译通过 · 全量 QA `PASS=74 SKIP=1 XFAIL=0 FAIL=0` · 门禁四条全过

## 一、结论先说

R7 修掉的是**三个「别的路径不受管」类缺陷**。它们的共同点是：主路径上一切正常，
出问题的一定是**旁路**——而旁路恰恰是用户最容易踩到的那条路。

| 缺陷 | 根因 | 用户可见后果 |
|---|---|---|
| 技能脚本绕过执行器 | `SkillRuntimeBridge.tool()` 直接 `registry.execute`，不走 `RegistryToolExecutor` | 脚本里的 `agent.http()` **没有任何超时保护**、没有熔断；`agent.writeFile()` 真实改了文件，日志里却一片空白 |
| 技能 callId 确定性重复 | callId 是 `skill:<id>:<工具名>`，同一脚本连调两次同一工具 → **同一个 id** | 回喂模型的 ToolMessage 出现重复 id；恢复器按 id 配对时把两条 DISP 配到一条 SETTLE 上，**判定结果直接是错的** |
| 子代理不在事件流里 | `SubAgentRunner` 构造 `RealAgentLoop` 时压根没传日志句柄 | 用户报「卡住了」时只看到主代理在等，**完全看不见子代理在干什么**；而子代理虽然只有无副作用工具，脚本形态技能却能写文件 |

还有一个更隐蔽的：改造前**整条事件流没有「谁在执行」这个维度**。
即便把上面三处补上，主代理、技能脚本、子代理的事件混在一起仍然无法区分——
所以 R7 先建立**执行作用域（scope）**这个载体，再把非主路径接进来。

### 本轮附带落地

- **NDJSON 事件流导出**（原待办项）：存储仍是 TSV（崩溃恢复走「同进程反复读回」，
  split 比解析 JSON 便宜），导出为 NDJSON 给跨工具消费用。
- 顺带修掉一条**陈旧断言**：`RepairVerification U9` 断言的是 v1 的列数（6 列），
  v2 加了 scope 列变 7 列——产品行为本就正确，坏的是断言的字面量。

## 二、缺陷一：技能脚本绕过执行器

### 2.1 症状

一个脚本形态技能执行 `agent.http('GET', 'https://slow.example')`，
对方不响应。用户看到的是：界面卡住，模型不吭声，日志里只有一行
`脚本执行超时（>10s）`。

### 2.2 根因：技能路径根本没进执行器

改造前 `SkillRuntimeBridge.tool()` 的最后一行是：

```kotlin
val call = ToolCall("skill:${skill.id}:$name", name, obj)
return runBlocking { registry.execute(call).content }
```

`registry.execute` 是**最底层的直调**——它在执行器（`RegistryToolExecutor`）之下。
于是技能路径拿不到执行器提供的全部东西：

| 执行器提供 | 技能路径（改造前） |
|---|---|
| R2 工具级超时预算（只读 90s / 写 600s） | **无**——只剩外层 10 秒脚本看门狗 |
| T04 失败熔断（同一调用失败 ≥2 次即拦） | **无** |
| R1「先落盘再执行」`ToolDispatched` | **无**——技能改了文件，日志一片空白 |
| 结果码（`tool_timeout` / `approval_denied` / …） | **无**——只有一段格式化文本 |

10 秒看门狗不是超时保护，是**放弃等待**：Rhino 1.7.14 无法强制中断已在跑的求值线程，
超时只是让协程返回 null，Rhino 那个线程仍会继续空转。所以「脚本超时」的代价是
**一个永久占住的线程 + 一个仍然在跑的请求**。

### 2.3 修法：走同一个执行器，DISP 交回执行器写

技能路径改为构造自己的 `RegistryToolExecutor`（共享 `FailureGuard`），
`approval = null`（脚本不得代弹审批——需确认的工具在第三道门已被拒绝）。

**关键细节**：DISP 必须由执行器的 `beforeEffect` 写，**不能**在脚本侧写。

这一点是本轮踩到并修掉的一个真实缺陷。最初的实现是「脚本侧先写 DISP，
再交给执行器判定」：

```kotlin
// ✗ 错误的第一版
turn?.toolDispatched(step, call.id)      // 先写
val outcome = executor.execute(call, d)   // 执行器内部才判熔断/审批
```

问题在于：`DISP` 的语义是「**越过了执行边界**」，而熔断拦截、审批拒绝、未知工具
这些路径都**没有**越过。先写 DISP 就会给一个**根本没执行**的调用留下 DISP——
崩溃恢复看到「有 DISP 无 SETTLE」，判成 `OUTCOME_UNKNOWN`，
让用户去核对一件**从未发生过**的写操作。

修法与主路径完全同序：**熔断判定 → 审批 → 写 DISP → 真正执行 → 写 SETTLE**。

## 三、缺陷二：技能 callId 确定性重复

改造前 callId 是 `skill:<skillId>:<工具名>`——**确定性**的。后果有两处：

1. **回喂模型的 ToolMessage 重复 id**：脚本连调两次 `agent.readFile()`，
   两条 ToolMessage 的 id 相同，模型侧配对混乱。
2. **恢复器配对错乱**（更严重）：回合日志里两条 `ToolDispatched` 共用一个 id，
   恢复器按 id 配对时把第一条的 SETTLE 算到第二条头上——
   崩溃时判定出的「哪个调用已生效」就是错的。

修法：callId 加序号 → `skill:<skillId>:<工具名>#<n>`。

## 四、缺陷三：子代理不在事件流里

`SubAgentRunner` 构造 `RealAgentLoop` 时**没有传日志句柄**——子代理跑在独立的
loop 里，主回合日志里连一个子代理事件都没有。

修法有两处讲究：

### 4.1 并入主回合文件，而不是自己开一个

崩溃恢复是**逐文件**判定的（扫描 → 找出未闭合回合 → 补尾）。
子代理单独成文件的话，「主回合到底有没有产生副作用」就得**跨文件聚合**——
而恢复流程必须在**单个文件内自洽**地判定。

所以子代理用主回合的**派生句柄**：同一个文件、同一把锁、同一个序号序列，
事件带 `scope=sub:<标题>` 标签。

### 4.2 作用域是「开放的」，不是枚举

技能 id、子代理标题都是运行期才知道的，用枚举只能表达「三类路径」，
具体的「哪个技能」就没了。所以作用域用**带前缀的字符串**：

| 作用域 | 含义 | 类别判定 |
|---|---|---|
| `main` | 主代理自身 | `RunScope.KIND_MAIN` |
| `skill:<skillId>` | 某个技能脚本 | `KIND_SKILL` |
| `sub:<标题>` | 某个子代理任务 | `KIND_SUBAGENT` |

前缀在 `RunScope.kindOf()` 里集中定义，供聚合统计与告警使用。

## 五、执行作用域怎么传递：为什么不用逐层传参

技能脚本与子代理都在**别人**的调用栈里执行：

```
主代理回合
  └─ use_skill 工具（主路径）
       └─ SkillExecutor.runSkill
            └─ Rhino 线程
                 └─ SkillRuntimeBridge.tool()   ← 脚本在这里调工具
```

要让最内层的 `bridge.tool()` 知道「当前回合日志句柄是谁」，逐层加参数会一路污染：
`use_skill` 工具签名、`SkillExecutor.runSkill` 签名、`SkillRuntimeBridge` 构造参数……
每加一条新执行路径就要改一遍全部中间层——这正是「漏一处就静默失效」的做法。

R7 用**协程上下文**（`AgentScope` + `AgentScopeContext`）传递，只改两端：
**入口安装、出口读取**。

两个实现细节值得记：

- **用 `ThreadContextElement` 而不是裸 `ThreadLocal`**：协程会挂起并在另一个线程恢复，
  恢复时裸 `ThreadLocal` 的值是那个线程的旧值。`ThreadContextElement` 由协程库
  负责「挂起时存、恢复时还原」。
- **自定义 key**：`ThreadContextElement` 自带的 key 是所有实例**共享**的
  （`AbstractCoroutineContextElement.Key<ThreadContextElement<*>>`），
  多个上下文元素挂进同一个协程时只有最后一个能被按 key 取到。
  `AgentScopeKey` 单独定义才拿得回本元素。

## 六、日志格式：v1 → v2

`RunEvent` 增加了 `scope` 维度，codec 随之升版：

```
v1: v1 \t seq \t atMs \t turnId \t TYPE \t 字段…
v2: v2 \t seq \t atMs \t turnId \t scope \t TYPE \t 字段…
```

**v1 文件必须仍能读**：崩溃恢复的依据是历史日志，读不懂等于让旧设备上的
未闭合回合永远补不上尾。读侧把版本头剥掉后，两种格式的 `TYPE` 与字段是同一套
相对布局，读侧代码不用分叉；v1 的 scope 缺省为 `main`。

序号唯一性由**共享计数器**保证：派生写入器与主写入器共用一个 `AtomicLong`，
否则两个作用域的事件在文件里会各自从 1 开始编号，读回按 seq 排序就乱了。

## 七、NDJSON 导出

存储格式仍是 TSV——崩溃恢复走的是「同进程反复读回」这条路，split 比解析 JSON 便宜，
也没有转义地狱。NDJSON 是**导出格式**，给跨工具消费用：

```json
{"seq":1,"at":100,"turn":"t1","scope":"main","type":"open"}
{"seq":2,"at":110,"turn":"t1","scope":"main","type":"assist","step":1,"calls":[{"name":"read_file","id":"c1"}]}
{"seq":3,"at":120,"turn":"t1","scope":"main","type":"disp","step":1,"call":"c1"}
{"seq":4,"at":130,"turn":"t1","scope":"main","type":"settle","step":1,"call":"c1","status":"SUCCEEDED","error":""}
```

约定：一行一个完整 JSON 对象、行内不含裸换行。转义规则手写而不引序列化器——
这个纯 IO 层不值得多一个依赖方向。

导出的信息与 TSV 存储**一致**（不增不减）：TSV 层净化掉的字符（分隔符、换行）
在 JSON 里也不会凭空回来。
