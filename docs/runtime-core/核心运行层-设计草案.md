# 运行层内核：设计草案与第一版实现

> 分支 `core/kernel` ｜ 2026-10-30 ｜ 6 个文件 995 行 + 1 个 harness ｜ 47 项断言全过

## 一、结论先说

你说的「运行层只留核心」，真正要动的不是 `runtime/`（那 3 个文件只管本地模型空闲卸载，加起来 532 行），
而是**每轮发消息都要经过的那条路**。现在的路径上有三处长在关键路径上的开销：

| 开销 | 现状 | 每轮成本 |
|---|---|---|
| 工具表全量发送 | 只有 `local-llama` 被裁到 7 个，云端 52 个全发 | ≈ 8000 字符 / 4k token（实测见 §四） |
| 系统提示整块重拼 | 角色+规则+工具提示+记忆+时间拼成一整块，每轮必变 | 本地推理 KV 前缀 100% 失效 |
| 历史裁剪从头砍 | 超预算就把最早的对话丢掉 | 丢掉任务原始意图，模型开始重复干活 |

这三条都不是「功能太多」，而是**功能被放在了每轮必经的位置上**。所以核心化的做法是：
把这些挪出循环，循环只留「请求 → 调工具 → 回填 → 再请求」。

## 二、三界划分

| 界 | 内容 | 判定标准 |
|---|---|---|
| **核** | 消息模型、主循环、工具契约、暴露策略、提示分段、预算折叠 | 每轮必经，且与具体功能无关 |
| **壳** | 浏览器、无障碍、终端/SSH、记忆、技能、知识库、子代理、工作流、审批 UI、二维码 | 用到才加载，不用就不该出现在请求里 |
| **外** | 本地推理、容器、抓屏 | 已是首用触发，这块本来就对 |

现有的 `core/agent/RealAgentLoop.kt`（974 行）把三界搅在一起：它同时做循环、拼提示、裁上下文、
选工具、算费用、注入记忆。结果是每加一个功能，循环就长一截，而且新功能自动进入「每轮必跑」的集合。

## 三、内核六件套

放在 `app/src/main/java/com/example/agentkit/core/kernel/`，零 Android 依赖、零第三方依赖（只用 stdlib + 协程）。

| 文件 | 行数 | 职责 | 关键取舍 |
|---|---|---|---|
| `KernelTypes.kt` | 174 | 消息、调用、入参、模型档位、结果 | 消息模型与 UI 渲染模型分开，内核不认识 Android |
| `ToolSpec.kt` | 133 | 工具契约 | `brief`/`params` 是**函数**（惰性求值）；审批看参数不看布尔 |
| `Exposure.kt` | 154 | 工具暴露三模式 | 按**能力档位**分派，不再维护 provider 白名单 |
| `Prompt.kt` | 94 | 提示按变化频率分段 | 稳定段逐字节一致，易变段永远在最后 |
| `Budget.kt` | 154 | 预算折叠 | 早期对话折成一条摘要，不从最新往回砍 |
| `Kernel.kt` | 286 | 主循环 | 只做四件事；功能全部通过 Hooks / Event 挂载 |

### 3.1 暴露三模式（省钱的主开关）

| 模式 | 模型看到的 | 触发档位 | 实测工具表 |
|---|---|---|---|
| `FULL` | 全部 52 个工具的完整说明 | 云端大模型 | 7997 字符 |
| `GROUPED` | 已激活组的完整说明 + 其余组只列组名 | 端侧较强模型 / 小参数云端 | 224 字符（激活一组后 1004） |
| `META` | 只有 3 个元工具：`__find_tools` / `__activate_group` / `__call_tool` | 端侧小模型 | 213 字符 |

关键设计：**执行侧永远看得见全部工具**。裁剪只影响模型的视野，不影响查找。
模型编造一个没暴露的工具名时，内核如实报告「它在未激活的组 X」，而不是假装不存在——
后者会让模型反复编造，浪费更多轮次。

### 3.2 提示分段（省钱在本地推理上）

```
[FROZEN] 身份 / 规则 / 工具调用格式   ← 整会话逐字节不变，排最前
[SESSION] 人格 / 模型配置 / 已激活技能  ← 会话内不变
[TURN]   时间 / 本轮计划 / 记忆摘要     ← 一定变，所以放最后
```

`Prompt.signature` 是对 FROZEN+SESSION 的 FNV-1a 指纹。两次请求指纹相同，本地推理的 KV 前缀就还能用；
指纹一变，日志里能立刻看出「是规则段被改了」还是「只是 TURN 段在变（正常）」。

### 3.3 预算折叠（不是硬砍）

以用户消息为界把历史切块，最近 `keepRecent` 块原样保留，更早的块折叠成**一条 system 摘要**：

```
[早期对话已折叠 48 条]；最初的任务：第 0 轮：帮我处理第 0 件事…；已用过的工具：read_file
```

摘要优先用调用方提供的 `Summarizer`（可以接本地小模型），失败或未提供时退回结构化摘要。
保留「最初的任务」是刻意的——那是丢了之后模型最容易跑偏的东西。

### 3.4 审批看参数

`shell_run` 跑 `ls` 和跑 `rm -rf` 是两件事。契约里审批是一个 `(Args) -> Approval`：

```kotlin
approval = { a -> if (a.opt("cmd")?.startsWith("rm") == true) Approval.ASK else Approval.ALLOW }
```

自检过程中这条抓到一个真 bug：元工具转发时内核只有原始 JSON 串、读不出子参数，
`opt("cmd")` 返回 null，`startsWith` 判定为 false → **`rm -rf` 被当成安全命令放行**。
修法是给 `Args` 加 `opaque` 标记，读不到参数 + 有副作用的工具一律降级为询问（fail-closed）。

## 四、实测数字

`bash scripts/qa/run-kernel-core-verification.sh` → **47 项断言全过**。

```
—— 真实规模（52 个工具 / 11 组）——
全量          7997 字符  ≈ 3998 token（现状：云端一路全发）
分组·未激活    224 字符  ≈  112 token
分组·激活一组 1004 字符  ≈  502 token  (比全量省 87%)
元工具         213 字符  ≈  106 token  (比全量省 97%)
```

> 这里的 7997 字符用的是 harness 里的**简化描述**（每工具一句话），只用来比较三种模式的相对差距。
> 换上仓库真实的 56 个工具与描述后是 21419 字符，见 §六之二。

一个 6 步任务按 `GROUPED` 算：工具表从 6 × 7997 = 48k 字符降到约 6 × 1000 = 6k 字符。
按 2 字符/token 粗算，单轮约省 1.5k–3.5k token；具体省多少取决于模型实际分词，
但**方向是确定的：工具表从「每轮固定 4k token」变成「每轮几百」**。

自检覆盖的不只是数字，还有会真出问题的路径：

- 编造工具名 → 不执行、回填「没有名为 X」+ 自纠提示
- 分组模式直接调未激活组的工具 → 不执行、提示先激活
- 审批拒绝 → 不执行，且回填原因
- 工具抛异常 → 收敛成带 hint 的失败结果，整轮不崩（`CancellationException` 原样抛）
- 单条消息超预算 → 标记 `truncated` 而不是静默丢

| 现有 | 行数 | 去向 | 处理方式 |
|---|---|---|---|
| `core/agent/RealAgentLoop.kt` | 974 | `Kernel.kt` 286 行 + `Hooks` | 循环主体重写；提示/裁剪/暴露/记账全部移出 |
| `core/agent/ContextBudget.kt` | 281 | `Budget.kt` 154 行 | 从「按比例砍」改为「分块折叠」 |
| `core/ToolExposurePolicy.kt` | 123 | `Exposure.kt` 154 行 | 删白名单，改按档位分派；保留「新工具默认不暴露」的安全侧 |
| `core/AgentContract.kt` 的消息模型 | ~80 | `KernelTypes.kt` | 内核用独立消息类型，`ChatViewModel` 侧加一层转换 |
| `core/AgentContract.kt` 的 `AgentTool` | ~50 | `ToolSpec.kt` | 52 个工具**不用改**，用适配器包一层即可（见下） |
| `runtime/*`（3 文件 532 行） | 532 | 不动 | 空闲卸载与内核正交，不需要合并 |
| `ui/ChatViewModel.kt` | 4110 | 暂不动 | 第一步只替换它内部调 loop 的那一段，避免和 UI 改动绑在一起 |

**适配器是关键的成本控制点**：现有 52 个工具实现 `AgentTool`，不要求它们改成 `ToolSpec`，
而是写一个 `ToolSpec(legacy: AgentTool)` 的包装——`brief` 取自 `description`，`params` 由
`JsonSchema` 转 `List<Param>`，`approval` 转调 `needsApprovalFor`。这样迁移不必一次性改 52 个文件。

### 实测（`bash scripts/qa/run-kernel-exposure-verification.sh`，30 项全过）

```
全量          56 个 → 21419 字符 ≈ 10709 token   ← 改造前云端每轮都发这个
云端·分组     16 个 →  6007 字符 ≈  3003 token   ← 省 72%
本地·最小集    5 个 →  1931 字符 ≈   965 token   ← 省 91%
```

工具表按 OpenAI function-calling 的报文结构拼算（name + description + 参数 schema），
不是只算 schema。数字是估算（2 字符/token），量级可比，绝对值有 ±15% 误差。

### 行为变化（必须知道）

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 云端首轮 | 56 个工具全发 | file + ui + skill 三组（14 个）+ 2 个元工具 |
| 云端要用记忆/工作流 | 直接能调 | 先调 `__use_tools(groups="memory")`，多一轮 |
| 本地小模型 | 写死 7 个（`LOCAL_CORE_TOOLS`） | file 组 3 个 + 2 个元工具 |
| 模型编造工具名 | 走未知工具路径 | 同上，且提示「用 `__find_tools` 查」 |
| 新增工具 | 忘了登记 = 对本地永久隐身 | 自动按名字归组，绝不会消失 |
| `forceFullTools = true` | 全量 | 全量（行为完全一致，可作回退开关） |

**代价说清楚**：分组模式在「需要用未激活组」时会多一轮 `__use_tools`。
按 6 步任务、其中 2 步需要新组算，多 2 轮 ≈ 多 2 次往返；但省下的是 6 × 4000 token 的固定开销。
只有当任务极短（1–2 步）且恰好不需要任何工具时，分组才可能比全量贵——那种情况本来也不该带工具表。

## 七、没做的、不打算做的

诚实清单，避免这份东西被当成「已经能用」：

- **没有流式**。`Kernel` 是 `suspend` 一次性拿完整回复。流式要在 `ModelCaller` 里做，
  用 `Event.Text` 分片发出——接口留了，实现没写。
- **没有真实 provider 适配**。`ModelCaller` 目前只有自检里的假实现。
  接 OpenAI / Claude / 本地 llama 的适配器要在第二步写。
- **token 是估算不是实测**。内核用字符数（2 字符/token）当上界，不引 tokenizer。
  精确值要用服务端返回的 usage 二次校正。
- **摘要器没接本地模型**。`Summarizer` 目前只有结构化兜底。
- **没在多模态上验证**。图片消息在 `Msg` 里没有字段，需要的话得加。
- **没有并发执行工具**。现有实现会判「全批只读才并行」，内核目前严格串行。
  这是有意的：先保证正确，并行是优化项。
- **Android 侧只改了工具暴露这一处**（`RealAgentLoop` 的 3 个私有方法），
  循环主体、提示拼装、上下文裁剪都还是老的。内核那 6 个文件仍未被主链路使用。

## 八、净室声明

设计过程中读过 RikkaHub、IRIDIS、Operit 的结构（Coomi 与 AiCode 的公开仓库里没有 Kotlin 源码，
只有壳与 rootfs，无法参考实现）。借的是**结构层面的判断**：

- 循环要薄、扩展点要外置（三家都是这样，这不是谁独创）
- 工具描述惰性求值、按组折叠（IRIDIS 的分组激活、Operit 的元工具，是同一个问题的两种解法）
- 提示按稳定性分段以复用 KV 前缀（IRIDIS 的做法）

没有复制任何一行代码、类名、函数名或注释措辞。本目录的命名（`Turn` / `Surface` / `Stability` /
`Fitted` / `opaque`）与逻辑切分均为自行设计，其中 `opaque` + fail-closed 的降级规则是自检跑出来的，
不是从别处抄的。

数字也没有照抄：IRIDIS 的档位表是它自己真机测的，我们的 `Budget.CHARS_PER_TOKEN = 2.0`
是按中英混排的保守上界推的，没有引用任何外部实测值。

## 九、下一步建议

第一步（工具暴露）已完成，等你本地 `compileDebugKotlin` + 一次真机验证。验证通过后：

**第二步：提示拼装**。把 `buildSystemPrompt` 拆成 FROZEN / SESSION / TURN 三段，
`MEMORY_USAGE_PROMPT` 改成「启用记忆才拼」。这一步的收益不在 token 数，而在本地推理的
KV 前缀复用——现在的实现每轮都让前缀失效，本地模型每轮都要重新 prefill。

**第三步：换循环**。`RealAgentLoop` 内部改调 `Kernel.run(turn)`。这一步之前必须先补：
流式（`ModelCaller` 分片）、真实 provider 适配、审批桥接。否则会丢掉流式输出，
而这是用户能直接感知的退步。

**暂不建议动**：`ChatViewModel` 那 4110 行。它是 UI 层，和「每轮成本」无关；
先动它只会把两件事的风险搅在一起。
