# W-78：-O3 确认生效；13 秒不是线程问题，是「权重第一次被读」

## 一、这次日志给出的最强证据

1.446 的日志里有三个数字，拼在一起说明优化确实生效了：

| 行 | 值 | 含义 |
|---|---|---|
| `编译优化：已开启` | — | `__OPTIMIZE__` 在，三层保险任一层成立 |
| `预热 decode：1 token / 13436 ms（6 线程）` | 13.4 s | 首次触碰 2 GB 权重 |
| `预热 decode 重试：1 token / 170 ms（4 线程）` | 170 ms | **稳态**单 token forward |

170 ms / token ≈ 5.9 tok/s，正好落在 3B Q4_K_M 在手机 CPU 上的正常区间
（IRIDIS 同款设备 4.8 tok/s）。**-O0 时期的 7521 ms 不会再回来了。**

## 二、但「6 线程 13 秒」不是线程问题

那天我们看到的是：

```
预热 decode：1 token / 13436 ms（异常慢）
预热 13436 ms 过慢，线程 6 → 4 重建上下文后重试一次
预热 decode 重试：1 token / 170 ms（线程 4）
```

表面上「线程越多越慢 79 倍」。但这个解释站不住：

- 79 倍远超线程调度的量级（线程争用最多 1.5~2 倍）；
- **紧接着的 170 ms 是在同一个进程、同一份权重上跑出来的**，只是多了前面那一次；
- 模型加载只花了 2993 ms —— mmap 只建映射，不读数据。

所以那 13 秒花在「2 GB 权重第一次被真正读进来」：4 KB 页随机缺页 + Q4_K 权重重排。
它是一次性成本，跟线程数、prompt 长度都无关。**第二次无论几线程都是百毫秒级。**

错的是我们的判据：把一次性成本当成了「这组线程不行」，于是白白把 6 线程降成 4 线程，
还可能因此少用了两个核。

## 三、四处改动

### 1. 冷启动成本挪到加载阶段

`nativeInit` 末尾用 bos 做一次 1-token decode，日志写成：

```
冷启动预热完成：1 token / 13xxx ms（含权重首次载入与重排，一次性成本）
```

用户看到的是「模型就绪，耗时 16 秒」，而不是「就绪 3 秒 → 发消息 → 空白 13 秒」。
后者会被当成卡死，前者只是慢一点。顺带把 bos 记进 KV 账本：下一轮 prompt 也以
bos 开头，公共前缀正好复用，第一轮的预热探针也省了。

### 2. `POSIX_FADV_WILLNEED` 预读

mmap 之前对模型文件做一次异步预读，让内核在解析 GGUF 头部的同时把权重拉进 page
cache。和 mmap 共用同一份缓存，能把 13 秒压掉一部分（取决于闪存，UFS 3.x 通常
1 GB/s 以上）。失败也不影响功能。

### 3. 预热判据：慢一次先复测，两次都慢才动线程

```cpp
if (ms > WARMUP_SLOW_MS) { ms = min(ms, probe()); }   // 复测取快的
if (ms > WARMUP_SLOW_MS && n_threads > 4) { ... }     // 两次都慢才降
```

降线程改用 `llama_set_n_threads`（b4600 有），就地生效，**不重建 context、不清 KV**。
原来那版重建一次要几十毫秒，还会把已经算好的前缀扔掉。

### 4. native 日志加序号，Kotlin 只消费本轮

这是日志里另一个真 bug。第二轮的日志是这样：

```
15:30:57.278 开始生成：… 线程 6
15:30:58.783 预热 decode：1 token / 13436 ms（异常慢）      ← 1.5 秒后
15:30:58.783 预热 13436 ms 过慢，线程 6 → 4 …
15:30:58.785 prefill 完成：复用 0 / 共 83 token，耗时 5169 ms
15:30:58.786 prefill 开始：从第 95 个起，共 108 token …
```

中间那四行的时间戳几乎完全相同 —— 它们不是跑出来的，是**把上一轮的行又打了一遍**。

原因：native 的 80 行诊断环形缓冲是进程级的、跨请求累积；Kotlin 每个请求新建一个
「已见过文本」集合去重，于是第一轮把所有旧行都当新行输出。危害不只是日志难看：

- 用户以为「又卡了 13 秒」；
- 看门狗读 `warmupMs = 13436`，据此把首字预算算成 45 s 或 150 s，完全错位。

现在每行带 `#<seq>|` 前缀，Kotlin 在开始一轮前取 `nativeLogSeq()` 做基线，
只消费序号更大的行。摘要也按基线过滤，第二轮不会再出现上一轮的 prefill。

## 四、顺手调的两处

| 项 | 旧 | 新 | 理由 |
|---|---|---|---|
| `PREFILL_CHUNK` | 64 | 128 | 83 token 的轻聊 prompt 原本切成 64+19，第二块只装 19 个 token 却付一次完整同步开销 |
| `n_threads_batch` | = n_threads | `min(核数, n+2)` | prefill 是纯算力（一批 token 共享一遍权重读数），生成是内存带宽（多线程互相抢）。-O0 已排除，可以分开设 |

## 五、这一版之后应该看到什么

第一轮（进程冷启动）：

```
加载模型 …（2007 MB）
冷启动预热完成：1 token / 2xxx~13xxx ms（一次性成本）
模型就绪: …，耗时 8~18 秒
开始生成：轻聊模式，prompt 2xx 字符
预热 decode：1 token / 1xx ms（正常）        ← 不再有 13 秒
prefill 完成：补算 82，耗时 3~5 秒
生成完成：xx token / xx 字符，3~6 tok/s
```

第二轮起：

```
复用已加载实例 …
开始生成：轻聊模式，prompt 2xx 字符
prefill 完成：复用 95 / 共 108，补算 13，耗时 ~1 秒
生成完成：xx token / 3~6 tok/s
```

判据只有两条：

1. `预热 decode：1 token` 应该在 **100~400 ms**；如果是几秒，说明冷启动没被吸到加载阶段；
2. 第二轮日志里**不应该再出现** `共 83 token`、`13436 ms` 这些第一轮的行。

## 六、还没做的

- **AARCH64 repack 仍然关着**。它在 -O3 下很可能能再提 20~50%（Q4_K 的 8x8 交错点积），
  但会把这 13 秒变长，且上次「卡死」的阴影还在。等这一版把冷/热分离验证干净，再单独开一版对比。
- **Vulkan / NPU**：留给后续。
- 3B 在 4 线程只有 5.9 tok/s 是物理上限区间，想要「秒回」得换 1.5B 或 0.5B。
