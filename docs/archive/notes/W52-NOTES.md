## 一、问题：能用，但比装 Shizuku 还麻烦

W-51 的配对对话框要四个字段：

```
IP 地址
配对端口（配对弹窗里）
6 位配对码
连接端口（主页 IP:端口）
```

其中**两个端口长得像、位置还不在一处**，我第一次写文案时专门加了句「填反了会提示解密失败」——
这句话本身就是设计问题的证据：需要靠提示语才能让人填对，说明输入项本身该消失。

用户的对比很直接：装 Shizuku 只需点一次授权。

## 二、改法：mDNS 自动发现，只留配对码

四个里**只有配对码是拿不到的**（系统弹窗里的随机数，属系统安全边界）。其余三个都在
Android 无线调试的 mDNS 广播里：

| 服务类型 | 广播的端口 = | 广播时机 |
|---|---|---|
| `_adb-tls-pairing._tcp` | 配对端口 | 仅「使用配对码配对设备」弹窗打开期间（约 2 分钟） |
| `_adb-tls-connect._tcp` | 连接端口 | 无线调试开启期间常驻 |

### 新增 `AdbEndpoint.kt`（纯逻辑，可测）

`mergeDiscoveredAdbServices(pairing, connect)` 负责「发现结果怎么挑」，三条规则都有踩坑背景：

| 规则 | 为什么 |
|---|---|
| host 优先取**配对**服务 | 它与用户此刻正开的弹窗同源；换 Wi-Fi 后常驻的 connect 广播可能还是旧地址 |
| 同类多条取**端口最大** | 无线调试每重开一次就换新端口；旧广播（已失效）还在缓存里时，靠这条挑中新的 |
| 非法端口（0/越界）**丢弃而非当 0** | 0 会被下游判成「未配置」，静默失败比明确报错更难查 |

### 新增 `AdbDiscovery.kt`（Android 侧接线）

用 `NsdManager` 而不是自己发 mDNS 查询——系统服务已处理组播加入、IPv6、多网卡选择。
代价是它的两个已知限制，都做了规避：

1. `resolveService` 并发会 `FAILURE_ALREADY_ACTIVE` → 串行队列逐个解析；
2. 同 serviceType 重复 `discoverServices` 会 `listener already in use` → 每次新建 listener、
   `stop()` 成对注销、所有调用包 `runCatching`。

**失败是常态，不是异常**：部分 ROM 限制 mDNS 组播。所以 `start()` 的失败走回调，
UI 保留「手动填写」折叠区——自动发现是加速，不是唯一路径。

### 对话框改造

```
① 手机上：开发者选项 → 无线调试 → 打开开关
② 点「使用配对码配对设备」，弹窗里有 6 位码
③ 在这里输入这 6 位码即可——IP 和两个端口会自动填
```

- 进对话框即开始扫描，状态行实时显示进度：
  - 「已找到 192.168.1.8：配对端口 37123、连接端口 35123（已自动填好）」
  - 「已找到连接端口 35123，配对端口还没出现——请在手机上点『使用配对码配对设备』」
  - 20 秒后收工（mDNS 常驻监听耗电，且配对端口只在弹窗期有效），可「重新扫描」
- 默认只显示「6 位配对码」一个输入框；IP / 两个端口收进「手动填写 IP / 端口」折叠区
- 权限：`CHANGE_WIFI_MULTICAST_STATE`（normal，安装即授予，不弹窗）

## 四、没做的事

1. **mDNS 在真机上的可达性未验**：`NsdManager` 对系统自己广播的服务能否稳定解析，
   部分 ROM 上会失败（尤其国产定制）。失败时对话框会明说「没拿到完整端点」并引导手动填，
   不会静默卡住。真机试一次即可确认。
2. **没能去掉配对码**：它是系统弹窗的随机数，除非去读无障碍/通知（越界，不做）。
3. **多网卡场景**：手机同时开热点 + Wi-Fi 时，`NsdManager` 给的是当前活动网络的地址；
   若配对服务广播在另一张网卡上，可能拿不到。此时代码退回手动填写。
