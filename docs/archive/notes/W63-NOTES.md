# W-63：重启后第一条命令必然失败（过期句柄）(2026-10-27)

真机 1.402，隔着一次 App 重启（15:03 新进程）：

```
15:16:17 DEBUG [Tool] → shell_run {"command":"echo hi","identity":"user","prefer_proot":false,"session":"b69f"}
15:16:17 WARN  [Tool] ← shell_run ERROR 0ms [error] code=no_such_session
         message: 会话句柄「b69f」不存在。
         hint: 会话可能已关闭或被回收；不带 session 重新调用一次以开辟新会话。
15:16:17 ERROR [HTTP] 请求失败 code=429 ...
```

`b69f` 不是模型编的——它是**上午 13:54 那次 `id` 返回的句柄**，躺在历史消息里。
App 重启后会话池空了，模型照着历史抄了一个已死的句柄，整轮白跑。

## 为什么这是个真问题，不是模型笨

1. **历史里有句柄，就一定看着"有效"**。模型无法知道进程重启过——它只知道「上次用 b69f 成功了」。
2. 工具返回的 hint 是对的（「不带 session 重试」），但那是**第二次往返**：用户要多等一个
   模型轮次，还要再花一次 token。真机上这次更是直接撞上 429，用户连第二次机会都没有。
3. 用户视角：发一句话，出来一张红色失败卡，写着「会话句柄不存在」——他会以为工具坏了。

## 修法：句柄失效 = 没有会话，但必须说出来

`ShellTool` 原来：

```kotlin
if (pool.lookup(sessionArg) == null) {
    return ToolResult.fail(code = "no_such_session", ...)
}
```

现在：自动开一条新会话把命令跑完，并在返回里点明：

```
会话 3c7a（身份 user，池 shizuku） 退出码 0，已开辟新会话（原句柄 b69f 已失效
——App 重启或会话被回收，工作目录已重置为默认）
```

**为什么一定要写「工作目录已重置」**：静默替换比直接失败更危险。模型会以为
`cd /sdcard` 还生效，后面每条命令都跑在 `/` 下，报错还找不到原因。
这句是给模型看的，也是给用户看的。

`bad_handle`（格式非法，如 `ZZZZ`）仍然直接失败——那是模型编的，不该兜。

## 同批的两处打磨

### 1. exit=1 不再吓人

真机：Alpine 装 `nodejs npm`，退出码 1，但

```
node --version → v20.15.1
npm  --version → 10.9.1
```

报错来自包管理器收尾的 trigger 脚本（`Executing busybox-...trigger` → `1 error`），
跟能不能用无关。原来的结论是「已就位：包管理器报了错误，但自检通过」——
话是对的，但用户看到「报错」两个字还是会来问。

改成：`Node.js 安装完成。包管理器收尾时报了个错（多在 trigger 脚本，不影响使用），node 已验证可运行。`

### 2. 命令预览不再撑爆卡片

`将在容器内执行：ALP=$(sed -n '1s/...') ...` 这条有 200 多字符（含社区源前奏），
不截断会把卡片撑到五屏高，下面的按钮全被挤出视野（真机 15:05 截图）。
现在 `maxLines = 3` + 省略号。

## 验收

1. 杀掉 App 重开 → 直接发「用 shell_run 执行 pwd」（不发第二句）：
   应该**成功**，返回里带「已开辟新会话（原句柄 xxx 已失效…）」。
2. 容器装 Node.js：完成后卡片显示「安装完成」，不再出现 exit=1 字样。
3. 卡片里那段「将在容器内执行」最多三行。

## 遗留

- 句柄没有"代际"信息：现在只能靠「查不到就重建」。更彻底的做法是在历史里给句柄
  加进程标识（如 `b69f@pid`），重启后一眼看出过期——但那要改协议与提示词，收益不大。
- `shell_close` 对不存在的句柄仍返回 `no_such_session`（幂等语义，正确，不动）。
