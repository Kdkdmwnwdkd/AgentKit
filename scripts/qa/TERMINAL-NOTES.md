# 终端仿真器 harness（首轮就抓到一个真 bug）

## 为什么先补这个文件

`terminal/TerminalEmulator.kt`：1040 行、零 Android 依赖、**此前一条断言都没有**。

它吃的是 pty 字节流——shell 提示符、`ls --color`、vim、htop、`top` 的每一次刷新都从这里过。
解析错一个字节，用户看到的是「终端里一堆乱码」或「颜色全错」，而这类 bug **不抛异常、
不进日志**，只会被当成「这个 App 的终端不好用」。全仓库 173 个未被 harness 触及的源文件里，
它是「风险 × 可测性」比值最高的一个：纯 Kotlin、无状态依赖、行为完全确定。

## 首轮跑出来的是什么

第一次跑 77 条断言，6 条红。逐条查下来：**3 条是我自己写错了期望**，2 条是文档与实现不符，
剩下的 1 条是真 bug：

### `REP`（CSI `b`）从来没打出过任何字符

```kotlin
'b' -> repeat(n.coerceAtMost(MAX_REPEAT)) { printCodepointString(lastPrinted) }  // REP
```

看起来对，但 `printCodepoint()` 第一行是：

```kotlin
if (state != ParserState.GROUND) return   // 非 GROUND 态的可打印字符丢弃
```

而 `csiDispatch()` 是在**状态还是 `CSI_PARAM` 时**被调用的——`state = GROUND` 那行在它后面。
于是 `repeat` 里每一次调用都撞在这道门上，静默返回。

后果：`ESC[3b` 只当没发生，屏幕上少三个字符。REP 在 `nvim` 横向滚动、`less`、部分
`zsh` 补全与 `printf` 输出里都会出现。用户看到的不是报错，是「某些程序画出来的界面缺一块」——
这种问题没人会想到去查终端仿真器。

修法不是给 REP 开后门，而是**把状态复位挪到派发之前**（真实解析器都是这个次序：动作发生在
状态转移上，而不是转移之后）：

```kotlin
b in 0x40..0x7E -> {
    state = ParserState.GROUND   // 先复位，再派发
    csiDispatch(b.toChar())
}
```

改完 `ESC[3b` → `ZZZZ`，`ESC[999999b` → 历史里多出 100 行（1024 次重复 / 10 列），
上限 `MAX_REPEAT` 也确实生效。

### 另外两处「文档与实现不符」

`TerminalRow.continued` 的注释写「是否为自动换行产生的**续行**」，实现标的是
「**被截断的那一行**」（xterm LINEWRAPPED 语义）。而且这个字段**没有任何消费方**。
注释已改成实际语义，并写明「现在没人用，留着是为了将来复制时还原软换行」。

## 反向验证

往产品码里注入两个变异，确认断言不是装饰：

| 变异 | 变红的断言 |
|---|---|
| `ED 2` 改为空操作 | ED 2 清空整屏 |
| 宽字符按 1 列推进 | CJK 占两列 / 右半格占位 / 拼接后光标前进 2 |

修 REP 之前，`REP(b) 重复上一个字符` 这条本身就是红的——**这就是它的价值**。

## 自己写错的三条期望（留档，免得下次再犯）

1. `EL 0` 清到行尾后 `trimEnd()` 得 `""` 而不是 `"   "`——断言里我忘了自己做了裁剪。
2. 2005 行写进 2 行屏：实际丢 4 行而不是 5 行（末尾那个 `\r\n` 也算一次换行）。
3. `resize` 把光标从列 10 收敛到 `cols-1 = 4`，不是 5。

第 1 条尤其值得记：**断言里的「期望值」本身要能被解释**，否则红了以后第一反应是改代码而不是
改断言。
