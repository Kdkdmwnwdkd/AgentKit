# W-34 行级 diff（github_diff）

## 缺口

`github_status` 只说"哪些文件变了"，用户/模型还是不知道**具体改了哪几行**。
提交前确认、review 自己的改动，都需要行级 diff。

## 为什么自己写 LCS

只为了"看一眼改了哪几行"，引 diff-match-patch 要几万行代码。
LCS 五十行就够，而且退化策略可以自己完全控制。

## 两个必须的保护

**① 先裁公共前后缀。** 实际改动通常只占文件很小一段，裁完剩下的规模往往从几千行降到几十行——
这一步比任何算法优化都管用。

**② 规模上限。** 裁完仍超过 25 万格子（约 500×500 行）就不做逐行 LCS（DP 表会吃掉几十 MB），
退化为"整段替换"。

## harness 抓到的 3 个真 bug

1. **空文件被当成"一个空行"**：`"".split('\n')` 在 Kotlin 里返回 `[""]`。
   结果"新增文件"被算成"先删一个空行，再新增 N 行"，diff 里冒出一行莫名的 `-`。
   → `splitLines()` 显式把空串视为 0 行。

2. **退化后截断把 + 行全砍掉**：600 删 + 600 增共 1200 行，被 400 行上限截断后
   **只剩删除行**——用户会以为"文件被删光了"。
   → 退化模式改成**两侧各取前 80 行示例** + 明确写出总行数（删除 600 / 新增 600）。

3. **（由 2 连带）** 退化提示原来只写"未逐行比对"，没说总量；
   现在写清"删除 N 行 / 新增 M 行，下面各展示前 80 行"。

## 边界处理

| 情况 | 行为 |
|---|---|
| 本地有、远端无 | 新增文件，全是 `+` |
| 本地无、远端有 | 拒绝并说明"这是删除操作，本工具不支持删远端文件" |
| 两者都无 | 报 `not_found` |
| 含 NUL | 拒绝（二进制 diff 是乱码） |
| 文件 > 1MB | 拒绝（GitHub contents API 也不返回 >1MB 内容） |
| 改动过大 | 退化 + 标注总数 |

- harness **13/13**（基本 9 + 退化/上限 2 + 统计/渲染 2）
- 既有 harness：27/25/14/9/12/13/18/16/34/18/24/21 全无回归
- 反验断言：8 条池条目 + 4 条文案

## 未做

- **不做语法级 diff**（只看行，不看 token）——手机上看行级足够。
- **不做并排视图**——宽度不够，unified 单列更好读。
- **不显示行号**：行号需要跟踪 hunk 起始行，收益小于复杂度；`github_status` 已能给行级定位。
