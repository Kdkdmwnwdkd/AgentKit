# W-33 后台命令 + 回到底部

## 为什么独立实现，不改会话池

`TerminalSessionPool.exec` 靠 sentinel 标记判断"这条命令跑完了"，本质**同步**。
在同一个 PTY 里塞一个十分钟的任务，后面所有命令都在排队等它。要支持后台，
就得给池加"提交-回调"双模式——池是 `shell_run`、`app_stop`、终端页共用的核心，
改它的回归面太大。

所以后台任务走**独立进程**（`ProcessBuilder("sh","-c",…)`），输出直接落文件，
与会话池零共享状态。代价写清楚：**不继承终端会话**（无 cwd 记忆、无 export 环境、
不走 proot 容器），后台只有本机 `sh`（uid = 应用）。

## 两个工具

| 工具 | 作用 | 读/写 |
|---|---|---|
| `shell_background` | 启动长命令，立即返回 job id | 写 |
| `shell_jobs` | 列最近任务 / 查单个任务状态+日志尾巴 / `cancel=true` 终止 | 写（含取消） |

跑完发通知（独立 channel `agentkit_jobs`，可与定时任务通知分开关闭）。

## 关键实现点

**读流与等结束必须并行。** `waitFor()` 在管道缓冲写满时会死锁，所以读流单独起协程，
主流程轮询 `isAlive`（400ms）——顺带就有了超时能力（1 小时硬上限 → kill 并标 timeout）。

**日志超限继续读但不写。** 超过 2MB 后停止写盘，但仍把流读空——不读会让管道堵住、进程卡死。

**五种终态分开。** `done` / `failed` / `cancelled` / `timeout` / `interrupted`。
尤其 `interrupted`：App 被杀后重启，残留的 running 标成「结果未知」，
**不假装还在跑，也不假装成功**。

**取消立刻生效。** `cancel` 先落盘 cancelled 再 destroy 进程，避免 UI 上"点了没反应"；
pump 收尾时检查"是否已是终态"，不覆盖用户的取消。

**日志按行截取。** 按字节截断会把最后一行砍成半句，而用户要看的就是最后那行报错。

## 顺手做的：回到底部

长对话往上翻之后，右下角出现圆形按钮，点一下滚回最新消息。用
`listState.canScrollForward` 判断是否在底部，不需要自己算偏移。

## 已知限制

- **后台任务不走容器**：proot 里的工具链在后台用不了。需要容器环境的长命令只能前台跑。
- **只有本机 uid**：要 root/Shizuku 的长命令也做不了（提权通道是一次性的，没有持久进程）。
- **App 被杀 = 任务中断**：没做前台服务常驻（成本高、耗电、国产 ROM 还会杀）。
- **没做进度百分比**：命令输出格式千差万别，猜进度不如老实显示"已运行多久"。
