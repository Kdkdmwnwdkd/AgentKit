# W-31 并行子代理（spawn_agents）

## 缺口与判断

四家对照里 P1 最后一项：AiCode / Operit 都有「子任务派发」。之前一直没做，因为
"并行子代理"听起来像并行多会话（我们评估过与稳定性冲突）。这次落地的是另一种东西：

**子代理 ≠ 并行多会话。** 并行多会话是多个用户任务同时跑（会抢 Key、抢工具、抢 UI）；
子代理是**主代理把一个只读子任务外包出去，只回收结论**——目的是省主上下文。

具体收益：让主代理"读 8 个文件找某个定义"，那 8 个文件的全文会永久留在主对话里，
之后每轮都要重新计费、还挤掉真正的任务信息。子代理把这段脏活关在独立消息栈里，
只交回一段 ≤1200 字的结论。

## 实现结构

| 层 | 文件 | 职责 |
|---|---|---|
| 纯逻辑 | `core/agent/SubAgentLogic.kt` | 参数校验、提示词、结论提取、汇总、并发归一、白名单 |
| 执行 | `core/agent/SubAgentRunner.kt` | 建子工具表、并发调度、超时/取消/失败分类 |
| 工具 | `tools/SubAgentTool.kt` | `spawn_agents` 参数解析与结果封装 |
| 接线 | `ChatViewModel` | 抽出 `buildMainClient()` 与子代理共用；注册工具 |

## 四条边界（写进代码，不只是注释）

1. **只读**：子代理工具表按 `READ_ONLY_TOOLS` 白名单过滤（16 个：read_file / web_search /
   ui_tree / ocr_image / memory_search …）。并行写会互相踩，而且子代理没有 UI 确认通道。
2. **不递归**：白名单里没有 `spawn_agents`，子代理无法再派子代理（防指数膨胀）。
3. **有预算**：单任务超时 240s、最多 8 步工具往返、上下文 12k token。
4. **可停止**：外层协程取消会传播，正在跑的子代理一起取消；超时只把自己记为失败，
   不影响同批其他子代理。

## 并发策略

`chunked(limit) + 批内 async`，不是一次全并发：手机端同时打 3 个请求最容易撞 429，
分批能让前一批的 Key 冷却在下一批生效。`limit = clampConcurrency(3, tasks.size)`。

## 已知限制（如实记）

- **子代理只有只读工具**：MCP 工具一律不注入（名字以 `mcp_` 开头，无法判断是否只读）。
- **过程不可见**：子代理内部的工具调用不推 AgentEvent，UI 上只有一张 `spawn_agents` 卡片
  从「执行中」跳到「终态」。要看得见过程需要给 Runner 传事件回调并做子卡片，成本大于收益。
- **不会自动派**：是否使用 `spawn_agents` 由模型按工具描述判断；本地小模型基本不会用
  （也不该用——本地模型并发跑 3 个只会更慢）。
- **子任务间无通信**：三个子代理互相看不到对方结论，需要交叉验证时得派第二轮。
