# 契约方法台账（R-19）
#
# 解决的问题：读代码时分不清「这个方法在生产上真的会发生」和「它只是存在」。
# 典型例子：`ConversationStore.flush()` 的注释写着「App 切后台时调用」，而全仓
# 一次都没调用过——注释比代码更有说服力，于是风险被一句话掩盖了。
#
# 三种状态，含义是**可执行**的，不是形容词：
#   WIRED    生产代码（app/src/main）里确实有调用点。runner 会 grep [EXPECT] 那一列；
#            调用点被删了就红——不是靠人记得回来改。
#   DELETED  方法已经从源码删除。runner 验证「确实找不到定义」；
#            只写 DELETED 不删代码，等于把台账当成了免罪符。
#   RESERVED 实现完整、但没有生产调用点，明确保留（附保留理由与接线条件）。
#            runner 验证「现在仍然零调用」；一旦有人接上线，这里会红，提醒改成 WIRED。
#
# 收条目的标准：**契约方法**（public、有行为）。不登记的：Android 生命周期回调
# （系统调）、私有辅助函数、单文件内的局部工具——它们零调用就是编译器会报的死代码。
#
# 为什么 WIRED 要比对完整调用片段：[SYMBOL] 常常是 `flush` 这种烂大街的名字，
# 只 grep `flush(` 会被 `out.flush()`（几十处）喂饱，等于没有判据。EXPECT 写的是
# 「能证明这次接线存在的最小片段」，它必须包含接收者或限定的对象。
#
# 冻结：条目总数写在 runner 里。加条目要同步改那个数字，改的时候必须回答
# 「这条为什么值得进台账」。数字只升不降——删条目等于把一条已裁决的事实抹掉。
#
# 格式：STATUS | SYMBOL | FILE | EXPECT | REASON（竖线分隔，字段内不要再出现竖线）
#   EXPECT 列：WIRED = 必须存在的调用片段；DELETED/RESERVED = 写 `-`
